# HFT 高频面试题库：从一分钟快答到系统故障推演

这不是一份“背完就过”的答案表。面试官通常会沿着你的第一句话不断追问。好的准备方式是：先用一句话给结论，再用不变量、算例或故障边界证明你真的理解。

## 1. 使用方法

每道题按三层作答：

```mermaid
flowchart LR
    A["第一层：一句话结论"] --> B["第二层：机制或算例"]
    B --> C["第三层：边界、例外与权衡"]
```

例如“IOC 和 FOK 有什么区别”：

1. **结论**：IOC 允许部分立即成交，FOK 要求立即全部成交；
2. **算例**：想买 100，当前可成交 60，IOC 成交 60 后取消 40，FOK 通常零成交；
3. **边界**：最终语义以场所规则和协议为准。

### 自评分标准

每题 0–4 分：

| 分数 | 表现 |
| ---: | --- |
| 0 | 无法回答或核心概念相反 |
| 1 | 只会术语，没有机制 |
| 2 | 核心正确，能给简单例子 |
| 3 | 能说明边界、竞态或权衡 |

建议先遮住参考答案，口述 60–90 秒，再对照修正。

## A 组：市场与微观结构快答

### Q1. 什么是 HFT？

**参考答法：** HFT 是一类常见特征包括自动化决策、高消息处理速率、短反应时间和严格延迟控制的电子交易实践，并不是某一种固定策略。消息、订单和成交频率要分开，低延迟也不能绕过风控和规则。

**追问：交易频率高就一定是 HFT 吗？** 不一定。还要看自动化程度、持有/决策时间尺度、接入和系统特征；法律或场所的正式定义可能另有标准。

### Q2. Bid、Ask、BBO、Spread、Mid 分别是什么？

**参考答法：** Best Bid 是最高买价，Best Ask 是最低卖价；二者合称 BBO。Spread 是 `ask - bid`，Mid 是 `(ask + bid) / 2`。Mid 是参考点，不保证可成交。

**追问：BBO 为 99.97/100.01 时 spread 和 mid？** spread 为 0.04，mid 为 99.99。

### Q3. 什么是流动性？

**参考答法：** 流动性描述在较小价格影响和合理时间内完成交易的能力。价差、可见/隐藏深度、成交概率、恢复速度和市场冲击都是维度，不能只用买一数量表示。

**追问：深度大为什么还会滑点？** 深度可能在订单到达前撤走，前面还有其他订单，数量分散在多场所，或订单需要跨多档成交。

### Q4. Maker 和 Taker 有什么区别？

**参考答法：** Maker 的订单先静止在簿中提供流动性；Taker 的到达订单立即与静止单成交、获取流动性。买卖方向不能决定 Maker/Taker，买单也可以是任一角色。

**追问：Maker 一定更赚钱吗？** 不能这样说。返佣/费用只是成本一部分，被动单还可能承受逆向选择、库存和对冲风险。

### Q5. L1、L2、L3 行情有什么区别？

**参考答法：** L1 主要给最优买卖，L2/MBP 给各价格档聚合量，L3/MBO 给单个公开订单事件。粒度越细，消息量、内存和恢复复杂度通常越高；L3 仍不代表能看到全部隐藏意图。

**追问：只有 L2 能否知道精确队列位置？** 通常不能，因为不知道同档撤单发生在你前还是后，也不知道每张订单顺序。

### Q6. Tick size 的作用是什么？

**参考答法：** Tick size 是允许报价变化的最小单位，影响合法价格、价差表达和同价排队竞争。工程上常用整数 tick 存价格，避免浮点比较误差。

**追问：价格 `100.01` 怎样存？** 必须先知道价格缩放或 tick。例如 tick 为 0.01，可存为 10,001 ticks/最小价格单位；换算时还要考虑合约乘数和币种。

### Q7. 什么是 marketable limit order？

**参考答法：** 到达时可以立即与对侧成交的限价单。买单满足 `limit >= best ask`，卖单满足 `limit <= best bid`。

**追问：买入限价 105 能否在 102 成交？** 可以。105 是最高可接受价；许多连续簿按静止卖单 102 成交，但最终以场所规则为准。

### Q8. 市价单与限价单的核心差异？

**参考答法：** 限价单约束最差成交价但不保证成交；市价单强调尽快成交但通常不保证价格，也可能因保护规则或流动性不足不能全部成交。

**追问：怎样避免用魔法值表示市价？** 在类型中用 `Market` / `Limit(price)` 枚举，而不是用 0 或最大整数。

### Q9. IOC、FOK、DAY、GTC 是什么？

**参考答法：** IOC 立即成交可成交部分并取消剩余；FOK 立即全部成交否则全撤；DAY 通常当日有效；GTC 通常撤销前有效，但跨日和产品细节看场所规则。

**追问：可成交量 30、IOC 买 50 会怎样？** 成交 30，剩 20 取消。FOK 买 50 通常整单零成交。

### Q10. Post-only 有什么用？

**参考答法：** 它要求订单只作为 Maker；若到达会立即成交，场所按规则拒绝、取消或调整。不能假设所有场所都会自动后退一个 tick。

**追问：为什么仍要风控？** Post-only 不限制数量、敞口、错误合约或消息速率，也不能保证订单最终不会成交。

### Q11. 价格—时间优先与 Pro-rata 的区别？

**参考答法：** 两者通常都先遵守价格优先；同价时，价格—时间按进入队列先后，Pro-rata 按订单量比例分配，并需处理整数舍入和特殊优先权。

**追问：所有市场都是 FIFO 吗？** 不是，期货等产品可能用 Pro-rata 或混合规则，必须以具体产品规则为准。

### Q12. 什么是队列位置？

**参考答法：** 它描述同价订单中在你之前等待成交的优先量/顺序。L3 可能更精确地重建，L2 通常只能在撤单位置等假设下估计。

**追问：撤单一定让你前进吗？** 只有撤掉的是你前方优先量才会；L2 往往无法确认，因此应维护乐观/保守边界。

### Q13. 什么是订单簿不平衡度？

**参考答法：** 一种常见 L1 定义是 `(Qbid - Qask)/(Qbid + Qask)`，描述当前最优两侧可见数量差。它受撤单、隐藏量和延迟影响，不保证未来方向。

**追问：Qbid=150、Qask=50？** 不平衡度为 `(150-50)/200 = 0.5`。

### Q14. Microprice 是什么？

**参考答法：** 常见定义是 `(Ask×BidQty + Bid×AskQty)/(BidQty+AskQty)`，用对侧数量把参考值拉向相对稀缺的一边。定义可能不同，应先声明公式；它只是特征，不是真实价值或收益保证。

**追问：为何买量大时更靠近 Ask？** 在该定义下，较大的 BidQty 给 AskPrice 更高权重，表达买侧队列相对更厚的当前状态。

### Q15. 市场冲击、滑点和逆向选择的区别？

**参考答法：** 滑点是参考/预期价与实际执行结果的差；市场冲击关注自身交易对价格和流动性的影响；逆向选择指被动成交后价格很快向不利方向变化。度量都必须声明基准和时间窗口。

**追问：被动成交在 Bid 就一定很好吗？** 不一定，紧接着价格下跌时可能遭遇逆向选择，还要算费用、对冲和库存风险。

### Q16. 连续撮合与集合竞价有什么区别？

**参考答法：** 连续撮合随订单到达持续匹配；集合竞价在指定时点集中用规则确定单一或少数成交价格。订单优先级、可见信息和允许类型可能不同，系统必须处理市场状态。

**追问：为什么不能复用同一策略假设？** 拍卖阶段未必有普通 BBO，撮合时间和分配规则也不同。

## B 组：白板计算题

### Q17. 计算 spread、mid、imbalance 和 microprice

BBO：`99.98 × 120 / 100.02 × 80`。

**参考答案：**

- spread = `0.04`；
- mid = `100.00`；
- imbalance = `(120-80)/200 = 0.20`；
- 按本书定义 microprice = `(100.02×120 + 99.98×80)/200 = 100.004`。

**追问：microprice 大于 mid 能直接买入吗？** 不能。还需数据质量、模型验证、费用、成交概率、风险和合规；单个特征不构成确定结论。

### Q18. 手算逐档成交

卖盘：`10.01×10、10.02×20、10.03×50`。限价 `10.02` 买 25。

**参考答案：** 在 10.01 成交 10，在 10.02 成交 15；均价 `(10×10.01+15×10.02)/25=10.016`。买单填满，10.02 还剩 5，10.03 不变。

**追问：若是 IOC 买 40，限价仍为 10.02？** 共成交 30，剩余 10 取消。

### Q19. 手算 FIFO

同价卖单依次是 A 20、B 15、C 10，主动买单数量 32。

**参考答案：** A 成交 20，B 成交 12，C 不成交；B 剩 3。若 A 在主动单到达前撤了 5，则需根据撤单后 A 的实际剩余重新计算。

**追问：本地接收时间能证明 A 比 B 先吗？** 不能；撮合优先级由交易所接受顺序和规则决定，本地行情到达时间只是观测。

### Q20. 手算理想 Pro-rata

同价订单 A/B/C 为 50/30/20，主动量 37。

**参考答案：** 理想份额为 18.5/11.1/7.4。由于成交单位通常是整数，实际如何舍入并分配余量必须依据场所规则；不能擅自四舍五入后声称是最终撮合。

**追问：为什么拆成多张单可能不提高分配？** 场所可能按参与者聚合、设最低量或使用混合优先级；拆单还可能受消息限制和合规约束。

### Q21. 算风险预占

当前净持仓 70，最大绝对持仓 100；已有未成交买单 20，现在想再买 15。按“所有买单最坏全部成交”检查。

**参考答案：** 最坏多头为 `70+20+15=105`，应拒绝或缩量至最多 10。不能只看当前持仓 70。

**追问：已有买单刚发撤单怎么办？** 撤单确认前仍可能成交，20 的风险占用不能直接释放。

### Q22. 算名义金额并考虑溢出

整数价格单位为 0.01 元，价格整数 1,234,567，数量 800，合约乘数 10。

**参考答案：** 价格为 12,345.67 元；未考虑其他规则的名义金额为 `12,345.67×800×10 = 98,765,360` 元。代码中应先用足够宽整数做 `price_int × qty × multiplier` 的 checked 运算，再按缩放解释，不能先用窄整数溢出。

**追问：为什么不能统一用 f64？** 边界比较、哈希和十进制金额可能出现不可精确表示；还会掩盖缩放单位。展示/分析可转换，核心账本通常用明确整数或十进制定点。

### Q23. 用 Little's Law 估算系统内事件数

系统稳定处理 600k event/s，平均停留 30µs。

**参考答案：** `L = 600,000 × 30×10^-6 = 18`，平均约 18 个事件。它不直接给 p99，也要求系统处于稳定状态。

**追问：队列变长会发生什么？** 事件 age 和延迟上升；对行情而言，处理陈旧事件可能比丢失后受控恢复更危险。

### Q24. 算突发积压

输入峰值 3M/s 持续 250ms，系统处理 2.2M/s。

**参考答案：** 积压 `(3.0M-2.2M)×0.25 = 200,000` 个事件。若每槽 128 bytes，仅队列约 25.6MB；但主要问题是陈旧度，不是内存是否装得下。

**追问：把队列加到一百万是否解决？** 不解决持续容量和延迟 SLO，只延迟故障显现；应提升可持续能力或进入明确安全降级。

### Q25. 10Gbps 上发送 1500 bytes 至少需要多久？

**参考答案：** 只算有效载荷序列化，`1500×8/10^10 = 1.2µs`。真实链路还包含帧开销、传播、交换机、排队和软件。

**追问：为何这对延迟优化重要？** 它给出物理下界，避免把所有时间都归咎于某个函数或语言。

### Q26. 各模块 p99 能否相加？

**参考答案：** 通常不能。各模块最慢 1% 未必是同一批事件。应直接计算端到端样本的 p99，并用相同 trace ID 的阶段时间归因。

**追问：模块预算还有用吗？** 有，用于目标分解、回归门槛和定位，但不能替代端到端分布。

## C 组：订单生命周期与故障场景

### Q27. ACK、Partial Fill、Fill、Cancel ACK 各表示什么？

**参考答法：** ACK 通常表示订单被接受；Partial Fill 表示部分成交且可能有剩余；Fill 表示全部或最终成交；Cancel ACK 表示剩余部分已成功取消。具体字段和消息顺序按协议解释。

**追问：ACK 一定早于 Fill 到达本地吗？** 不可泛化。协议可能合并、重放或在网络中呈现特殊顺序，状态机应按官方会话语义处理。

### Q28. 为什么发出 Cancel 后仍可能 Fill？

**参考答法：** 撤单和对手订单在传播与交易所处理上存在竞态；只要 Cancel 尚未被权威确认，原订单就可能先成交。状态应是 PendingCancel，剩余风险继续预留。

**追问：先收到 Fill 还是 Cancel Reject？** 两者都可能按协议出现；需用订单状态、执行 ID 和会话序列幂等处理。

### Q29. 行情序号从 1002 跳到 1005 怎么办？

**参考答法：** 检测缺少 1003–1004，标记对应频道/订单簿不可信；按风险政策阻止依赖它的新单，申请重传或快照，并把快照与后续增量按序拼接；不变量通过后再回 Live。

**追问：能否继续撤单？** 通常应保留受控撤单/kill 能力，因为它降低风险；具体动作由系统和场所政策决定。

### Q30. 收到重复成交回报怎么办？

**参考答法：** 使用协议保证唯一的 execution ID 与会话语义去重，重复输入不应再次增加累计成交、持仓或费用。去重状态也要能在恢复重放后保持正确。

**追问：能用价格+数量+时间去重吗？** 不可靠，两笔合法成交可能具有相同字段；应优先使用协议唯一标识。

### Q31. 发单后立刻断线，订单是什么状态？

**参考答法：** 若不知道交易所是否收到，应进入 Unknown，而不是猜测 Rejected 或 Working。保留风险，通过会话重放、订单查询和 drop copy/经纪商状态核对。

**追问：多久后可以释放风险？** 不能仅凭本地超时释放，要满足权威确认或预先定义的安全场所语义，并记录/升级仍无法确定的情况。

### Q32. 怎样设计订单状态机？

**参考答法：** 至少有 Local/PendingNew、Working、PartiallyFilled、PendingCancel、Canceled、Filled、Rejected、Unknown；状态由交易所回报驱动，转换验证订单 ID、累计量和会话序列，终态不随意复活。

**追问：为什么不用 `is_active: bool`？** 布尔值表达不了待确认、部分成交、撤单竞态和未知状态，容易错误释放风险或重复发单。

### Q33. 快照与增量如何拼接？

**参考答法：** 在申请/接收快照期间缓存后续增量；读取快照覆盖的最后序号，丢弃已包含的增量，从下一连续序号开始应用，并验证无缺口和订单簿不变量。协议可能提供专门 recovery 语义，必须按规范实现。

**追问：快照到达就立即切换吗？** 不能，只靠快照可能已经落后；要与快照之后的增量连续衔接。

### Q34. 本地持仓与 drop copy 不一致怎么办？

**参考答法：** 先停止扩大相关风险并标记差异，按 execution ID、订单 ID、会话序列和时间窗口逐笔核对；检查重复/漏回报、会话重置、映射和人工交易。以约定权威来源修复并保留审计链。

**追问：能直接把本地数改成外部数吗？** 不应静默覆盖。要记录差异原因、修复事件和风险影响，否则问题会被掩盖且无法审计。

### Q35. 日志队列满了怎么办？

**参考答法：** 区分可采样遥测与必须保留的订单/审计事件。可采样项按策略丢弃并计数；关键事件不能静默丢，达到水位应告警并受控停止新单，保留撤单与 kill 通道。

**追问：异步日志为什么仍影响热路径？** 生产者可能等待队列空间、争用缓存行，或触发分配；需要有界队列、背压语义和性能测量。

### Q36. 进程重启后如何恢复到可交易状态？

**参考答法：** 启动时默认禁用交易；加载版本化配置、快照和日志；恢复行情连续性；重建订单会话并查询/重放场内订单和成交；与 drop copy/经纪商核对持仓与风险；所有不变量和人工/自动门禁通过后才 Live。

**追问：自动重启为什么不够？** 新进程可能不知道旧订单仍在场内或漏了成交，贸然发单会重复风险。

## D 组：低延迟系统与 Rust 场景

### Q37. 延迟和吞吐量有什么区别？

**参考答法：** 延迟是一件事完成所需时间，吞吐量是单位时间完成数量。批处理可提高吞吐却让首条消息等待；容量应定义为满足尾延迟 SLO 下的可持续吞吐。

**追问：平均吞吐低于能力为什么仍会过载？** 到达具有突发性，短时速率可能超过处理能力并形成队列。

### Q38. 怎样定义 tick-to-trade？

**参考答法：** 必须明确起点和终点，比如“NIC 收到触发行情最后一个字节的硬件时间戳，到 NIC 发出对应订单第一个字节的硬件时间戳”，并说明负载、关联规则、百分位和时钟。

**追问：为何“对应订单”难定义？** 决策可能依赖多个事件，一个事件也可能产生零个或多个订单；需要 trace/causality ID 和明确归因规则。

### Q39. 为什么 p99 比平均值重要？

**参考答法：** 平均值会隐藏少量大暂停；尾延迟可能让系统基于陈旧状态行动。应同时报告 p50、p99/p99.9、max、样本数和窗口。

**追问：100 个样本能看 p99.9 吗？** 不能有意义估计，需要足够样本和稳定口径。

### Q40. 无锁一定比锁快吗？

**参考答法：** 不一定。无锁可能有原子竞争、重试、缓存一致性和内存回收成本。若状态天然单写者，事件循环可能更简单、更快且确定；必须按目标硬件和竞争分布测量。

**追问：何时 Mutex 可能足够？** 冷路径、低竞争控制面或正确性优先且不在关键路径时；仍要防止它通过共享资源阻塞热线程。

### Q41. 为什么 HFT 常用单写者？

**参考答法：** 单写者让相关状态按确定顺序更新，减少锁和缓存争用，便于重放。代价是单核容量、热门分片倾斜和跨分片协调。

**追问：如何分片？** 可按行情频道、标的或相关标的组；要考虑负载倾斜、跨标的策略、NUMA 和网关/全局风险瓶颈。

### Q42. Rust 所有权对这类系统有什么帮助？

**参考答法：** 它能在编译期限制悬垂引用和数据竞争，鼓励明确状态所有者；枚举也适合表达订单状态。但语言不会自动保证业务顺序、无分配、无 cache miss 或低尾延迟，仍需设计和测量。

**追问：`Arc<Mutex<_>>` 为什么不是万能方案？** 它保证某些内存安全，却可能产生锁竞争、优先级反转和不清晰的业务所有权。

### Q43. 零拷贝解析有什么风险？

**参考答法：** 借用输入缓冲可减少复制，但视图不能活得比底层包缓冲更久；还要处理字节序、未对齐、长度校验和缓冲复用。不能为零拷贝跳过边界检查。

**追问：什么时候复制反而合理？** 事件很小、需要跨线程/长生命周期，或复制能形成紧凑内部布局并简化所有权时；用实测决定。

### Q44. 怎样避免热路径分配？

**参考答法：** 预分配固定容量队列、对象池、栈上/内联小对象、借用解码和复用编码缓冲。必须定义容量耗尽行为和代际 ID，防止复用旧句柄。

**追问：对象池满了怎么办？** 不应隐式扩容造成延迟尖峰；按业务预案拒绝新工作、降级或触发 kill，同时保留撤单能力和告警。

### Q45. 怎样定位 p99.9 突然恶化？

**参考答法：** 先验证口径和版本，用同一 trace 抽取慢事件，定位 RX、排队、应用或 TX 阶段；关联调度、中断、page fault、cache/NUMA、NIC drop 和日志水位；单变量验证，修复后做峰值与故障回归。

**追问：第一步是不是换内核旁路？** 不是。先用证据找瓶颈，内核旁路带来运维和安全复杂度且未必针对根因。

### Q46. 为什么基准测试会骗人？

**参考答法：** 编译器可能删掉结果，输入过于理想，没测突发/错误路径，机器频率和拓扑不同，负载生成器还有协调遗漏。要固定环境、报告分布、使用生产近似数据并做端到端验证。

**追问：如何避免 coordinated omission？** 按计划到达时间发请求或用能校正遗漏的工具，不让系统变慢时负载生成器也自动少发。

## E 组：风控、合规与生产治理

### Q47. 预交易风控至少检查什么？

**参考答法：** 合约/时段合法性、价格和 tick、单笔数量/金额、成交后持仓与敞口、未结订单、消息速率、自成交防护、账户权限和 kill 状态。拒绝原因要可审计。

**追问：参考行情失效时价格偏离检查怎么办？** 不能默认通过；按政策使用可靠备用参考，或 fail closed/只撤单，并明确数据新鲜度门槛。

### Q48. 为什么风险检查要“预占”？

**参考答法：** 因为订单发出后可能全部成交。先检查后异步更新会产生 TOCTOU，多线程都可能看到剩余额度并同时超限。check-and-reserve 将检查与额度占用作为一个一致动作。

**追问：订单拒绝后呢？** 依据权威 Reject 释放对应预占；部分成交把预占转换为实际持仓和剩余订单占用。

### Q49. Kill switch 应怎样设计？

**参考答法：** 应支持策略、账户、场所和全局层级，动作可包括阻止新单、批量撤单、断开会话；控制链需独立、权限受控、幂等、有审计，并定期演练。触发后要确认场内订单实际状态，而不只修改本地标志。

**追问：主进程挂了还能 kill 吗？** 最好有独立监督/网关或经纪商/场所级控制作为防线，具体取决于架构和规则。

### Q50. 什么是自成交防护？

**参考答法：** 当同一受益主体或配置组的买卖单相遇时，按规则取消新单、旧单或双方，防止非预期自成交。它不能替代账户治理、监控和合规审查。

**追问：为什么只在策略内部检查不够？** 多策略、进程或会话可能共享主体，局部视图看不到其他订单；应在合适聚合层和场所功能共同防护。

### Q51. Spoofing/Layering 为什么与系统设计有关？

**参考答法：** 这类行为通常涉及无真实交易意图、试图误导市场的订单模式，可能违法或违反场所规则。系统需要权限、速率/行为监控、审计和人工治理，开发者不能把可实现的改撤模式当作默认合法。

**追问：高撤单率等于 spoofing 吗？** 不能仅凭单一指标下结论，但它可以触发监控；判断需结合意图、模式、市场影响、规则和合规调查。

### Q52. 为什么规则要做 venue-specific？

**参考答法：** 订单类型、撮合优先级、改单保序、断线撤单、会话恢复和速率限制会因场所/产品改变。应版本化规则配置和协议适配，并用官方样例与认证测试验证。

**追问：怎样防止规则更新造成事故？** 规则版本、双人复核、差异测试、影子回放、分阶段发布和可回滚配置；未确认的新规则 fail closed。

### Q53. 怎样安全发布新的交易版本？

**参考答法：** 可复现构建，历史回放和故障测试，影子只读比较，新旧决策差异分析，小额度 canary，实时对账和明确回滚/场内订单处置。上线闸门同时看正确性、风险和性能。

**追问：回滚是不是换回二进制即可？** 不是，还要处理配置版本、协议会话、仍在场内的订单、状态格式和数据库/日志兼容。

### Q54. 系统是否应该在行情陈旧时自动平仓？

**参考答法：** 没有通用答案。自动动作本身也依赖可靠价格和可用连接，可能扩大风险。应按预先批准的风险政策，在只撤单、对冲、限额缩减、人工介入等选项中选择，并进行场景演练。

**追问：默认安全策略？** 通常先阻止扩大风险并保留受控减险能力，但具体资产和法规环境需要风险/合规共同定义。

## F 组：系统设计综合题

### Q55. 设计一个 L3 订单簿

**回答主线：**

1. 先问协议事件、标的数、活跃订单量和查询模式；
2. 用 Order ID → arena index 的索引定位订单；
3. 每个价格档维护总量与 FIFO 节点链/索引；
4. 买卖价格档分别能找到 best；
5. 按标的/频道单写者，预分配 arena；
6. 序号、订单存在性、数量守恒等不变量；
7. 快照 + 增量恢复，确定性重放；
8. 基准测峰值消息类型和尾延迟。

**追问：为什么不用 `BTreeMap<OrderId, Order>` 解决全部问题？** Order ID 查找和按价格/队列查找是两个索引维度；树节点分配与指针跳转也可能不符合目标访问模式。应按数据分布实测选择。

### Q56. 设计一个低延迟订单网关

**回答主线：** Client ID、会话序号、协议编码、预交易风控、场所限流、订单状态机、回报幂等、Unknown 状态、断线恢复、drop copy 对账、审计、kill switch、端到端时间戳。

**追问：多策略共享网关如何隔离？** 每策略/账户额度与队列、加权/优先调度、禁止一个策略无限占满队列，同时保持全局场所速率和账户风险一致。

### Q57. 设计多场所 Smart Order Router

**回答主线：** 规范化各场所行情但保留来源/时间，构建每场所可用量与费用/延迟状态；订单拆分前做全局风险预占；每个子单独立状态机；处理单边成交、部分失败和路由陈旧；满足适用的最佳执行/订单保护要求并留审计。

**追问：怎样让子单同时到达？** 可估计每条路径延迟并错开发送，但无法保证绝对同时；必须处理先到订单改变市场和另一腿未成交的 leg risk。

### Q58. 设计行情回放系统

**回答主线：** 保存原始包和/或规范化事件、来源与序号；提供确定性时钟；支持原速、加速、单步和故障注入；同一输入得到同一状态哈希；版本化解码器和参考数据；不能引入未来信息。

**追问：回放为什么可能比生产结果好？** 忽略网络缺口、排队、延迟和订单成交模型，或使用未来数据；需要模拟数据可见时间而不只按事件时间排序。

### Q59. 设计全局风险服务

**回答主线：** 定义哪些限额强一致；以账户/组合做状态所有者；本地额度切片或租约降低热路径访问；订单预占、成交转换、拒绝/取消释放；代际和 fencing token 防双主；独立成交回报核对；fail closed 与 kill 通道。

**追问：额度租约节点崩溃后如何回收？** 不能仅凭超时让新旧节点同时使用。需租约期限、代际/fencing、确认旧节点失权，并核对其场内订单与成交后才安全回收。

### Q60. 设计延迟监控系统

**回答主线：** 明确 RX/TX 边界，硬件时间戳 + 内部阶段打点；同一 trace 关联；无分配有界采样缓冲；异步直方图；报告 p50/p99/p99.9/max、样本量和时钟质量；慢 trace 与 CPU/NIC/队列指标关联；防 coordinated omission。

**追问：每条消息都打点会怎样？** 可能改变缓存、分支和内存流量。可做固定低开销字段、硬件支持或采样，并单独测量监控开销和丢样本偏差。

## G 组：行为与事故题

### Q61. “讲一次你解决性能问题的经历”怎么答？

用 STAR，但加入可验证数据：

- **Situation**：业务边界和 p99 指标；
- **Task**：你的责任和不能破坏的正确性约束；
- **Action**：如何打点、建立假设、做单变量实验；
- **Result**：前后分布、峰值负载、回归结果；
- **Reflection**：错误假设、监控或流程改进。

没有 HFT 经历也可以讲数据库、网络服务或嵌入式实时系统，重点是方法可信，不要编造纳秒数字。

### Q62. “速度和正确性冲突时怎么选？”

**参考答法：** 先区分可优化实现和不可破坏的不变量。风控、订单状态和数据连续性不能绕过；我会用所有权、预计算、数据布局等方式降低其成本。若仍不满足 SLO，应调整容量/架构或业务目标，而不是静默放松安全边界。

### Q63. “线上出现未知订单，你怎么处理？”

**参考答法：** 先阻止扩大相关风险并保留最坏风险占用；记录时间线和会话状态；用场所查询、重放和 drop copy 核对；必要时触发 kill/人工升级；修复后补充 Unknown 状态、告警和故障测试，避免只手工改数据。

### Q64. “你不同意交易策略提出的危险优化怎么办？”

**参考答法：** 用具体不变量和数据解释风险，例如撤单未确认仍可成交；提出同目标的安全替代方案和基准；涉及规则/限额时让风险、合规和业务负责人按治理流程决策并留记录。不是用个人意见暗中放行。

## 三套模拟面试卷

### 初级：30 分钟

1. 解释 BBO、spread、mid；
2. 手算 Q18；
3. 区分 IOC/FOK；
4. 画订单生命周期；
5. 行情序号缺口怎么办；
6. 为什么用整数价格；
7. 说出三项预交易风控。

**通过标准：** 核心概念无反向错误，能算对订单簿，知道 ACK 非成交、Cancel 有竞态、数据失步要恢复。

### 中级：60 分钟

1. 解释 L1/L2/L3 和队列估计；
2. 手算 FIFO、Pro-rata 和风险预占；
3. 设计单场所行情到订单系统；
4. 下钻线程模型、尾延迟、Unknown 订单；
5. 给出恢复和测试方案；
6. 解释 kill switch 与合规边界。

**通过标准：** 能主动给假设和权衡，设计不只覆盖正常路径，容量与延迟口径清晰。

### 高级：90 分钟

1. 设计多场所系统与全局风险；
2. 处理跨分片状态和热门标的倾斜；
3. 推演订单连接断开 + drop copy 延迟 + 行情失步同时发生；
4. 给出 fencing、幂等、重放与对账模型；
5. 估算峰值积压和内存流量；
6. 设计发布、故障演练和事故响应。

**通过标准：** 能明确故障模型和安全优先级，知道哪些结论依赖场所规则，并能用测试证明设计。

## 最后十个“绝不能说错”的点

1. Best Bid 是最高买价，Best Ask 是最低卖价；
2. 买单不一定是 Maker，卖单不一定是 Taker；
3. Mid 不保证可成交；
4. 限价是最差价格边界，不是指定成交价；
5. IOC 可部分成交，FOK 通常要求全部立即成交；
6. ACK 不等于 Fill；
7. Cancel 已发送不等于 Canceled；
8. L2 通常不能给精确队列位置；
9. 各模块 p99 不能简单相加成端到端 p99；
10. 任何低延迟优化都不能绕过风控、合规、审计和安全停止能力。
