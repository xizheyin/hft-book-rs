# 智能指针与内存管理 (Smart Pointers)

在 C++ 中，指针就是内存地址，用不好就 Segfault。
在 Rust 中，智能指针（Smart Pointers）不仅包含地址，还包含**元数据（Metadata）**和**所有权语义**。

对于 HFT，我们必须清楚每个智能指针背后的**机器码实现**和**内存开销**。

## 1. `Box<T>`：独占的堆内存

`Box<T>` 是最简单的智能指针。

### 它是做什么的？
默认情况下，Rust 的变量（如 `i32`, 定长数组）都分配在**栈（Stack）**上。栈非常快，但空间有限。
`Box::new(x)` 会做两件事：
1.  调用内存分配器（如 `malloc`），在**堆（Heap）**上申请一块内存。
2.  把 `x` 的数据从栈拷贝到堆上。
3.  返回一个指向堆内存的指针（这个指针本身在栈上）。

### 形象比喻
*   **栈（Stack）**：你的**随身背包**。存取极快，伸手就来，但装不了太大东西，而且函数返回（离开房间）时必须清空。
*   **堆（Heap）**：你的**仓库**。空间无限大，但存取麻烦（要填单子申请空间），而且离你远。

### HFT 为什么讨厌 `Box`？
在核心交易路径上，我们**极其痛恨** `Box::new`：
1.  **慢**：`malloc` 需要搜索空闲内存块，可能需要加锁，甚至触发系统调用。这可能耗时 10ns 到 1000ns 不等。对于 HFT，这太久了。
2.  **碎片化**：堆上的数据是散乱的。CPU 喜欢顺序读取（预取），乱序读取会导致 Cache Miss。

**对策**：系统启动时把仓库（堆）填满（预分配），交易时只用背包（栈）或预分配好的内存池。

## 2. `Arc<T>`：共享的原子引用

`Arc` = **A**tomic **R**eference **C**ounted（原子引用计数）。

### 它是做什么的？
有时候，多个人（线程）需要同时看同一份数据。Rust 的所有权规则不允许两个人都“拥有”它。
`Arc` 引入了一个**计数器**。
*   `Arc::clone(&ptr)`：计数器 +1。
*   `ptr` 被销毁（Drop）：计数器 -1。
*   计数器归零：真正释放数据（关灯走人）。

### HFT 为什么讨厌 `Arc`？
既然是多线程共享，为了防止两个线程同时修改计数器导致数据错乱，这个“+1/-1”的操作必须是**原子（Atomic）**的。
在 x86 CPU 上，这对应 `LOCK XADD` 指令。

这会导致：
1.  **锁总线**：CPU 必须协调所有核心，确保它们看到的计数器是一致的。
2.  **缓存行争用**：如果核心 A 和核心 B 频繁 clone/drop 同一个 `Arc`，这块内存对应的缓存行会在两个核心之间来回“乒乓”，导致巨大的延迟。

**对策**：尽量让每个线程有自己的数据副本（Share Nothing 架构），不要共享。

## 3. `Cow<'a, B>`：聪明的“变色龙”

我们在生命周期一章提到了 `Cow` (Clone-on-Write)。它是一个枚举，可以是 `Borrowed`（引用），也可以是 `Owned`（拥有）。

### 形象比喻
*   **Borrowed**：借阅图书馆的书。你只能看，不能改。
*   **Owned**：把书复印一份带回家。你可以随便涂改。
*   **Cow**：你先借书看。如果你发现需要做笔记，**在那一瞬间**，你去复印机复印一份，然后开始涂改。如果你只看不改，那就永远不用复印。

### HFT 实战
解析 FIX 协议的消息类型 `MsgType`。
*   绝大多数情况是标准的单字符（如 'D' 代表 NewOrderSingle）。我们直接引用 buffer。
*   极少数情况是自定义的特殊类型。我们需要分配内存来存储。

`Cow` 让我们在 99% 的情况下享受引用的零开销，同时兼容那 1% 的特殊情况。

## 4. 进阶：自定义内存分配 (Allocator API)

我们之前说过“HFT 痛恨 `Box`”，主要是痛恨默认的 `malloc`。如果你能控制内存从哪里分配，`Box` 也可以很快。

Rust 的 `Allocator` API（目前还在 nightly）允许我们为智能指针指定分配器。

### 场景：Arena Allocation

在处理行情快照时，我们可能需要构建复杂的树状结构（如 L3 OrderBook）。如果每个节点都用默认的 `Box::new`，会有大量的小内存分配，导致碎片化。

使用 Arena（区域）分配器，我们可以一次性申请一大块内存（如 1MB），然后像切蛋糕一样把小块分给对象。

```rust
// 需要在 Cargo.toml 中添加 bumpalo
// use bumpalo::Bump; 

struct Order { id: u64, price: f64 }

fn process_market_data() {
    // 1. 创建一个 Arena，预分配 1MB 内存
    // let arena = Bump::with_capacity(1024 * 1024);
    
    // 2. 在 Arena 上分配对象
    // 这几乎是零开销的（只是移动一个指针）
    // let order = arena.alloc(Order { id: 1, price: 100.0 });
    
    // 3. 甚至可以创建在 Arena 上的 Vec (需要开启 bumpalo 的 collections feature)
    // let mut orders = bumpalo::collections::Vec::new_in(&arena);
    // orders.push(order);
    
    // 4. 函数结束，arena 销毁，所有内存一次性释放！
    // 没有任何碎片，没有多次 free 的开销。
}
```

### HFT 结论

如果你必须使用动态数据结构（`Vec`, `HashMap`, `Box`），**请务必考虑使用 Arena Allocator**。它能将内存分配的开销从 ~20ns (malloc) 降低到 ~1ns (pointer bump)，并且极大地提高了缓存局部性。

## 5. 总结

*   **Box**：把数据放进仓库（堆）。HFT 启动时可以用，盘中交易严禁使用。
*   **Arc**：多线程共享数据。原子操作很贵，尽量别用。
*   **Cow**：能借就不买，要改才复印。HFT 处理动态数据的神器。
