# Send 与 Sync 的本质 (Send & Sync)

如果说“内部可变性”是面试的必考题，那么 `Send` 和 `Sync` 就是面试的**送命题**。

它们是 Rust 并发安全的灵魂。理解它们，你就能理解为什么 Rust 敢说自己是“无畏并发 (Fearless Concurrency)”。

## 1. 定义：一句话解释

这两个都是 `unsafe auto trait`（编译器自动实现的标记 Trait），它们没有任何方法。

*   **`Send`**：表示一个类型的所有权可以在线程间**转移 (Transfer)**。
    *   潜台词：“你可以把它 move 到另一个线程去。”
*   **`Sync`**：表示一个类型可以在线程间**共享 (Share)**。
    *   潜台词：“多个线程可以同时持有它的引用 (`&T`)。”

**核心公式**（必须背诵）：
> **如果 `&T` 是 `Send` 的，那么 `T` 就是 `Sync` 的。**

## 2. 为什么需要它们？

### 2.1 那些 `!Send` 的家伙
绝大多数类型都是 `Send` 的（`i32`, `String`, `Vec`）。那么，谁不是 `Send`？

**典型代表：`Rc<T>` (Reference Counted)**
`Rc` 的引用计数是非原子的（普通的 `add` 指令）。
如果我们将一个 `Rc` 移动到线程 A，又把它的克隆移动到线程 B：
1.  线程 A 执行 `rc.clone()` -> 计数器 +1。
2.  线程 B 执行 `rc.clone()` -> 计数器 +1。
3.  因为没有原子锁，两个 `+1` 可能会发生数据竞争，导致结果只加了 1。
4.  最终导致内存被提前释放（Use After Free）或双重释放（Double Free）。

所以，`Rc<T>` 是 `!Send`。编译器会禁止你把它传给 `thread::spawn`。

### 2.2 那些 `!Sync` 的家伙
谁不能在线程间共享引用？

**典型代表：`Cell<T>` / `RefCell<T>`**
它们提供了内部可变性，但没有锁。
如果线程 A 拿到 `&Cell<i32>`，线程 B 也拿到 `&Cell<i32>`：
1.  A 写：`cell.set(1)`。
2.  B 写：`cell.set(2)`。
3.  数据竞争！结果不可预测。

所以，`Cell<T>` 是 `!Sync`。编译器会禁止你把 `&Cell<T>` 跨线程共享（比如放入 `Arc` 中）。

## 3. 核心数据结构底层原理大汇总

要理解这些结构的底层原理，你只需要盯住两样东西：**引用计数**（如何活下去）和 **内部可变性**（如何改数据）。

| 数据结构 | 底层原理 | 为什么不是 Send？ | 为什么不是 Sync？ |
| :--- | :--- | :--- | :--- |
| **`Rc<T>`** | 堆上的数据 + **普通整数**计数器 | ❌ **引用计数非原子**。移动一个克隆体到新线程，会导致两个线程并发修改同一个普通整数计数器。 | ❌ 同理。多个线程通过引用同时修改计数器，计数器会乱。 |
| **`Arc<T>`** | 堆上的数据 + **原子整数**计数器 | ✅ 它是 `Send`。原子整数 (Atomic) 保证了多线程增减计数器时是排队的。 | ✅ 它是 `Sync`。原子操作保证了并发访问计数的安全性。 |
| **`Cell<T>`** | 内存里的值。通过 `unsafe` 强行把 `&T` 转成 `*mut T` | ✅ 它是 `Send`。把整个盒子搬走是安全的，只要 `T` 能搬。 | ❌ **没有锁**。多个线程通过 `&Cell` 同时 `set()`，数据会写花。 |
| **`RefCell<T>`** | 数据 + **普通整数**借用标志位 (0:无, 1:读, -1:写) | ✅ 它是 `Send`。搬走整个盒子没问题。 | ❌ **标志位不是原子的**。两个线程可能同时读到“无人借用”，然后**同时拿到可变引用**。 |
| **`Mutex<T>`** | 数据 + 操作系统的锁/信号量 | ✅ 它是 `Send` (前提 `T: Send`)。 | ✅ 它是 `Sync` (前提 `T: Send`)。**因为有锁！**想改数据必须先拿锁，锁保证了同一时间只有一个人能动它。 |

## 4. 深度总结：为什么是（或不是） Send 和 Sync？

### 4.1 为什么 `Rc` 连 `Send` 都不给？（最容易困惑点）
你会想：“我把 `Rc` 移动走，原线程不就没了吗？为什么会有竞争？”
*   **真相**：`Rc` 可以被 `clone()`。如果你手里有两个 `Rc` 指向同一个地方，你把其中一个 `move` 到新线程，**两个线程就实际上共享了同一个底层计数器**。
*   **后果**：普通整数计数器在多线程下增加/减少会产生“竞态条件”，导致内存被提前释放或永不释放。
*   **结论**：只要底层计数器不是原子的，就绝对严禁跨线程。

### 4.2 为什么 `RefCell` 允许 `Send` 但拒绝 `Sync`？
*   **允许 `Send`**：你把一个 `RefCell` 整体卖给了线程 B，线程 A 以后再也不碰它了。这时候，内部那个借用标志位依然只会被线程 B 一个人看。它是安全的。
*   **拒绝 `Sync`**：如果你把 `&RefCell` 分给两个线程，它们会同时调用 `.borrow_mut()`。因为内部标志位是普通整数，两个线程可能同时判断成功，从而违背了“唯一可变引用”的铁律，导致崩溃。

### 4.3 为什么 `Mutex<T>` 必须要求 `T: Send` 才能是 `Sync`？
这是最绕的。`Mutex` 已经有锁了，为什么还要看 `T` 的脸色？
*   **真相**：当你通过 `&Mutex` 拿到锁时，你实际上在当前线程拿到了 `T` 的所有权（访问权）。你可以用 `std::mem::replace` 把里面的 `T` 换出来，拿走。
*   **逻辑**：如果你在线程 A 关上门写东西，过一会你在线程 B 打开门接着写（甚至把东西拿走）。这在逻辑上等同于把 `T` 从线程 A **发送**到了线程 B。
*   **结论**：如果 `T` 本身不能安全地 `Send`（比如 `T` 是个只能在主线程跑的 GUI 句柄），那么 `Mutex` 也就不能让你跨线程共享。

## 5. 决策图（保命指南）

```mermaid
graph TD
    A[我要在多线程共享同一个东西吗？]
    A -- 是 --> B{我要在多线程还要修改这个东西吗？}
    A -- 否 --> E[单线程环境]
    
    B -- 要 --> C[Arc<Mutex<T>> 或 Arc<RwLock<T>>]
    B -- 不要 --> D[直接 Arc<T> (只要 T 是 Sync)]
    
    E --> F{想绕过借用检查改数据？}
    F -- 小数字/布尔值 --> G[Cell]
    F -- 复杂对象 (String, Vec) --> H[RefCell]
```

**口诀**：
*   **多线程共享** -> 外层必须套 `Arc`。
*   **多线程修改** -> `Arc` 里面再套个 `Mutex`。
*   **单线程修改** -> `Cell` (简单值) 或 `RefCell` (复杂值)。

理解了底层这个“原子计数器”和“锁”的区别，Rust 的并发报错就再也唬不住你了。
