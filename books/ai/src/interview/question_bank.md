# AI Agent Infra 面试题库：80 题带答题要点

题库不是背诵比赛。正确用法是：先遮住答案，在 30 秒内给结论；再用 2 分钟讲机制、取舍和验证；最后让同伴从答案里的任何名词继续追问。若只能复述本页文字，却不能画图、举例或说明限制，就还没有真正掌握。

时间权重按岗位主次分配：核心系统 60%，Agent 20%，简历 20%。题库保留恰好 80 题，其中超过 25 题直接覆盖 OS、文件写入、虚拟化、存储、网络、控制面、HA、容量与事故响应；LLM 知识只保留理解 Agent 负载所需的部分。

> 个性化事实边界：某量化机构保持匿名；Reaper 是 OOPSLA 2026 Revision；SkillFuzz 与 Rust 生态漏洞传播工作是 ICSE 2027 Under Review。凡简历没有给出的团队规模、模型、硬件、SLA 或失败案例，答案只提供准备骨架，不替候选人虚构经历。

## 1. 30 秒答法：通用模板

面对技术题，可以先说：

> 我先给定义和结论，再说明它解决的失败模式。系统上我会画出状态与信任边界，给出一个主要方案和一个备选方案；最后用指标、测试或 verifier 说明怎样证明，并补充适用限制。

面对经历题，可以先说：

> 当时的约束是……，我负责……。我先定义了……不变量，再做了……，通过……验证。结果是……。这个结论只覆盖……，如果重做我会……。

## 2. 基础题：先把共同语言讲清楚

### 1. LLM 和 Agent 有什么区别？

答题要点：

- LLM 主要根据上下文生成下一个 token；Agent 是围绕模型增加状态、工具、环境反馈、停止条件和验证的执行系统。
- 模型回答错误是模型风险；Agent 还会产生文件、网络、权限和外部副作用，因此系统边界比聊天场景更重要。

### 2. 什么是 Agent Infra？

答题要点：

- 它是让 Agent 可运行的基础设施，包括任务 API、调度、模型路由、工具协议、沙箱、状态存储、观测、评测和审批。
- 高分回答要强调“模型提出意图，确定性系统控制权限和结果”，而不是只列框架名称。

### 3. 为什么模型能力强，不代表 Agent 系统可靠？

答题要点：

- 模型输出具有概率性，也可能受不可信上下文影响；工具、网络和外部服务还会独立失败。
- 可靠性来自权限边界、幂等、重试、状态机、verifier、回放和人工门禁，不能只靠更长 Prompt。

### 4. 从 `write()` 到数据真正落盘经过哪些层？

答题要点：

- 普通 buffered write 从用户缓冲区进入系统调用，经 VFS、具体文件系统和页缓存成为脏页，再由 writeback、块层、驱动和设备队列写向介质。
- `write` 还可能短写；即使返回完整长度，也通常只表示内核接受了数据，不等于掉电安全。还要根据恢复语义讨论 `fdatasync`、`fsync`、目录同步和远端副本确认。

### 5. `write`、`fsync`、原子可见和持久化有什么区别？

答题要点：

- `write` 成功、其他进程可见、更新原子和崩溃后仍存在是不同承诺；不能用一个“写成功”概括。
- 常见原子替换协议是写临时文件、同步文件、同文件系统 `rename`，再同步父目录；具体保证仍取决于文件系统和设备语义。

### 6. 页缓存何时提高性能，何时造成长尾？

答题要点：

- 命中页缓存可避免设备 I/O、合并小写，但脏页积累到阈值会触发集中 writeback 或写入节流，造成 p99 尖刺。
- 排查要同时观察 dirty/writeback、缺页、I/O 队列、设备延迟和内存压力；不能只看应用层耗时。

### 7. 容器、用户态内核与 VM 的隔离边界有何不同？

答题要点：

- 普通容器共享宿主内核；用户态内核重实现或代理大量系统接口；VM 使用 guest kernel 和 VMM/硬件虚拟化形成更强内核边界。
- 选择要共同考虑攻击面、兼容性、异构 OS、启动、密度、I/O/网络开销和运维，而不是简单排序“谁更安全”。

### 8. namespace、cgroup、capability、seccomp 各解决什么？

答题要点：

- namespace 隔离进程可见视图；cgroup 计量和限制资源；capability 拆分 root 权力；seccomp 过滤系统调用。
- 它们互补但都不是完整沙箱，还需文件、网络、LSM、身份、更新和宿主安全边界。

### 9. 什么是结构化工具调用？

答题要点：

- 模型输出工具名和符合 schema 的参数，执行器校验后调用真实工具，再把结果作为新观察返回。
- 结构化不等于安全；仍需鉴权、路径和网络控制、超时、输出限制及副作用审批。

### 10. 为什么工具参数要用 schema 校验？

答题要点：

- schema 能拒绝缺字段、类型错误、超范围值，并让版本演进和错误返回更清晰。
- schema 只验证“形状”，不能判断调用者是否有权限或业务语义是否合理，必须叠加策略检查。

### 11. 什么是幂等？

答题要点：

- 同一个逻辑请求执行一次或重复执行，最终可观察结果相同。例如客户端超时重试创建任务时，不应生成两个任务。
- 常用方法是稳定 idempotency key、唯一约束、状态检查和外部动作收据；并非所有副作用都天然可幂等。

### 12. 重试为什么可能让故障更严重？

答题要点：

- 大量客户端同步重试会放大流量；非幂等动作还可能重复扣费、发布或写入。
- 应分类错误，使用指数退避、随机抖动、重试预算和熔断；结果未知的外部写操作优先对账。

### 13. Agent 为什么需要状态机？

答题要点：

- 状态机明确 queued、running、waiting approval、verifying、cancelled 等合法迁移，避免多个 worker 对同一任务做矛盾动作。
- 每次迁移应带版本检查和事件记录，使暂停、恢复、取消和审计可实现。

### 14. checkpoint 应保存什么？

答题要点：

- 保存仓库基础快照与 diff、已完成 step、预算、结构化 Agent 状态、策略/模型/工具版本和外部动作收据。
- 不应只保存自由文本对话；也不应把秘密和无限增长的完整 stdout 全塞进热状态库。

### 15. 容器就是安全沙箱吗？

答题要点：

- 容器提供进程、文件和资源隔离能力，但通常共享宿主内核，默认配置不等于适合执行恶意代码。
- 还需非 root、只读基础层、cgroup、seccomp、网络默认拒绝、秘密代理和必要时更强的 microVM 隔离。

### 16. 什么是 prompt injection？

答题要点：

- 不可信文档、代码或工具输出包含诱导模型忽略原目标、泄露数据或执行越权动作的内容。
- 不能只靠 Prompt 防守；仓库文本不能修改权限，所有工具调用必须在模型外重新鉴权。

### 17. 最小权限原则如何用于 Agent？

答题要点：

- 每个任务只获得完成目标所需的工具、文件、网络、秘密和时间范围，能力令牌绑定 job 与动作。
- 读写权限分开，高风险外部写需要审批；任务结束立即撤销临时能力。

### 18. 控制面与数据面为什么要分开？

答题要点：

- 控制面管理期望状态、策略、调度、租约和版本；数据面真正启动沙箱、挂卷、转发网络和执行工具。
- 控制面短暂失联时，数据面只能在未过期策略和租约内工作；撤销、fencing 和重建收敛语义必须明确。

### 19. 为什么 trace 比普通日志更适合长程 Agent？

答题要点：

- trace 用 job、attempt、step 串起模型、工具、文件和 verifier 的因果关系，能定位第一个分叉点。
- 普通文本日志仍有价值，但缺少结构和上下文传播；两者都要脱敏、限长并设置保留期。

### 20. microVM 快照恢复时必须重置哪些状态？

答题要点：

- 实例身份、机器 ID、随机数状态、网络地址、短期凭证和租户数据不能原样复制；内存与磁盘必须来自一致点。
- 基础镜像升级要使旧快照失效；恢复失败需要有界退回冷启动，并防止批量失败形成风暴。

### 21. 临时块设备、共享卷和对象存储怎样分工？

答题要点：

- 临时块设备适合每个 run 的兼容工作区；共享卷提供跨实例文件语义；对象存储适合不可变制品、日志和 checkpoint。
- 共享卷先定义可见性、锁、`rename`、缓存和分区语义；不能因为“大家都要文件”就把所有数据放进一个 POSIX 卷。

### 22. `strace`、`perf`、火焰图和 I/O 指标分别回答什么？

答题要点：

- `strace` 看系统调用、返回值和阻塞位置；`perf`/火焰图看 CPU 样本、热点和调用栈；I/O 指标看队列、延迟、吞吐、IOPS 和饱和。
- 工具会有观测开销和盲区，应先用低开销指标缩小范围，再做受控深挖，并固定负载与版本复现。

### 23. 存储租约为什么还需要 fencing token？

答题要点：

- 租约只表达“控制面认为谁当前拥有资源”；失联旧节点可能稍后恢复并继续写。
- 数据面必须比较单调递增 epoch/fencing token，永久拒绝旧 epoch，才能阻止两个 writer 同时认为自己合法。

### 24. veth、tap、underlay 和 overlay 分别处在哪一层？

答题要点：

- veth 常连接容器 network namespace 与宿主；tap 常把 VM 虚拟网卡接入宿主；underlay 是物理路由网络，overlay 在其上封装租户网络。
- overlay 带来 MTU、隧道状态和排障成本；网络隔离还需工作负载身份、策略、DNS 与受控 egress。

## 3. 深入追问：把简历与 Agent Infra 连起来

### 25. 请解释 HFT 迁移中的关键数据路径。

答题要点：

- 从 Parser、Normalizer/Orderbook、Feature/Model 到 Alpha 依次说明输入、状态和输出，强调逐事件因果顺序。
- 画出每个组件的所有者和验证点；策略细节保持匿名，不用“保密”回避通用机制。

### 26. Rust/C++ 双实现怎样做逐事件差分？

答题要点：

- 固定输入、配置和初始状态，为每个事件建立稳定身份，在多个组件边界记录可比较状态。
- 先找第一个分叉事件，再检查浮点规则、顺序、时间戳和隐藏状态；只比较最终输出会丢失定位信息。

### 27. 为什么事件顺序是语义的一部分？

答题要点：

- 订单簿和特征是有状态计算，相同事件集合换一个顺序可能得到不同结果。
- 需要定义同时间戳排序、重复、缺失和乱序处理，并让 replay 与线上路径共享这些规则。

### 28. 浮点输出不完全相等时怎么办？

答题要点：

- 先判断业务要求是位级一致还是允许绝对/相对误差；不要随意设置宽容阈值掩盖逻辑错误。
- 记录第一个误差来源，控制编译优化、运算顺序和硬件差异，并对误差累积做边界分析。

### 29. 能否由简历数字证明 Rust 比 C++ 快？

答题要点：

- 不能。简历只能证明在覆盖样本的特定离线 replay 中，迁移后 p50/p99 改善 10%-20%。
- 必须补充硬件、编译参数、数据、预热和 profile，才能判断收益来自实现、数据布局还是其他变化。

### 30. 为什么严格控制 `unsafe` 和 `RefCell`？

答题要点：

- 两者会把一部分别名、线程或运行时借用不变量交给开发者维护，扩大审计责任。
- 它们仍可在小而明确的边界使用；需要说明不变量、测试、基准和安全封装，而不是一律禁止。

### 31. Coding Agent 迁移中，人和 Agent 怎样分工？

答题要点：

- 简历明确：人负责架构、业务语义、风险判断和最终审计；Agent 在受约束 harness 中做代码理解、迁移、测试等任务。
- 面试要补一个门禁拒绝错误输出的实例，并准确区分团队累计产出与个人责任。

### 32. HIR 与 MIR 有何区别？

答题要点：

- HIR 是 AST 经宏展开、名称解析和降糖后的高层中间表示；类型检查作用于 HIR，完整的 typed 表示可在 THIR 中看到，之后再构建控制流更明确的 MIR。
- MIR 更适合数据流、借用、优化和静态分析，但具体版本细节应以对应 rustc 源码为准。

### 33. rustc 诊断共享状态污染怎样治理？

答题要点：

- 简历事实是重构主诊断与子诊断参数生命周期，自动完成快照、翻译、清理和恢复，并加入同名异值不变量检查。
- 回答时需补真实复现和异常路径，说明为什么顺序正确以及测试怎样阻止回归。

### 34. UB 前置条件检查为什么做成可选？

答题要点：

- 检查能更早暴露违反 unsafe 契约的问题，但可能增加运行或编译成本，也不能覆盖所有 UB。
- 简历证据包括 Vec/String 路径的 run-fail 测试和 rustc-perf；具体开销只按实际记录回答。

### 35. host、target 和 toolchain 有什么区别？

答题要点：

- host 是编译工具运行的平台，target 是生成程序面向的平台，toolchain 包含对应编译器、标准库和相关工具。
- 交叉编译中 host 与 target 不同；构建通过也不等于目标机运行验证完成。

### 36. 为什么把 Buck2 RISC-V 支持拆成 3 个 PR？

答题要点：

- 简历给出的范围跨主机识别、平台约束、target/toolchain、发布矩阵和 artifact 映射，按依赖拆分能降低评审与回滚风险。
- 要能画出实际依赖顺序，并说明每一步在 RISC-V Debian 上验证到什么程度。

### 37. 块存储、文件存储和对象存储应怎样选择？

答题要点：

- 块存储提供原始块和文件系统自由度；文件存储提供目录/锁/共享语义；对象存储按 key 管不可变或大对象，通常不提供完整 POSIX 语义。
- 选择取决于小文件元数据、共享写、一致性、快照、恢复、成本和生命周期；Agent 工作层与持久制品往往需要不同介质。

### 38. Kafka 的“至少一次”对消费者意味着什么？

答题要点：

- 消息可能重复，消费者必须用事件 id、唯一约束或版本检查做到幂等。
- 数据库写入与 offset 提交之间会有故障窗口；要说明提交顺序、重放和对账，不轻率声称端到端 exactly-once。

### 39. 小包能通、大文件卡住，你怎样排查虚拟网络？

答题要点：

- 先按节点、路径和包大小对比，检查端到端 MTU、隧道封装、PMTU/ICMP、分片、重传和策略拒绝。
- 若只在新节点发生，检查 underlay MTU 与数据面配置；同时防客户端重试把出口和 conntrack 进一步打满。

### 40. 什么是抽象解释？

答题要点：

- 它不枚举所有具体运行状态，而是在抽象域中保守地传播可能状态，通过 join 和 fixpoint 处理分支与循环；抽象域不必有限，收敛可依赖有限高度或 widening/narrowing。
- 抽象越粗越可扩展，但误报可能更多；要用已知缺陷和真实扫描评估召回、精确率和性能。

### 41. 怎样面对 Reaper 51.6% 的告警级精确率？

答题要点：

- 不回避：约一半告警不是评测定义下的真实缺陷，使用成本取决于告警数量、排序和人工审查时间。
- 同时给出召回和真实生态结果，再分析误报类别与适用场景；论文状态只能说 Revision。

### 42. SkillFuzz 为什么做有/无 Skill 配对？

答题要点：

- 同一任务比较使用 Skill 与不使用 Skill 的运行，有助于判断错误是否由 Skill 诱发，而非任务天然困难。
- 配对不能自动消除模型随机性、oracle 错误或样本偏差，还需准入、重复试验和轨迹审查。

### 43. verifier 自己错了怎么办？

答题要点：

- 用参考解先验证任务和 verifier 能得到预期结果，对 verifier 做单元、边界和变异测试。
- 对不稳定或无唯一答案任务标为不确定并拒绝自动归因；必要时双人审查或使用多个独立证据。

### 44. 包依赖可达与函数调用可达有何区别？

答题要点：

- 包进入依赖图只说明代码可能存在；函数级调用路径更接近实际触达，但仍不等于输入可控或漏洞可利用。
- feature、默认配置、泛型单态化和动态分派会改变可达性，结论必须绑定构建配置。

## 4. 故障题：看你能否安全收场

### 45. 沙箱文件 I/O 的 p99 突然升高，你怎样跨层定位？

答题要点：

- 先拆应用 syscall、页缓存/dirty、文件系统锁、块层队列、设备和远端副本延迟，再按节点、租户、文件大小和时间窗口对比。
- 检查日志洪水、inode/配额、集中 writeback、GC、慢盘和重试放大；止血应限流和隔离，不只增大超时。

### 46. 节点心跳丢失后，为什么不能立即重调度全部沙箱？

答题要点：

- 网络抖动可能让旧节点仍在执行；立即批量重调度会造成双写、镜像/存储风暴和级联过载。
- 先隔离故障域、停止旧 epoch 提交，用租约与 fencing 确认所有权，再按受控速率恢复，并保留人工熔断开关。

### 47. shell 命令超时但子进程仍在运行怎么办？

答题要点：

- 在独立进程组或沙箱内执行，超时先停止接受后续动作，再终止整个进程树并回收资源。
- 使用 cgroup 限制 fork、CPU 和内存；仅杀父进程可能留下孤儿进程。

### 48. worker 执行一半崩溃，怎样恢复？

答题要点：

- worker 依靠带过期时间和单调 fencing epoch 的租约成为单写者；租约过期后，新 worker 用更高 epoch 从已提交检查点创建新 attempt，数据面永久拒绝旧 epoch。
- attempt/step id 用于追踪，外部副作用使用跨 attempt 稳定的 `logical_effect_id` 幂等或对账；否则恢复会生成新 key 并重复动作。

### 49. 队列重复投递同一任务怎么办？

答题要点：

- 接受至少一次投递，用 event id、job version、当前有效租约与 fencing epoch、唯一约束拒绝重复推进。
- 重复投递是正常情形，不应依赖“消息绝不会重复”的假设。

### 50. 状态数据库不可用时，运行中沙箱要继续吗？

答题要点：

- 只有仍持有未过期本地租约的低风险纯计算才能在有界窗口内继续；不得产生外部可见提交、获取新权限或越过本地 deadline。
- 租约到期或无法续租立即停止；控制面停止调度新任务并告警，恢复后按 event id 与 fencing epoch 对账。

### 51. 检查点引用的对象损坏怎么办？

答题要点：

- 内容寻址和校验和能在读取时发现损坏，元数据只有在对象持久化成功后才指向它。
- 尝试上一检查点或重新执行可幂等 step；若证据不足，标记失败而非悄悄跳过。

### 52. 测试偶尔通过、偶尔失败，verifier 怎么判？

答题要点：

- 将其标为 flaky 或 inconclusive，不应一次通过就自动放行；固定依赖、随机种子、时间和并发条件。
- 记录多次结果与失败分布，将修复 flake 与修复目标 bug 分开。

### 53. 外部 API 超时，不知道写操作是否成功，能直接重试吗？

答题要点：

- 不能盲目重试。先使用稳定幂等键查询结果或读取动作收据，对账后再决定。
- 若对端不支持幂等与查询，高风险写应禁用自动化或要求人工处理与补偿流程。

### 54. 仓库 README 命令 Agent 上传凭证，怎样阻止？

答题要点：

- README 是不可信数据，不能改变工具策略；网络默认拒绝，秘密不进入沙箱或提示。
- Tool Proxy 对每次调用重新鉴权，外发目标受 allowlist 和数据限制，策略拒绝写入审计。

### 55. 日志中发现秘密泄漏怎么办？

答题要点：

- 立即撤销和轮换凭证，限制日志访问并确认传播范围；保留受控审计证据。
- 长期修复是让秘密通过代理使用而非暴露给不可信进程，脱敏只能作为第二道防线。

### 56. 发现可能的沙箱逃逸怎么办？

答题要点：

- 隔离受影响宿主与租户，停止相关 worker 池，保留取证并轮换宿主可接触的能力。
- 修补镜像/内核后分阶段恢复；用更强隔离、最小宿主权限和小爆炸半径降低影响。

### 57. 取消请求与“任务成功”同时发生，状态如何决定？

答题要点：

- 用状态版本和 compare-and-swap 定义合法竞争结果；终态不可被另一条迟到事件覆盖。
- 产品语义要提前决定：若 verifier 已原子提交成功，取消返回终态；否则先递增 cancellation epoch，让排队和在途的旧能力失效，再终止进程、清理资源并进入 `CANCELLED`。

### 58. Agent 的摘要漏掉关键约束，后续动作跑偏怎么办？

答题要点：

- 关键约束、审批、预算和未完成副作用必须存结构化状态，不能只靠自由文本摘要。
- trace 保留来源引用，发现分叉后可回放；摘要器本身也要版本化和回归评测。

## 5. 容量与性能题：会算，才会做取舍

### 59. 怎样估算同时需要多少沙箱？

答题要点：

- 先估高峰到达率和平均任务占用时间，用并发约等于到达率乘停留时间得到一阶结果。
- 再按任务类型、长尾、重试、预热池和资源画像校正，不能只报一个平均数。

### 60. 怎样估算模型网关峰值？

答题要点：

- 高峰任务/秒乘每任务平均模型调用数得到请求率，再分模型、输入长度和输出长度统计 token 速率。
- 请求数相同但长上下文成本可差很多；还要考虑 cache hit、fallback 和重试放大。

### 61. Agent 成本为什么容易失控？

答题要点：

- 多轮把历史与仓库重复送入模型，循环和失败重试又会放大 token、沙箱时间与日志量。
- 使用总预算、step 上限、按需上下文、前缀缓存、模型路由和每成功任务成本指标。

### 62. 怎样设计轨迹存储？

答题要点：

- 热层保存结构化事件和索引，大 stdout、模型内容和文件转对象存储；用 cursor 流式读取。
- 设置按敏感度和用途的保留期、压缩与删除策略，审计数据和 debug 数据分开。

### 63. 怎样降低沙箱冷启动？

答题要点：

- 维护按镜像/资源类型的小规模预热池，复用只读基础镜像、仓库对象和依赖缓存。
- 不复用租户可写层或秘密；预热过多会浪费资源，需根据到达分布动态调整。

### 64. 多租户怎样公平调度？

答题要点：

- 使用租户级加权公平队列和并发、token、CPU、存储多维配额，防止大任务独占。
- 预留系统和交互任务容量，长期任务可抢占到检查点，但必须保证副作用安全。

### 65. 什么叫背压？

答题要点：

- 下游变慢时，上游减少生产或排队，而不是无限堆积和重试；它是把资源真实能力反馈给调用者。
- 可通过队列上限、并发令牌、预计等待、429/重试时间和 admission control 实现。

### 66. 哪些内容可以缓存？

答题要点：

- 不可变仓库对象、依赖包、镜像层、确定性只读工具结果和稳定模型前缀可以按哈希缓存。
- 带权限、时效或外部状态的结果要把租户、版本和策略纳入 key；错误缓存可能泄密或返回过期事实。

### 67. 队列如何分片？

答题要点：

- 可按资源类型建立池，再在池内按租户或 job hash 分片；同一 job 的状态事件需保持可解释顺序。
- 热租户会造成热点，必须结合虚拟分片、配额和 work stealing，而不是只选一个字段固定分片。

### 68. SLO、RTO 和 RPO 分别约束什么？

答题要点：

- SLO 描述正常服务目标；RTO 约束故障后多久恢复；RPO 约束最多允许丢失多少已提交状态或数据。
- Agent 平台应分开控制面可用性、排队、取消、平台执行和任务正确性，并用故障演练验证恢复目标而非只写数字。

## 6. 行为题：事实、责任与反思

### 69. 请做一分钟自我介绍。

答题要点：

- 主线用“可靠执行”串起 rustc、Rust 安全、生产 C++→Rust 迁移和 Agent 评测，不按时间流水账罗列。
- 结尾落到岗位：希望把不确定的模型行为放入可隔离、可观测、可恢复、可验证的系统。

### 70. 为什么申请 AI Agent Infra？

答题要点：

- 已有证据集中在系统边界、程序分析、replay/verifier、工具约束和大型代码库，这些正好可迁移到 Agent 执行层。
- 同时坦诚模型推理和 GPU 服务是需要补齐的方向，说明学习与验证计划，不假装已经拥有生产经验。

### 71. 你没有大规模 VM、存储或虚拟网络运营经验，为什么适合？

答题要点：

- 先承认这是主岗直接证据缺口，再给已证明的可迁移能力：Rust/C++、rustc、低延迟验证、不变量、安全分析和大型代码库协作。
- 现场必须用 `write` 链路、隔离矩阵、存储 fencing、网络故障和容量实验展示补课结果；练习设计不能冒充生产经历。

### 72. HFT 迁移中最大的挑战是什么？

答题要点：

- 选择一个真实且可匿名的挑战，例如隐式生命周期或第一个逐事件分叉；说明本人决策和验证，不只说代码量大。
- 用 STAR+限制回答。简历没有给出具体案例，面试前必须从项目记录选定，不能临场虚构。

### 73. 讲一次失败。

答题要点：

- 选一个确实发生、不会泄密的方案失败或错误假设，重点讲怎样被测试、评审或数据发现。
- 说明责任、纠正动作和流程改进；不要把“我太追求完美”包装成失败。简历未提供具体事件，需本人补证据。

### 74. 与评审者意见不一致时怎么办？

答题要点：

- 可从 rustc/Buck2 上游贡献中选择真实评审案例：先复述对方关心的兼容、维护或性能风险，再用最小实验或拆分方案讨论。
- 目标是让变更更安全地落地，不是证明自己赢；最终结果和学到的原则要具体。

### 75. 论文在审或 Revision，如何准确介绍？

答题要点：

- 明确说 Reaper 是 OOPSLA 2026 Revision；SkillFuzz 和供应链工作是 ICSE 2027 Under Review。
- 可以讲方法和当前实验结果，但不使用“发表”“录用”等词，也要说明结论可能随修订变化。

### 76. 20 万行迁移如何说明个人贡献？

答题要点：

- 准确说“累计迁移与验证约 20 万行，负责关键数据路径”，再拆人、团队、Agent 和验证系统的责任。
- 用亲自作出的一个架构决定、一个验证设计和一个问题定位证明深度，不拿团队总量冒充个人手写量。

### 77. 10%-20% 性能改善怎样避免被质疑？

答题要点：

- 说明该结论只针对覆盖样本的离线 replay p50/p99，不推广为所有组件和线上场景。
- 准备测量卡：硬件、编译配置、输入、预热、阶段边界、样本、噪声和 profile；缺失数据不猜。

### 78. 开源经历说明了什么协作能力？

答题要点：

- 83 个已合并 rust-lang/rust PR 和 Buck2 上游导入能证明持续参与大型代码库，但数量本身不等于影响。
- 选一个评审驱动的设计变化，讲兼容、测试、拆分和维护者反馈，体现可协作性。

### 79. 怎样把研究原型变成工程系统？

答题要点：

- 从明确输入/输出和失败模式开始，把实验 oracle 变成版本化 verifier，把自由流程变成状态机和可观测事件。
- 增加隔离、预算、幂等、回归、发布和用户反馈；论文指标不能直接当生产 SLO。

### 80. 为什么应该选择你？

答题要点：

- 差异化不是“懂 Rust”，而是同时有生产低延迟迁移、编译器上游、安全分析和 Agent Skill 归因评测的证据。
- 结论保持克制：能为 Agent 执行层带来边界、不变量、回放和 verifier 思维；模型/GPU 缺口会用明确计划补齐。

## 7. 常见失分点

- 只给定义，不说它解决哪个失败模式。
- 答案出现十个组件名，却没有状态、数据流和信任边界。
- 一说“幂等”就声称 exactly-once，一说“容器”就声称安全。
- 性能数字没有分母、样本、硬件和阶段边界。
- 把模型判断当最终授权或最终 verifier。
- 论文状态、团队贡献或项目数字表述失真。
- 未知问题强行作答；承认边界后给验证方法通常更专业。
- 每题都套同一个项目，导致无法展示研究、开源、数据链路和教学的不同侧面。

## 8. 本章速记

- 80 题仍分为：24 道基础、20 道深入、14 道故障、10 道容量、12 道行为题；其中超过 25 道直接覆盖核心系统。
- 技术题四步：**定义 → 失败模式 → 方案/取舍 → 验证与限制。**
- 经历题六步：**问题 → 不变量 → 本人行动 → 验证 → 结果 → 限制。**
- 高频关键词不是装饰：幂等、租约、背压、verifier、trace、最小权限都要能画出机制。
- 每天随机抽 10 题：30 秒结论、2 分钟展开、再承受 3 次追问。
