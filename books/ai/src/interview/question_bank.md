# AI 系统与 Agent Infra 高频问题库

每个问题都围绕同一套技术结构组织：先定义对象，再解释机制和失败模式，最后给出验证方法或适用限制。系统题如果涉及多个组件，还应画出状态、数据或信任边界，避免只列产品名。

## 1. 基础概念

### 1. LLM 和 Agent 有什么区别？

答题要点：

- LLM（Large Language Model，大语言模型）主要根据上下文生成下一个 token；Agent 是围绕模型增加状态、工具、环境反馈、停止条件和验证的执行系统。
- 模型回答错误是模型风险；Agent 还会产生文件、网络、权限和外部副作用，因此系统边界比聊天场景更重要。

### 2. 什么是 Agent Infra？

答题要点：

- Agent Infra 是 Agent Infrastructure（Agent 基础设施）的简称，包括任务 API（Application Programming Interface，应用程序接口）、调度、模型路由、工具协议、沙箱、状态存储、观测、评测和审批。
- 高分回答要强调“模型提出意图，确定性系统控制权限和结果”，而不是只列框架名称。

### 3. 为什么模型能力强，不代表 Agent 系统可靠？

答题要点：

- 模型输出具有概率性，也可能受不可信上下文影响；工具、网络和外部服务还会独立失败。
- 可靠性来自权限边界、幂等、重试、状态机、verifier、回放和人工门禁，不能只靠更长 Prompt。

### 4. 容器、用户态内核与 VM 的隔离边界有何不同？

答题要点：

- 普通容器共享宿主内核；用户态内核重实现或代理大量系统接口；VM 使用 guest kernel 和 VMM/硬件虚拟化形成更强内核边界。
- 常见 KVM 路径中，vCPU 由宿主线程驱动；guest 页表先完成 `GVA（guest virtual address，客体虚拟地址）→ GPA（guest physical address，客体物理地址）`，EPT/NPT 等第二阶段页表再完成 `GPA → HPA（host physical address，宿主物理地址）`。I/O 可用 virtio 共享队列减少传统设备模拟成本，但 virtio 不保证零拷贝或零退出。
- 选择要共同考虑攻击面、兼容性、异构 OS、启动、密度、I/O/网络开销和运维，而不是简单排序“谁更安全”。

### 5. namespace、cgroup、capability、seccomp 各解决什么？

答题要点：

- namespace 隔离进程可见视图；cgroup 计量和限制资源；capability 拆分 root 权力；seccomp 过滤系统调用；Linux Security Module（LSM，如 SELinux、AppArmor）通过内核安全钩子实施对象访问策略。
- 它们互补但都不是完整沙箱，还需文件、网络、身份、更新和宿主安全边界；这里的 LSM 与数据库的 LSM-tree 无关。

### 6. 什么是结构化工具调用？

答题要点：

- 模型输出工具名和符合 schema 的参数，执行器校验后调用真实工具，再把结果作为新观察返回。
- 结构化不等于安全；仍需鉴权、路径和网络控制、超时、输出限制及副作用审批。

### 7. 为什么工具参数要用 schema 校验？

答题要点：

- schema 能拒绝缺字段、类型错误、超范围值，并让版本演进和错误返回更清晰。
- schema 只验证“形状”，不能判断调用者是否有权限或业务语义是否合理，必须叠加策略检查。

### 8. 什么是幂等？

答题要点：

- 同一个逻辑请求执行一次或重复执行，最终可观察结果相同。例如客户端超时重试创建任务时，不应生成两个任务。
- 常用方法是稳定 idempotency key、唯一约束、状态检查和外部动作收据；并非所有副作用都天然可幂等。

### 9. 重试为什么可能让故障更严重？

答题要点：

- 大量客户端同步重试会放大流量；非幂等动作还可能重复扣费、发布或写入。
- 应分类错误，使用指数退避、随机抖动、重试预算和熔断；结果未知的外部写操作优先对账。

### 10. Agent 为什么需要状态机？

答题要点：

- 状态机明确 queued、running、waiting approval、verifying、cancelled 等合法迁移，避免多个 worker 对同一任务做矛盾动作。
- 每次迁移应带版本检查和事件记录，使暂停、恢复、取消和审计可实现。

### 11. checkpoint 应保存什么？

答题要点：

- 保存仓库基础快照与 diff、已完成 step、预算、结构化 Agent 状态、策略/模型/工具版本和外部动作收据。
- 不应只保存自由文本对话；也不应把秘密和无限增长的完整 stdout 全塞进热状态库。

### 12. 容器就是安全沙箱吗？

答题要点：

- 容器提供进程、文件和资源隔离能力，但通常共享宿主内核，默认配置不等于适合执行恶意代码。
- 还需非 root、只读基础层、cgroup、seccomp、网络默认拒绝、秘密代理和必要时更强的 microVM 隔离。

### 13. 什么是 prompt injection？

答题要点：

- 不可信文档、代码或工具输出包含诱导模型忽略原目标、泄露数据或执行越权动作的内容。
- 不能只靠 Prompt 防守；仓库文本不能修改权限，所有工具调用必须在模型外重新鉴权。

### 14. 最小权限原则如何用于 Agent？

答题要点：

- 每个任务只获得完成目标所需的工具、文件、网络、秘密和时间范围，能力令牌绑定 job 与动作。
- 读写权限分开，高风险外部写需要审批；任务结束立即撤销临时能力。

### 15. 控制面与数据面为什么要分开？

答题要点：

- 控制面管理期望状态、策略、调度、租约和版本；数据面真正启动沙箱、挂卷、转发网络和执行工具。
- 控制面短暂失联时，数据面只能在未过期策略和租约内工作；撤销、fencing 和重建收敛语义必须明确。

### 16. 为什么 trace 比普通日志更适合长程 Agent？

答题要点：

- trace 用 job、attempt、step 串起模型、工具、文件和 verifier 的因果关系，能定位第一个分叉点。
- 普通文本日志仍有价值，但缺少结构和上下文传播；两者都要脱敏、限长并设置保留期。

### 17. microVM 快照恢复时必须重置哪些状态？

答题要点：

- 若把快照克隆为新实例，实例/机器 ID、随机数状态、网络身份与旧连接、短期凭证、密钥和前一租户数据都不能原样复制。
- 一致恢复还要保存匹配的 vCPU 寄存器、guest memory、虚拟设备/中断/virtqueue 状态，并协调块设备快照；KVM dirty bitmap 只说明哪些内存页写过，不等于内存、磁盘或应用已经一致。
- 基础镜像、guest kernel、VMM、CPU 特性或设备模型升级时要做版本兼容门禁；恢复失败需要有界退回冷启动，并防止批量失败形成风暴。

### 18. 临时块设备、共享卷和对象存储怎样分工？

答题要点：

- 临时块设备适合每个 run 的兼容工作区；共享卷提供跨实例文件语义；对象存储适合不可变制品、日志和 checkpoint。
- 共享卷先定义可见性、锁、`rename`、缓存和分区语义；不能因为“大家都要文件”就把所有数据放进一个声称兼容 POSIX（Portable Operating System Interface，可移植操作系统接口）语义的卷。

### 19. `strace`、`perf`、火焰图和 I/O 指标分别回答什么？

答题要点：

- `strace` 看系统调用、返回值和阻塞位置；`perf`/火焰图看 CPU 样本、热点和调用栈；I/O 指标看队列、延迟、吞吐、IOPS（Input/Output Operations Per Second，每秒输入输出操作数）和饱和。
- 工具会有观测开销和盲区，应先用低开销指标缩小范围，再做受控深挖，并固定负载与版本复现。

### 20. 存储租约为什么还需要 fencing token？

答题要点：

- 租约只表达“控制面认为谁当前拥有资源”；失联旧节点可能稍后恢复并继续写。
- 数据面必须比较单调递增 epoch/fencing token，永久拒绝旧 epoch，才能阻止两个 writer 同时认为自己合法。

### 21. veth、tap、underlay 和 overlay 分别处在哪一层？

答题要点：

- veth 常连接容器 network namespace 与宿主；tap 常把 VM 虚拟网卡接入宿主；underlay 是物理路由网络，overlay 在其上封装租户网络。
- overlay 带来 MTU、隧道状态和排障成本；网络隔离还需工作负载身份、策略、DNS 与受控 egress。

## 2. 故障处理

### 22. 沙箱文件 I/O 的 p99 突然升高，你怎样跨层定位？

答题要点：

- 先拆应用 syscall、页缓存/dirty、文件系统锁、块层队列、设备和远端副本延迟，再按节点、租户、文件大小和时间窗口对比。
- 检查日志洪水、inode/配额、集中 writeback、GC、慢盘和重试放大；止血应限流和隔离，不只增大超时。

### 23. 节点心跳丢失后，为什么不能立即重调度全部沙箱？

答题要点：

- 网络抖动可能让旧节点仍在执行；立即批量重调度会造成双写、镜像/存储风暴和级联过载。
- 先隔离故障域、停止旧 epoch 提交，用租约与 fencing 确认所有权，再按受控速率恢复，并保留人工熔断开关。

### 24. shell 命令超时但子进程仍在运行怎么办？

答题要点：

- 在独立进程组或沙箱内执行，超时先停止接受后续动作，再终止整个进程树并回收资源。
- 使用 cgroup 限制 fork、CPU 和内存；仅杀父进程可能留下孤儿进程。

### 25. worker 执行一半崩溃，怎样恢复？

答题要点：

- worker 依靠带过期时间和单调 fencing epoch 的租约成为单写者；租约过期后，新 worker 用更高 epoch 从已提交检查点创建新 attempt，数据面永久拒绝旧 epoch。
- attempt/step id 用于追踪，外部副作用使用跨 attempt 稳定的 `logical_effect_id` 幂等或对账；否则恢复会生成新 key 并重复动作。

### 26. 队列重复投递同一任务怎么办？

答题要点：

- 接受至少一次投递，用 event id、job version、当前有效租约与 fencing epoch、唯一约束拒绝重复推进。
- 重复投递是正常情形，不应依赖“消息绝不会重复”的假设。

### 27. 状态数据库不可用时，运行中沙箱要继续吗？

答题要点：

- 只有仍持有未过期本地租约的低风险纯计算才能在有界窗口内继续；不得产生外部可见提交、获取新权限或越过本地 deadline。
- 租约到期或无法续租立即停止；控制面停止调度新任务并告警，恢复后按 event id 与 fencing epoch 对账。

### 28. 检查点引用的对象损坏怎么办？

答题要点：

- 内容寻址和校验和能在读取时发现损坏，元数据只有在对象持久化成功后才指向它。
- 尝试上一检查点或重新执行可幂等 step；若证据不足，标记失败而非悄悄跳过。

### 29. 测试偶尔通过、偶尔失败，verifier 怎么判？

答题要点：

- 将其标为 flaky 或 inconclusive，不应一次通过就自动放行；固定依赖、随机种子、时间和并发条件。
- 记录多次结果与失败分布，将修复 flake 与修复目标 bug 分开。

### 30. 外部 API 超时，不知道写操作是否成功，能直接重试吗？

答题要点：

- 不能盲目重试。先使用稳定幂等键查询结果或读取动作收据，对账后再决定。
- 若对端不支持幂等与查询，高风险写应禁用自动化或要求人工处理与补偿流程。

### 31. 仓库 README 命令 Agent 上传凭证，怎样阻止？

答题要点：

- README 是不可信数据，不能改变工具策略；网络默认拒绝，秘密不进入沙箱或提示。
- Tool Proxy 对每次调用重新鉴权，外发目标受 allowlist 和数据限制，策略拒绝写入审计。

### 32. 日志中发现秘密泄漏怎么办？

答题要点：

- 立即撤销和轮换凭证，限制日志访问并确认传播范围；保留受控审计证据。
- 长期修复是让秘密通过代理使用而非暴露给不可信进程，脱敏只能作为第二道防线。

### 33. 发现可能的沙箱逃逸怎么办？

答题要点：

- 隔离受影响宿主与租户，停止相关 worker 池，保留取证并轮换宿主可接触的能力。
- 修补镜像/内核后分阶段恢复；用更强隔离、最小宿主权限和小爆炸半径降低影响。

### 34. 取消请求与“任务成功”同时发生，状态如何决定？

答题要点：

- 用状态版本和 compare-and-swap 定义合法竞争结果；终态不可被另一条迟到事件覆盖。
- 产品语义要提前决定：若 verifier 已原子提交成功，取消返回终态；否则先递增 cancellation epoch，让排队和在途的旧能力失效，再终止进程、清理资源并进入 `CANCELLED`。

### 35. Agent 的摘要漏掉关键约束，后续动作跑偏怎么办？

答题要点：

- 关键约束、审批、预算和未完成副作用必须存结构化状态，不能只靠自由文本摘要。
- trace 保留来源引用，发现分叉后可回放；摘要器本身也要版本化和回归评测。

## 3. 容量与性能

### 36. 怎样估算同时需要多少沙箱？

答题要点：

- 先估高峰到达率和平均任务占用时间，用并发约等于到达率乘停留时间得到一阶结果。
- 再按任务类型、长尾、重试、预热池和资源画像校正，不能只报一个平均数。

### 37. 怎样估算模型网关峰值？

答题要点：

- 高峰任务/秒乘每任务平均模型调用数得到请求率，再分模型、输入长度和输出长度统计 token 速率。
- 请求数相同但长上下文成本可差很多；还要考虑 cache hit、fallback 和重试放大。

### 38. Agent 成本为什么容易失控？

答题要点：

- 多轮把历史与仓库重复送入模型，循环和失败重试又会放大 token、沙箱时间与日志量。
- 使用总预算、step 上限、按需上下文、前缀缓存、模型路由和每成功任务成本指标。

### 39. 怎样设计轨迹存储？

答题要点：

- 热层保存结构化事件和索引，大 stdout、模型内容和文件转对象存储；用 cursor 流式读取。
- 设置按敏感度和用途的保留期、压缩与删除策略，审计数据和 debug 数据分开。

### 40. 怎样降低沙箱冷启动？

答题要点：

- 维护按镜像/资源类型的小规模预热池，复用只读基础镜像、仓库对象和依赖缓存。
- 不复用租户可写层或秘密；预热过多会浪费资源，需根据到达分布动态调整。

### 41. 多租户怎样公平调度？

答题要点：

- 使用租户级加权公平队列和并发、token、CPU、存储多维配额，防止大任务独占。
- 预留系统和交互任务容量，长期任务可抢占到检查点，但必须保证副作用安全。

### 42. 什么叫背压？

答题要点：

- 下游变慢时，上游减少生产或排队，而不是无限堆积和重试；它是把资源真实能力反馈给调用者。
- 可通过队列上限、并发令牌、预计等待、429/重试时间和 admission control 实现。

### 43. 哪些内容可以缓存？

答题要点：

- 不可变仓库对象、依赖包、镜像层、确定性只读工具结果和稳定模型前缀可以按哈希缓存。
- 带权限、时效或外部状态的结果要把租户、版本和策略纳入 key；错误缓存可能泄密或返回过期事实。

### 44. 队列如何分片？

答题要点：

- 可按资源类型建立池，再在池内按租户或 job hash 分片；同一 job 的状态事件需保持可解释顺序。
- 热租户会造成热点，必须结合虚拟分片、配额和 work stealing，而不是只选一个字段固定分片。

### 45. SLO、RTO 和 RPO 分别约束什么？

答题要点：

- SLO（Service Level Objective，服务水平目标）描述一个统计窗口内的正常服务目标；RTO（Recovery Time Objective，恢复时间目标）约束故障后多久恢复；RPO（Recovery Point Objective，恢复点目标）约束恢复后最多可以回退到多早的数据状态。RPO 为 5 分钟，表示灾难发生后最多接受丢失最近 5 分钟内已确认的数据，而不是“备份每 5 分钟一定成功”。
- Agent 平台应分开控制面可用性、排队、取消、平台执行和任务正确性，并用故障演练验证恢复目标而非只写数字。

## 4. AI、GPU 与科学评测

这组题把 Transformer 结构连接到训练、硬件执行和优化证据，避免只会解释模型结构却无法计算系统成本。

### 46. 一个 Linear 层的参数量和计算量怎样估算？

答题要点：

- 输入维度为 `d_in`、输出维度为 `d_out` 时，权重有 `d_in × d_out` 个参数，若含 bias 再加 `d_out`。
- 单个 token 的前向主计算约为 `d_in × d_out` 次 MAC（Multiply-Accumulate，乘加）；若乘法和加法各记一次，则约为 `2 d_in d_out` FLOPs（Floating-Point Operations，浮点运算次数）。对 `[B,T,d_in]` 输入，主矩阵计算约为 `2BT d_in d_out` FLOPs；训练还要计算输入梯度和权重梯度，主矩阵计算粗略约为前向的 3 倍，具体口径必须说明。

### 47. 为什么神经网络不能只堆 Linear 层？

答题要点：

- 多个纯线性变换合起来仍可化成一个线性变换，表达能力没有本质增加；激活函数加入非线性。
- ReLU、GELU、SiLU 是逐元素激活，平滑性和成本不同；SwiGLU 不是普通激活函数，而是包含两条输入投影、SiLU 与逐元素门控乘法的 FFN 结构，会改变参数量、计算量和形状。回答时应说明作用与形状，公式细节按具体结构推导。

### 48. 残差连接和 Normalization 为什么重要？

答题要点：

- 残差让一层学习“在原表示上加什么”，也为梯度提供较直接路径；Normalization 控制激活尺度，使深层训练更稳定。
- 它们不是防止一切爆炸或消失的魔法，还要结合初始化、优化器、精度和数据观察 loss、梯度与激活分布。

### 49. 监督、无监督、自监督和强化学习怎样区分？

答题要点：

- 监督学习使用外部标签；无监督学习从无标签数据发现结构；自监督从数据本身构造预测目标；强化学习根据行动后的奖励优化策略。
- LLM 预训练通常是自监督 next-token prediction，SFT 使用示范标签，偏好/RL 阶段再引入比较或奖励信号；这些阶段可以组合。

### 50. GPU 的算力、显存容量和显存带宽分别限制什么？

答题要点：

- 算力决定每秒可完成多少运算；容量决定模型权重、激活与 KV Cache 能否放下；带宽决定数据在 HBM 与计算单元间搬运多快。
- 大矩阵乘可能更受算力限制，逐元素或 decode 小批次操作常更受带宽和启动开销限制；结论需结合算术强度实测。

### 51. 什么是 GPU kernel、fusion 和 Roofline 直觉？

答题要点：

- kernel 是一次提交到设备执行的函数；频繁启动和反复读写 HBM 都有成本。fusion 把相邻操作合并，减少中间数据搬运与启动。
- Roofline 用“每搬一个字节做多少运算”的算术强度判断更可能受计算峰值还是内存带宽上限约束。

### 52. FP16、BF16、FP8 和混合精度有什么取舍？

答题要点：

- 位数越少通常越省存储和带宽，并可能利用更高吞吐硬件；但动态范围、精度和硬件支持不同，会带来溢出、下溢或累计误差。
- 混合精度把敏感累加或状态保留在较高精度，把大规模矩阵计算放低精度；正确性要用训练稳定性和任务指标验证。

### 53. 权重量化、激活量化和 KV Cache 量化有什么不同？

答题要点：

- 它们分别压缩模型参数、算子中间值和注意力历史状态，影响的内存占比、校准难度和误差传播不同。
- 不能只说“INT8 快四倍”：实际收益受反量化、kernel、batch、硬件和带宽限制；必须同时报告质量、显存、吞吐与分位延迟。

### 54. LoRA、全量微调和知识蒸馏怎样选择？

答题要点：

- LoRA 冻结主权重并训练低秩增量，降低可训练参数和优化器状态；全量微调可改变全部权重，成本更高；蒸馏让学生模型学习教师输出或分布，目标是能力迁移。
- LoRA 不是模型压缩的同义词，蒸馏也不保证学生保留全部能力。选择取决于部署形态、数据、许可、训练预算和评测。

### 55. 数据并行、张量并行、流水线并行和专家并行在切什么？

答题要点：

- 数据并行让各 rank 处理不同数据：传统 DDP（Distributed Data Parallel，分布式数据并行）在每卡复制完整模型，FSDP（Fully Sharded Data Parallel，全分片数据并行）或 ZeRO 等方案还会切分参数、梯度或优化器状态；张量并行切一个算子中的张量；流水线并行切层；专家并行把 MoE 专家分到不同设备。
- 它们分别引入 all-reduce 或 reduce-scatter/all-gather、算子通信、流水线气泡和 all-to-all/负载倾斜。组合方案必须同时看显存、网络拓扑、通信量和故障域。

### 56. 模型置信度高，为什么仍可能错？什么是校准？

答题要点：

- softmax 概率来自模型内部相对分数，不是现实世界正确率保证；分布外输入和训练目标偏差会造成高置信错误。
- 若许多预测都报 80% 置信，其中约 80% 真的正确，才称在该分桶上较校准。Agent 仍需 verifier 和权限门禁，不能把置信度当授权。

### 57. 基线、消融和置信区间为什么是优化证据的底线？

答题要点：

- 基线回答“比什么好”，消融回答“提升来自哪个组件”，置信区间或重复实验回答“差异是否可能只是随机波动”。
- 除被测变量外，其余数据、Harness、模型、预算和评测器版本都要固定；只挑最好一次运行或只报一个总分，无法证明系统改进可复现。

## 5. AI 核心系统开发

### 58. Tensor 的 shape、stride、Storage 和 View 分别是什么？

答题要点：

- Storage 保存底层元素；Tensor 用 shape、stride、storage offset、dtype 和 device 解释这些元素；View 与原 Tensor 共享 Storage。
- `transpose` 后逻辑形状改变，但数据未必重排，所以可能 non-contiguous；`contiguous()` 必要时会分配并复制。
- 原地修改共享 Storage 会被其他 View 看见，编译器和 Autograd 必须知道 alias/mutation。

### 59. Autograd 在 forward 时保存什么，backward 为什么会占显存？

答题要点：

- forward 同时建立由操作组成的动态计算图，并为梯度公式保存必要 Tensor 或元数据。
- backward 按反向拓扑应用链式法则，把梯度累积到叶子或所需中间量。
- 激活显存取决于网络、Batch、序列和算子保存策略；activation checkpointing 丢弃部分激活并在 backward 重算，用计算换显存。

### 60. CUDA 的 grid、block、thread 和 warp 是什么关系？

答题要点：

- CPU 启动 Kernel，形成 grid；grid 由 thread block 组成，block 可被调度到 SM，block 内线程可用 shared memory 与 barrier 协作。
- warp 是硬件共同发射一组线程指令的执行单位；同一 warp 分支走不同路径会产生 divergence，路径可能串行执行。
- block 必须能独立调度，跨 block 同步通常需要另一个 Kernel 或专门机制，不能随意用 block 内 barrier。

### 61. 什么是合并访存（coalescing）？为什么 stride 会影响 Kernel？

答题要点：

- 相邻线程访问相邻且对齐的数据时，硬件更容易用较少内存事务服务整个 warp；访问分散则会增加事务与浪费带宽。
- Tensor 逻辑相邻不保证物理相邻，真实地址由 stride 决定；Kernel 必须支持该布局或先明确复制成本。
- 是否成为瓶颈要看实际字节、缓存和 profiler，不是看到 non-contiguous 就必然复制。

### 62. Occupancy 越高是否一定越快？

答题要点：

- Occupancy 描述一个 SM 上活跃 warp 相对于硬件上限的比例，受每 block 线程、寄存器和 shared memory 限制。
- 足够 warp 可隐藏部分等待，但盲目减少寄存器可能造成 spill，更多 warp 也不能修复低效访存或算法。
- 应同时看 Kernel 时间、带宽、指令、stall 和资源使用；目标是端到端更快，不是单一 occupancy 最大。

### 63. 为什么普通 CPU 时钟容易把 GPU Kernel 测得过快？

答题要点：

- Kernel launch 通常是异步提交，CPU 可能在 GPU 完成前就走过结束时间。
- 使用同 stream 的 GPU event 或在计时边界正确同步，先预热并排除首次 JIT/分配；固定 shape、dtype、layout 和并发。
- 同步过多也会改变流水，微基准与真实端到端都要测。

### 64. All-Reduce、All-Gather、Reduce-Scatter 和 All-to-All 各做什么？

答题要点：

- All-Reduce 聚合每个 rank 的输入，并让每个 rank 得到完整聚合结果。
- Reduce-Scatter 先聚合再把不同结果块分给各 rank；All-Gather 把各 rank 的块收集成每个 rank 都有的完整结果，两者组合可实现一种 All-Reduce。
- All-to-All 让每个 rank 向所有 rank 发送各自片段，常用于专家并行 Token 派发；它对负载均衡和网络很敏感。

### 65. DDP 与 FSDP/ZeRO 的根本区别是什么？

答题要点：

- DDP（Distributed Data Parallel）通常每 rank 保存完整模型副本，处理不同数据并同步梯度。
- FSDP/ZeRO 进一步分片参数、梯度或优化器状态，在使用前后 All-Gather、Reduce-Scatter 等，以通信和调度复杂度换单卡显存。
- 选择先算权重、梯度、优化器、激活和通信；不能只说“FSDP 更省显存所以总更好”。

### 66. 一个 collective 卡住，为什么首先核对所有 rank 的调用顺序？

答题要点：

- 参与者必须以兼容的顺序、count、dtype 和 communicator 调用匹配操作；某 rank 少调用、提前异常或进入另一 collective，会让其他人等待。
- 先找最后一次全体完成点，收集各 rank 栈、stream、进程/设备错误，再查 NCCL、NIC、链路和拥塞。
- 无条件增大 timeout 只会推迟发现协议不一致或失联参与者。

### 67. RDMA 为什么仍需要内存注册、队列和完成处理？

答题要点：

- RDMA 让 RNIC 在被授权的注册内存区域之间搬运数据，减少远端 CPU 参与；注册产生可供设备使用的地址/权限信息。
- QP（Queue Pair，队列对）包含发送与接收工作队列；应用把工作请求提交为 WQE（Work Queue Entry，工作队列项），CQ（Completion Queue，完成队列）返回完成信息。连接、授权、缓冲生命周期、拥塞和错误仍由协议处理。
- GPUDirect RDMA 可减少经过主存的搬运，但不自动提供 collective 顺序、一致性或应用层重试语义。

### 68. 编译器的 graph break、guard 和 recompile 分别是什么？

答题要点：

- graph break 是捕获图无法继续，程序在编译区与 Eager 区之间切换；过多 break 会切碎融合机会并增加交界成本。
- guard 验证已编译版本依赖的 shape、dtype、layout 或 Python 条件；失败时可能选择另一版本、重新编译或回退。
- 动态输入过散可造成重新编译风暴，应结合日志、shape 分布、bucket/动态策略和缓存观察，不是简单扩大缓存上限。

### 69. 一个自定义训练算子怎样证明正确？

答题要点：

- 先声明 shape、dtype、device、layout、alias、mutation 与特殊值契约。
- 与可信高精度参考实现比较正常、极值、零长、非整块和 non-contiguous 输入；按 dtype/归约规模设置合理容差。
- 使用 `torch.library.opcheck` 一类工具核对 Schema、FakeTensor 与编译注册等框架契约，再用 `gradcheck` 或数值差分核对数学梯度；覆盖 Eager、compiled、不同设备和动态形状，最后才做正确同步与预热后的性能比较。

### 70. 为什么 GPU 作业需要 gang scheduling 和拓扑感知？

答题要点：

- 分布式作业少一个 rank 就可能全部等待，部分启动会占住 GPU，因此要达到最小集合后成组提交，并让预留可超时回滚。
- GPU、CPU、NUMA、PCIe、NVLink/NVSwitch 与 RNIC 的相对位置会改变通信路径。
- 总卡数够仍可能因节点级碎片、型号/健康/版本或拓扑硬约束而无法运行。

### 71. 一张慢卡为什么会拖慢整个训练作业？

答题要点：

- 同步训练在 collective 或流水依赖处以最慢参与者为准，其他 rank 会等待。
- 按 rank 对齐数据加载、forward、backward、collective 和 Checkpoint，找最早偏离点；再查降频、Xid/ECC、Kernel、shape、NIC 和存储。
- 集群平均 GPU 利用率会掩盖慢 rank，必须看同一步骤的分布。

### 72. Checkpoint 为什么需要 manifest 和 READY 状态？

答题要点：

- 多 rank 分片不会同时完成，看到部分文件不代表模型、优化器、随机数、数据进度和并行元数据完整。
- 每个 shard 保存大小/checksum，manifest 绑定 job/attempt/step、格式和全部对象；验证后原子发布 READY。
- 恢复只选 READY 版本，WRITING/坏 shard 被拒绝；失败临时对象由幂等 GC 清理。

### 73. 推理调度为什么不能只按请求到达顺序处理？

答题要点：

- 请求的输入长度、预期输出长度、优先级和 KV Cache 占用不同。严格先进先出会让一个超长 Prefill 挡住后面的短请求，也可能让显存被少量长会话占满。
- 调度器要在 TTFT、TPOT、吞吐、公平性和显存之间取舍，可使用连续批处理、Token 预算、队列年龄和租户配额；过载时应准入或拒绝，而不是无限排队。
- 抢占不是免费动作：可以丢弃后重算 KV、换出到较慢存储，或保留部分块。比较方案时要把搬运/重算成本和尾延迟算进去。

### 74. Prefix Cache 的 key 为什么不能只有 Prompt 文本？

答题要点：

- 可复用 KV 取决于产生它的模型权重、Tokenizer、位置编码、精度、适配器和实际 Token 序列；相同可见文字不一定得到相同 Token 或状态。
- 多租户系统还要把权限与隔离域纳入 key，避免一个租户通过命中、计时或返回内容观察另一个租户的数据。
- 更新模型、系统提示或适配器后必须自然失效；命中率、节省的 Prefill 计算、额外显存和错误命中都要监控。

### 75. Prefill/Decode 分离后，KV Cache 怎样安全交给 Decode 节点？

答题要点：

- Prefill 产出按层组织的 KV 块及元数据；控制面先选择兼容的 Decode 节点，再传输数据，接收端校验模型版本、请求代次、层/块范围、dtype、shape 和完整性信息。
- 只有全部必需块可见且元数据原子发布后，请求才能进入 Decode READY；超时或发送端重试必须靠稳定 request/attempt id 去重，旧 attempt 的迟到块不能覆盖新 attempt。
- 分离减少某些资源干扰，却新增网络字节、排队、失败恢复和容量耦合；是否划算要比较 TTFT、TPOT、吞吐与传输带宽，而不是看到“解耦”就采用。

### 76. CUDA Stream 与 Event 解决什么问题？同步到哪里才算完成？

答题要点：

- Stream 给其中排入的工作定义顺序；不同 Stream 之间默认不能凭主机提交先后推断依赖。Event 可在一个 Stream 中记录完成点，让另一个 Stream 或主机等待并用于设备时间测量。
- Kernel launch、异步拷贝和 NCCL 调用返回，通常只表示工作已经排入相应队列，不表示 GPU 或网络已经完成。复用缓冲、读回结果或报告成功前必须建立所需依赖。
- 全设备同步最容易理解，却会破坏重叠。正确做法是只等待真实数据依赖，并用 profiler 时间线确认计算、拷贝和通信是否按预期重叠。

### 77. TP、PP、EP 和分片数据并行分别在哪里通信？为什么恢复时可能要 reshard？

答题要点：

- 张量并行（TP）在单层算子内部切矩阵，常在层内产生 All-Reduce 或 All-Gather；流水线并行（PP）在阶段之间传激活与梯度；专家并行（EP）路由 Token，常用 All-to-All；FSDP/ZeRO 在使用参数和归并梯度时进行 All-Gather、Reduce-Scatter 等。
- Checkpoint 必须描述逻辑 Tensor 及原来的并行布局。若恢复时 world size 或 mesh 变化，旧 shard 不能简单按文件名发给新 rank，要按全局 offset、shape 和 dtype 重组再切分，这就是 reshard。
- 计算通信量时先写每个逻辑 Tensor 的字节数，再标出谁持有什么、在哪一步发送给谁；只背并行方式名称无法判断瓶颈。

### 78. NCCL 调用成功返回，是否说明接收缓冲已经可用？

答题要点：

- 通常不是。主机侧 API 返回多表示 collective 已异步排入 CUDA Stream；同一 Stream 的后续工作可依赖其顺序，主机或另一 Stream 读取前则需要 Event、Stream 同步或等价依赖。
- 远端 rank 退出、链路故障或设备错误可能稍后才暴露。系统要轮询异步错误、设置有边界的超时，并让所有 rank 对同一次失败作一致退出或恢复。
- “队列提交完成”“本地设备工作完成”“所有参与者得到可用结果”和“训练步骤已持久提交”是四个不同边界。

### 79. RDMA Read/Write 为什么叫 one-sided？本地完成是否等于远端应用已经处理？

答题要点：

- RDMA Read/Write 的数据搬运可以由发起端 RNIC 直接访问已授权的远端注册内存，远端 CPU 不必为每次传输执行匹配的收发调用，因此叫 one-sided。
- 本地 CQE（Completion Queue Entry，完成队列项）说明的是所请求操作达到该传输语义的完成边界，不代表远端业务线程已经看见、校验或提交了数据。
- 应用仍需版本号、所有权或通知协议来判断缓冲何时可读、能否覆盖以及失败后如何重试；Send/Receive 则需要双方预先准备匹配缓冲。

### 80. 分布式 AI 存储为什么要把元数据和大块数据分开设计？纠删码为什么不是“免费省副本”？

答题要点：

- 路径、目录、对象版本、权限和块位置是小而频繁变化的元数据；数据集 shard、模型权重和 Checkpoint 是大块数据。两者的请求大小、并发、事务和扩展方式不同，分开后可各自选择一致性与扩展机制。
- 纠删码把数据编码成多个数据块与校验块；满足规定数量的块才能重建。它比多副本节省容量，但小写更新、编码、降级读、修复流量和故障相关性更复杂。
- 设计题先列 workload：顺序吞吐、随机小读、Checkpoint 突发、恢复时间与故障域，再决定副本或纠删码；不能只按静态容量价格选择。

## 6. AI 与 Agent 综合问题

下面把模型、Agent 与平台机制组合成跨层问题。每一项都要求同时说明数据流、状态边界和失败条件。

| 口试主题 | 必须能口述与画出的内容 | 不能踩的坑 |
|---|---|---|
| Transformer、Q/K/V 与 Mask | 从 Token、Embedding 到 Attention、FFN、残差和归一化；说明 Q 用来查询、K 用来匹配、V 承载被聚合信息，以及 causal mask 为什么遮住未来 Token | Q/K/V 是学习出的投影，不是三份固定数据库；mask 也不等于权限隔离 |
| 自回归与采样 | 解释 next-token 循环，以及 greedy、temperature、top-k、top-p 怎样改变候选分布 | 温度越高不保证更有创造力或更正确；温度 0 的具体行为依实现 |
| MoE、MLA 与 MTP | 区分稀疏专家路由、注意力状态压缩和多 Token 预测训练目标，并说明各自影响计算、通信或训练 | MTP 不等于服务端 speculative decoding；MoE 总参数不等于每 Token 激活参数 |
| Prefill、Decode、KV Cache、TTFT 与 TPOT | 画出请求排队、prefill 建缓存、逐 Token decode 的时间线；说明 KV Cache 为什么省计算却占显存，TTFT 与 TPOT 分别量什么 | 不能只用总延迟掩盖排队/prefill/decode，也不能把 TTFT 与 TPOT 当同一指标 |
| MCP 与工具边界 | 说明 host/client/server、工具或资源发现、schema、调用与结果返回，以及凭证和授权应由谁控制 | MCP 的传输授权不会自动完成每个工具、资源和参数的业务授权，也不会自动信任 server 或消除 prompt injection |
| Memory | 区分当前上下文、短期工作状态、跨会话长期记忆与外部事实库；说明写入、检索、过期、版本和删除 | Memory 是可能过时或被污染的不可信数据，不等于模型参数或事实真相 |
| Planning 与执行 | 说明目标拆解、状态机、依赖、预算、停止条件、失败后重规划和 verifier | 更长计划不保证正确；计划文本不能越过实时权限和环境状态 |
| Multi-Agent | 说明为什么拆分、怎样分工、共享什么状态、如何合并冲突，以及权限、预算和终止怎样限制 | Agent 越多不必然越强，还会增加通信、重复工作、级联错误和成本 |
| RAG、索引与权限 | 画出采集、清洗、切分、embedding/倒排索引、召回、混合检索、rerank、上下文组装和生成；说明增量更新、删除与 ACL 过滤 | 相似不等于相关，召回结果不等于可信事实；权限过滤不能等生成后再补 |
| 模型网关 | 说明模型路由、版本、限流、预算、超时、重试、fallback、流式响应、观测和租户隔离 | fallback 会改变质量与语义；模型调用超时和重试也要考虑重复计费及未知结果 |
| 自进化闭环 | 画出轨迹采集、失败归因、数据/规则/Prompt/策略候选、离线评测、消融、门禁、灰度、回滚和新失败回流 | 不能让同一个有缺陷的 evaluator 同时出题、打分和决定上线，也不能只报最好一次结果 |

## 7. 开放追问：没有唯一标准答案

这些问题没有唯一方案，关键是先定义约束，再提出能够验证的设计：

- 同一平台需要同时运行 Linux 与 Windows guest，你会怎样划分镜像、设备模型、补丁、快照和故障域？
- 什么时候值得把 `epoll` 路径换成 `io_uring`？请给出可证伪的 benchmark 设计，而不是只列优点。
- 跨三个地域的 Agent 控制面，任务状态、审计事件和大制品应采用相同一致性协议吗？为什么？
- 如果量化使模型吞吐提高 30%，但工具 JSON 失败率上升 0.2%，怎样决定是否上线？
- Multi-Agent 在什么条件下比单 Agent 更值得？怎样用消融实验区分能力提升与预算增加？
- 设计一次不会危及宿主机的 OOM、网络分区或存储长尾演练，写出清理、停止和观测边界。
- 面对陌生的虚拟化或 GPU 机制，怎样从接口、资源、失败模式和证据四步推导？

- **Linux 与 Windows guest：**镜像、内核/驱动补丁流水线和快照格式按 OS/版本独立管理，控制面只共享 Task、租约和审计等通用协议；设备模型暴露经过验证的最小交集，OS 特有能力通过 capability 标记调度。节点池和故障域至少按宿主版本、guest OS 与虚拟化能力划分，分别做启动、快照恢复、时钟/网络重置和补丁回滚演练，避免一个坏镜像影响全部平台。
- **何时从 epoll 换 io_uring：**先提出假设，例如“该负载的系统调用和上下文切换是主要 CPU 成本，批量提交可降低每请求开销”。用同硬件、同连接数、同请求大小和同业务逻辑实现 A/B，逐级扫描并发，测吞吐、p50/p99、CPU/请求、系统调用、取消正确性和内存；同时覆盖过载与连接关闭。若瓶颈实际在应用计算或网络，或复杂度增加而指标无稳定收益，就不迁移。
- **三地域不同数据：**不必采用同一协议。任务当前所有权需要清晰单写者和可接受的故障切换，可按 home region/共识范围设计；审计事件偏向不可丢、可追加和跨区复制，但读取可稍后；大制品通常不可变，可异步复制并用哈希校验。先为每类数据写一致性、RPO、RTO、写入延迟和成本，再选择协议，不能因都叫“数据”就统一强一致。
- **量化上线决策：**先把 0.2% JSON 失败换成绝对业务量和风险成本，并给差值置信区间；再按工具风险、Schema 类型和任务分层，确认失败由量化引起。可尝试敏感层保留高精度、约束解码或失败回退，再做配对评测。只有吞吐收益达到目标且工具正确率/安全硬门槛仍满足才 canary；高风险动作不应拿平均 30% 吞吐抵消正确性回归。
- **Multi-Agent 是否值得：**任务能划成低耦合子问题、可并行关键路径、角色确有不同信息/工具且合并可验证时更可能值得。实验至少比较单 Agent 同预算、单 Agent 增加同等 Token、Multi-Agent 同总预算三组；再逐个移除并行、角色提示和投票做消融。若提升只来自多花预算而非协作结构，就不能宣称多 Agent 本身有效。
- **安全故障演练：**在独立测试故障域和专用租户中注入，预先限制最大节点/任务数、时长和资源，配置自动停止与人工 kill switch。OOM 用测试 cgroup limit，网络分区只作用于指定 namespace/代理，存储长尾由测试后端延迟；全程观察任务状态、重试、队列、孤儿资源和邻居 SLO。结束后撤销注入、终止进程树、卸载并清理资源、核对外部副作用和审计，未通过清理检查不得扩大范围。
- **陌生机制四步法：**先找接口：谁调用、输入输出和完成信号；再列资源：内存、队列、计算单元和所有权何时转移；然后在每个边界插入超时、重复、容量满和崩溃，写出可见结果；最后用文档、trace、计数器或最小实验验证。例如 GPU kernel 从 launch 接口开始，追输入缓冲和 stream，考虑 OOM/异步错误，再用 profiler 时间线证实，而不是先背厂商名词。

## 8. 常见回答缺陷

- 只给定义，不说它解决哪个失败模式。
- 答案出现十个组件名，却没有状态、数据流和信任边界。
- 一说“幂等”就声称 exactly-once，一说“容器”就声称安全。
- 性能数字没有分母、样本、硬件和阶段边界。
- 把模型判断当最终授权或最终 verifier。
- 未知问题强行作答；承认边界后给验证方法通常更专业。

## 9. 回答框架

- 技术题四步：**定义 → 失败模式 → 方案/取舍 → 验证与限制。**
- 高频关键词不是装饰：幂等、租约、背压、verifier、trace、最小权限都要能画出机制。
- 数量题先写单位和假设，再计算并说明平均值、分位数和故障余量的差别。
- 系统设计题需要同时画出正常数据流、状态变化、信任边界和至少一条失败恢复路径。
