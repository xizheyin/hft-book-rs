# 简历深挖：让每个亮点都经得住五层追问

简历面试不是朗读简历，而是一场“证据审计”。面试官通常会连续追问：你解决了什么问题？为什么这样设计？你本人做了什么？怎样证明结果？如果重来会改什么？亮眼数字只能帮你拿到第一问，完整证据链才能撑到第五问。

这章按六组经历展开。每组都包含：通俗解释、30 秒答法、追问树、答题骨架和红线。示例骨架只整理简历已经证明的内容；凡是团队人数、硬件型号、具体模型、线上 SLA 等简历未提供的信息，都必须从本人记录中补齐，不能现场编造。

> 公开表达边界：不披露量化机构名称或敏感业务细节。Reaper 是 **OOPSLA 2026 Revision**；SkillFuzz 与 Rust 生态漏洞传播工作均为 **ICSE 2027 Under Review**。

## 1. 一套通用的五层追问法

面对任何经历，先在纸上填好这五层：

| 层次 | 面试官的问题 | 你要给的证据 |
|---|---|---|
| 问题 | 为什么值得做？旧方案哪里痛？ | 一个具体失败模式或约束 |
| 设计 | 为什么选这个方案？ | 不变量、接口、备选方案与取舍 |
| 归属 | 你本人做了什么？ | 亲自作出的判断、实现或验证 |
| 验证 | 如何知道它正确且更好？ | 数据集、基线、指标、测试和反例 |
| 反思 | 方案在哪些条件下会失败？ | 适用边界、遗留风险和改进方向 |

如果某层答不出来，不要用更多术语遮盖。可以明确说“这个数据简历中没有，我会回到实验记录核对；目前能确认的是……”。

## 2. HFT：生产级 C++ 向 Rust 迁移

### 2.1 通俗解释

一条期货数据链路像传送带：Parser 把交易所字节流拆成消息；Normalizer 把不同格式整理成统一事件；Orderbook 根据增量事件维护盘口；Feature/Model 计算特征；Alpha 产生策略信号。迁移的难点不是逐行翻译语法，而是保证同一个事件在相同顺序下导致相同状态变化，同时不能破坏尾延迟。

### 2.2 30 秒答法

> 我参与某量化机构生产级高频期货系统的 C++ 到 Rust 迁移，累计迁移与验证约 20 万行，负责 Parser、Orderbook/Normalizer、Feature/Model 到 Alpha 的关键数据路径。核心工作不是语法替换，而是梳理数据所有权、生命周期和逐事件因果顺序，把共享对象、裸指针和回调形成的隐式依赖改成明确的模块、trait 与所有权边界。验证上用 C++ 参考实现与 Rust 实现做 replay 和影子验证，逐事件对齐中间状态与输出；在覆盖样本上验证语义一致性，离线 replay 的 p50/p99 改善 10%-20%。Coding Agent 用于受约束的迁移、验证和测试任务，人类负责语义、架构、风险与最终验收。

### 2.3 高频追问

1. **请画出完整数据路径。**
   - 先画输入、解析、标准化、订单簿、特征、模型、Alpha。
   - 标出每一步的状态所有者、事件序号和验证点。
   - 不要讲机构特有策略逻辑；用匿名字段和通用事件说明即可。

2. **所谓“隐式依赖”具体是什么？**
   - 可解释为共享运行时对象、裸指针和回调订阅让调用者难以看出谁能修改状态、对象活多久、事件按什么顺序到达。
   - 再讲 Rust 中怎样用模块、trait、借用或所有权表达这些关系。
   - 必须准备一个真实但匿名的例子，不能只重复术语。

3. **如何保证 C++ 与 Rust 语义一致？**
   - 固定输入、配置和初始状态。
   - 对齐事件身份与顺序，在多个边界记录状态摘要或关键字段。
   - 找到第一个分叉事件，而不是只比较最终 Alpha。
   - 对浮点误差、时间戳、并发和缺失数据制定明确比较规则。

4. **影子验证与离线 replay 有何区别？**
   - replay 强调可复现的历史输入与快速回归。
   - 影子验证强调在真实或仿真运行链路旁边执行新实现，但不让它影响生产决策。
   - 回答本人项目中的准确含义前，应核对内部定义；不同团队对“shadow”叫法可能不同。

5. **为什么 p50 和 p99 都改善？**
   - 只能提出待验证机制：更少的动态分配、拷贝、间接访问或更清楚的数据布局等。
   - 要用 profiling 或分阶段基准证明，不能把语言选择直接当因果。
   - 补充测量对象、时钟、预热、硬件、编译参数、样本规模和噪声控制。

6. **`unsafe` 与 `RefCell` 为什么受控？**
   - 它们不是错误；问题是会把部分证明责任从编译器交还给人。
   - 说明允许条件：边界足够小、不变量明确、有测试或基准、审计成本可控。

7. **Agent 到底做了什么？**
   - 讲任务拆分、上下文范围、可调用工具、门禁和停止条件。
   - 清楚区分“Agent 生成”“验证系统检查”“人类决策”。
   - 准备一个被门禁拒绝的真实案例、处置过程和后续流程。

8. **20 万行是你个人写的吗？**
   - 准确复述为“累计迁移与验证约 20 万行，我负责关键数据路径”。
   - 说明自己的责任边界；不要把团队和 Agent 产出算成个人手写代码。

### 2.4 答题骨架

#### 面试前阻塞项：HFT 测量卡

| 字段 | 本人填写 |

| 被计时的起点、终点与单位 | 【本人填写；不知道就写未记录】 |

阻塞验收：让同伴只围绕这张卡连续追问五层；任何关键字段仍只能靠猜，就继续按简历原句克制陈述。

```text
约束：生产语义不能变，关键路径不能退化，机构细节需要匿名。

限制：测量口径和个人贡献需准确说明；不把离线结果推广为所有生产场景。
```

### 2.5 红线

- 不泄露机构、策略、品种、交易参数或内部架构标识。
- 不说“我独立写了 20 万行”。
- 不说“Rust 一定比 C++ 快”。
- 没有测量卡时，不猜硬件、样本量或优化来源。
- 不把 Agent 描述成独立承担生产风险的主体。

## 3. rustc 与 Buck2：大型上游项目中的可靠变更

### 3.1 通俗解释

编译器像一条多阶段工厂：源代码经过解析、类型检查和中间表示，最后成为机器码。任何共享状态处理错误，都可能让诊断信息互相污染；任何安全检查，都可能给数百万次编译带来成本。因此“能实现”只是第一步，还要证明兼容、性能可接受、测试能阻止回归。

Buck2 的 RISC-V 支持则像给物流系统增加一个新国家：不仅要认出地址，还要准备路线、工具、发布清单和制品映射，多个改动必须按依赖顺序落地。

### 3.2 30 秒答法

> 我长期贡献 rust-lang/rust，简历统计为 106 个 PR、83 个已合并，也是 Triage Team 成员。代表工作包括：重构 rustc 诊断参数生命周期，通过快照、翻译、清理、恢复和同名异值不变量检查避免共享状态污染；为 Vec 多个 unsafe API 添加可选 UB 前置条件检查，并用 run-fail 测试覆盖 Vec/String 路径、经 rustc-perf 评估后合入。这两项随 Rust 1.90 发布。另一个例子是 Buck2 RISC-V 基础设施，我按依赖拆成 3 个 PR，覆盖平台识别、target/toolchain、发布矩阵和 artifact 映射，在 RISC-V Debian 验证后均被 Meta 上游导入。

### 3.3 rustc 追问

- HIR 与 MIR 是什么，为什么安全分析常落在 MIR？
- 主诊断与子诊断共享了什么状态？污染会导致错误文本、参数还是生命周期问题？
- 快照、翻译、清理、恢复的严格顺序是什么？异常路径怎样保证恢复？
- “同名异值”为什么构成不变量违规？发现后是编译期错误、调试断言还是其他机制？
- 为什么 UB 前置条件检查是可选的？开启和关闭各适用于什么场景？
- Vec 与 String 的委托路径为什么需要同时测试？
- rustc-perf 看了哪些指标？是否存在统计噪声？只能根据实际记录回答。
- 评审提出过什么反对意见？最终设计和初稿有何变化？
- Triage Team 的工作流程是什么？如何判断 regression、优先级与责任组件？

### 3.4 Buck2 追问

- host triple、target triple、execution platform 和 toolchain 分别是什么？
- RISC-V 支持为什么不只是增加一个字符串？
- 3 个 PR 的依赖图如何画？其中一个未合入时其余是否安全？
- DotSlash artifact 映射解决什么分发问题？
- 如何在 RISC-V Debian 验证构建？验证了“能编译”还是也验证运行？
- 为什么由 Meta upstream import，而不是直接在最终仓库一次提交？
- 如何避免平台矩阵增长造成 CI 成本爆炸？

### 3.5 答题骨架

```text
背景：上游项目变更影响面大，正确性、兼容性和性能必须一起考虑。
问题：选一个具体问题——诊断共享状态、unsafe 前置条件或 RISC-V 缺口。
设计：先写不变量，再讲最小改动面和依赖拆分。
验证：测试用例、目标平台、性能套件、评审和回归路径。
结果：给出准确 PR/发布事实。
反思：讲一个被评审改变的选择，以及为什么新方案更稳妥。
```

### 3.6 红线

- PR 数量不是答案主体；至少讲透一个设计。
- 不把“随 Rust 1.90 发布”扩大成主导整个版本。
- 不声称可选 UB 检查能发现所有未定义行为。
- 不混淆 host 与 target，也不把交叉编译等同于在目标机成功运行。

## 4. Crates-Pro：从生态元数据到增量数据链路

### 4.1 通俗解释

Crates.io 像一个不断更新的零件市场。一个 crate 有许多版本，每个版本又依赖其他零件；当任何版本变化时，系统既要更新它自己的信息，也要知道哪些下游可能受影响。PostgreSQL 适合可靠保存结构化记录，Kafka 适合传递持续到来的事件，图数据库适合做多跳依赖查询，但多种系统一起使用会引入一致性与重放问题。

### 4.2 30 秒答法

> 我是 Crates-Pro 的核心贡献者，参与约 16 万个 crates、100 余万个版本的 Cargo 元数据解析和依赖图构建，支持批量分析、反向依赖更新与实时增量更新。驻场协作期间参与 controller 拆分、PostgreSQL-Kafka 数据链路和异步导入，也实现过 TuGraph/PostgreSQL 数据传输；之后继续维护模块化 workspace 并实现 OpenAPI 服务。这个经历让我接触到生态级数据建模、事件链路和跨存储同步，但简历没有提供线上 QPS 或 SLA，我不会虚构这些指标。

### 4.3 追问树

- Cargo 版本约束、feature、可选依赖、平台条件如何改变依赖边？
- 为什么“一个 crate”与“一个 crate version”必须分开建模？
- 批量全量构建和实时增量更新如何共存？
- Kafka 消息重复、乱序或消费者重启时怎么办？
- 事件的幂等键是什么？数据库提交与 offset 提交顺序如何选择？
- PostgreSQL 与 TuGraph 之间谁是事实来源？同步失败如何发现和修复？
- 反向依赖更新如何避免一次变更触发无限扩散？
- controller 为什么拆分？拆分前后的责任边界是什么？
- OpenAPI 如何处理分页、错误协议、版本演进和输入校验？
- 百万版本的规模是存量，不等于吞吐；实际性能如何测？

### 4.4 答题骨架

```text
对象：crate、version、dependency edge、分析结果。
写入路径：来源事件 → 解析/校验 → Kafka 或任务队列 → 消费者 → 存储。
关键不变量：重复消息不产生重复状态；失败可重放；图与关系记录可核对。
我的贡献：只说自己实际参与的 controller、链路、传输、workspace、OpenAPI。
结果：规模用简历数字；没有 QPS/SLA 就明确没有。
改进：补充 checksum、对账任务、dead-letter、背压和可观测性，但标为设计建议。
```

### 4.5 红线

- 不把参与链路说成独自设计整个平台。
- 不声称 Kafka 提供端到端 exactly-once；必须说明应用和存储侧条件。
- 不把图数据库说成所有依赖查询的唯一正确选择。
- 不拿存量规模冒充每秒吞吐。

## 5. Reaper：检测 Rust 安全抽象的 Soundness

### 5.1 通俗解释

Rust 允许库作者在内部使用 `unsafe` 实现高性能功能，再向用户提供看起来安全的 API。这像餐厅后厨可以使用锋利工具，但端给顾客的菜不能带来额外危险。所谓安全抽象 soundness，就是：只要调用者遵守 safe API 的正常规则，就不应该被迫承担未定义行为。Reaper 试图在编译器中分析这条承诺是否被破坏。

### 5.2 30 秒答法

> Reaper 是我的第一作者工作，目前状态是 OOPSLA 2026 Revision。它面向由 unsafe 实现、对外暴露 safe API 的 Rust 安全抽象，直接在 MIR 上做流敏感抽象解释，在共享状态中联合建模所有权、对象有效性和内存布局，同时检查指令级未定义行为以及能逃逸到 safe API 边界的契约违规。在 46 个 RustSec 漏洞、53 个真实缺陷上，检测到 32 个漏洞、36 个缺陷，漏洞召回 69.6%、缺陷召回 67.9%、告警级精确率 51.6%；生态扫描在 83 个 crates 中发现 114 个此前未知缺陷，45 个获维护者确认，27 个已修复。

### 5.3 追问树

- soundness、completeness、precision、recall 分别是什么？
- 为什么直接分析 MIR，而不是源代码 AST、HIR 或 LLVM IR？
- “流敏感”比“流不敏感”多保存了什么信息，成本是什么？
- 抽象域怎样表达所有权、存活、移动、析构、未初始化、边界、对齐和偏移？
- 多种规则按需组合如何避免状态空间爆炸？
- 指令级 UB 与可逃逸契约违规有什么差别？
- 51.6% 精确率意味着什么？误报是否可接受要结合审查成本回答。
- 漏掉的漏洞属于不支持特性、近似损失，还是实现缺陷？
- 维护者确认的标准是什么？27 个修复如何追踪？
- 生态扫描如何选择 83 个 crates，结论能否推广？

### 5.4 答题骨架

```text
问题：safe API 隐藏 unsafe 实现，普通调用者无法检查内部契约。
选择 MIR：比源码更规范，又保留 Rust 语义；具体优势与损失按论文回答。
方法：流敏感抽象解释 + 所有权/对象状态/内存布局的组合域。
验证：已知 RustSec 基准衡量召回和精确率；生态扫描看真实新缺陷。
结果：准确复述 46/53、32/36、69.6%/67.9%/51.6%、114/45/27。
限制：主动讨论误报、漏报、选择偏差和不支持的 Rust 特性。
```

### 5.5 红线

- 论文状态只能说 Revision。
- 不说“证明了程序安全”或“能检测所有 UB”。
- 不回避 51.6% 精确率，也不把维护者未回复当成错误或正确。
- 不把静态分析结果直接等同于可利用漏洞。

## 6. SkillFuzz：把 Agent Skill 当成可测试的软件

### 6.1 通俗解释

Agent Skill 往往同时包含自然语言说明、例子和脚本。它更像一个“小软件包”，而不只是一段提示词。Skill 可能要求工具按某个顺序调用、输入必须符合某种格式、某类文件不得修改。SkillFuzz 的思路是：先把这些要求改写成能被推翻的假设，再故意构造只违反一条假设的任务，看 Skill 是否会把 Agent 引向错误行为。

### 6.2 30 秒答法

> SkillFuzz 是我的第一作者工作，目前为 ICSE 2027 Under Review。它从 Skill 的文件组织、输入格式、工具调用、工作流顺序和领域规则中抽取可证伪假设，并生成定向违反单一假设的任务变体。为避免把无解任务或模型能力不足误判为 Skill 缺陷，我们先在 Docker 中执行参考解和 verifier 做准入，再对同一任务进行有/无 Skill 配对运行，并审查执行轨迹。80 个真实 Skills 共生成 800 个任务，569 个通过准入并完成配对，产生 79 个候选；审查排除 31 个误报，最终确认 48 个严格缺陷，覆盖 18 个 Skills。

### 6.3 追问树

- 为什么 Skill 是软件制品，而不是普通 Prompt？
- 怎样从自然语言说明抽取“可证伪假设”？
- 如何保证一个变体只违反一条假设？若条件互相依赖怎么办？
- 参考解与 verifier 由谁产生？如何防止 oracle 自己出错？
- 为什么有/无 Skill 配对能帮助因果归因？它仍不能排除什么？
- 模型采样随机性如何控制？是否需要多次运行和统计区间？
- 执行轨迹审查看哪些事件：提示、工具参数、文件变化、错误、最终答案？
- 569/800 未通过的 231 个任务为什么被过滤？
- 79 个候选中的 31 个误报有哪些类别？
- 48 个严格缺陷怎样定义？是否经过双人审查或维护者确认？以论文记录为准。
- 如果变成 CI 服务，如何做版本固定、缓存、预算和回归选择？
- 如何防止被测 Skill 窃取凭证、联网或破坏宿主机？

### 6.4 答题骨架

```text
目标：测试 Skill 是否诱发错误，而不是泛泛测试模型聪明程度。
假设：把自然语言和工作流要求改成可验证命题。
变异：每次定向破坏一个命题，尽量控制其他因素。
准入：Docker 运行参考解 + verifier，排除无解或不稳定任务。
归因：同任务有/无 Skill 配对 + 轨迹审查。
漏斗：800 → 569 → 79 → 排除 31 → 48，覆盖 18 个 Skills。
限制：随机性、oracle 偏差、Skill 样本代表性和人工审查成本。
```

### 6.5 红线

- 论文状态只能说 Under Review。
- 不说配对实验“完全证明”了因果关系。
- 不把被准入过滤的任务都叫失败。
- 不把候选缺陷数 79 当成最终确认数 48。
- 不忽略 verifier、参考解和人工审查本身也可能出错。

## 7. 供应链研究与 FRIES

### 7.1 通俗解释

“我的项目依赖了一个有漏洞的库”不等于“我的代码一定会运行到漏洞函数”。供应链研究把问题拆成三层：包是否进入依赖图、下游何时升级修复、实际调用图能否走到脆弱函数。FRIES 则从真实客户端怎样使用库中学习 API 依赖和顺序，生成更可能触发复杂交互的模糊测试目标。

### 7.2 30 秒答法

> 我有两组相关工作。第一组是 Rust 生态漏洞传播与函数级可达性，第一作者、ICSE 2027 Under Review：从 712 个可分析 RustSec advisories 构建 249 万组 advisory-下游记录，覆盖 138,869 个下游 crates，并进一步分析下游修复、GitHub PR 和跨 crate 调用可达性。第二组是 FRIES，第一作者、发表于 ISSTA 2024：从生态客户端 MIR 挖掘 API 数据依赖与调用顺序，结合类型和所有权规则生成可编译 fuzz targets；在 20 个流行库上达到 62% API 覆盖率和 99% 目标可编译率，发现 130 个缺陷，其中 84 个此前未知、54 个获维护者确认或修复。

### 7.3 追问树

- 为什么直接依赖只占传播记录一小部分？传递依赖怎样放大影响？
- “本地修复延迟”如何定义？披露、PR、合并、发布分别是哪一个时间点？
- 自动更新 PR 与更长本地修复延迟只是相关，可能有哪些混杂因素？
- 跨 crate 调用图如何处理泛型、动态分派、宏和 build script？
- 62/405 个脆弱函数受 feature gate 控制意味着什么？不能推出什么？
- 为什么只在 193 个含脆弱函数信息的 advisories 上做可达性？
- FRIES 的加权控制依赖图如何构建？权重来自生态频率还是其他信号？
- 生成序列怎样通过类型匹配和所有权检查？
- 62% API 覆盖率和代码覆盖率有何区别？
- 99% 可编译率的分母是什么？失败目标如何分类？
- 发现的 130 个缺陷如何去重、复现和负责任披露？

### 7.4 答题骨架

```text
共同问题：包级信号很粗，真实风险和测试价值需要更细粒度的程序信息。
供应链：包暴露 → 下游修复 → 函数可达，逐层缩小结论。
FRIES：真实使用挖掘 → 依赖/顺序图 → 类型与所有权约束 → fuzz target。
验证：分别给出数据规模、覆盖、可编译率、缺陷确认。
边界：可达不等于可利用；默认配置不可达不等于所有配置都不可达；相关不等于因果。
```

### 7.5 红线

- 供应链论文状态只能说 Under Review。
- 不把依赖存在直接等同于漏洞可利用。
- 不把默认构建不可达说成永久安全。
- 不把“自动 PR 与延迟相关”讲成自动化导致延迟。
- 不把 API 覆盖率误称为行覆盖率。

### 8.2 项目级故事索引

以下六组只是选择故事的索引，不是已经完成的行为题答案。只有把后面的事件级模板用真实事件填满，才可以称为 STAR。

#### STAR 1：关键数据路径迁移与双实现验证

- **S**：生产 C++ 系统通过共享对象、裸指针和回调表达隐式依赖，迁移又受语义与低延迟双重约束。
- **T**：迁移 Parser 到 Alpha 的关键路径，并保持与参考实现一致。
- **A**：梳理所有权、生命周期与事件顺序；建立模块/trait 边界；限制 unsafe/RefCell；用 replay、影子验证和逐事件检查定位分叉；为 Agent 设置验证门禁。
- **R**：累计迁移验证约 20 万行；覆盖样本语义一致；离线 p50/p99 改善 10%-20%。
- **L**：准备说明测量环境、覆盖范围、个人贡献边界和未覆盖场景。

#### STAR 2：SkillFuzz 的因果归因漏斗

- **S**：Skill 出错时，很难判断是 Skill 诱导错误、任务无解，还是模型本身不会。
- **T**：建立能确认严格 Skill 缺陷的测试流程。
- **A**：生成单假设变体；用 Docker 参考解和 verifier 准入；有/无 Skill 配对；审查轨迹并剔除误报。
- **R**：800 个任务中 569 个完成配对，79 个候选经审查后确认 48 个严格缺陷，覆盖 18 个 Skills。
- **L**：配对不能自动消除模型随机性和 oracle 偏差，需说明控制方法。

#### STAR 3：rustc 诊断共享状态不变量

- **S**：主诊断和子诊断参数生命周期可能造成共享状态相互污染。
- **T**：让派生代码自动、安全地处理参数状态。
- **A**：重构快照、翻译、清理与恢复流程，并加入同名异值不变量检查和回归测试。
- **R**：改动合入并随 Rust 1.90 发布。
- **L**：面试前准备具体复现、替代方案及评审反馈。

#### STAR 4：Vec unsafe API 的低成本检查

- **S**：unsafe API 的调用者若违反前置条件，可能触发未定义行为；检查又不能无视编译性能。
- **T**：增加可选前置条件检查，同时控制兼容和性能风险。
- **A**：覆盖多个 Vec API 和 Vec/String 委托路径，加入 run-fail 测试，用 rustc-perf 评估。
- **R**：改动合入并随 Rust 1.90 发布。
- **L**：只能说检测已建模的前置条件，不能宣称覆盖全部 UB。

#### STAR 5：Buck2 RISC-V 的依赖拆解

- **S**：支持新架构横跨主机识别、平台约束、target/toolchain、发布矩阵和制品映射。
- **T**：降低大改动的评审与落地风险。
- **A**：按依赖拆成 3 个 PR，逐步验证，在 RISC-V Debian 构建检查，并配合上游导入流程。
- **R**：3 个 PR 均经 Meta upstream import 合入。
- **L**：准备说明验证深度，不能把“构建通过”自动说成全功能验证。

#### STAR 6：Reaper 从抽象模型到真实修复

- **S**：safe API 背后的 unsafe 实现可能把契约违规暴露给普通调用者。
- **T**：同时捕获指令级 UB 和能逃逸到 API 边界的问题。
- **A**：在 MIR 上设计流敏感抽象解释，组合所有权、对象有效性和内存布局信息；用 RustSec 与生态扫描验证。
- **R**：已知数据上得到相应召回/精确率；发现 114 个此前未知缺陷，45 个确认、27 个修复。
- **L**：主动说明 51.6% 精确率、漏报和样本选择边界；论文状态为 Revision。

### 8.3 三张事件级 STAR 模板

三张模板不得用“项目整体”代替具体事件，也不得根据本书示例虚构。每张都要有时间点、触发信号、候选方案、本人决定和可验证结果。

## 9. 常见失分点

- 只背 30 秒版本，一进入细节就无法画数据流或状态机。
- 每个问题都从背景讲五分钟，没有先给结论。
- 把团队累计结果、Agent 生成结果和个人贡献混在一起。
- 数字很多，却没有分母、基线、样本和限制。
- 论文指标讲得很熟，但说不出误报、漏报和失败案例。
- 用“保密”回避通用技术方法；保密的是业务细节，不是因果顺序、验证思想和故障分类。
- 回答工具名，却不讲为什么选它以及失败后怎样恢复。
- 遇到未知就猜。高质量回答可以是：“简历没有这个指标，我不想编造；我会这样测……”

## 10. 本章速记

- 所有经历统一使用：**问题 → 不变量 → 本人动作 → 验证 → 结果 → 限制。**
- HFT 重点：事件顺序、双实现 diff、尾延迟、Agent 与人的责任边界。
- rustc/Buck2 重点：共享状态、可选检查、性能回归、依赖拆 PR。
- Crates-Pro 重点：版本图、幂等、重放、跨存储对账；没有线上指标就不编。
- Reaper 重点：MIR 抽象解释、soundness、精确率/召回率与真实确认。
- SkillFuzz 重点：单假设变异、准入、配对、轨迹、误报漏斗。
- 供应链/FRIES 重点：包级不等于函数级，可达不等于可利用，相关不等于因果。
- 练熟六个 STAR，但每次只选最贴近问题的一个。
- 下一步可用[题库](question_bank.md)做压力追问，或用[系统设计](system_design.md)练习迁移这些方法。
