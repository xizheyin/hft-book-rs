# 一次文件写入：从 `write()` 到真正落盘

> 难度：必会。DeepSeek 的 Agent Infra 官方岗位描述直接点名：要能讲清一次文件写入的完整路径与潜在瓶颈。

调用 `write(fd, buf, 4096)` 后，**若返回值是 4096**，通常只代表这 4096 字节已被操作系统接受，并不等于它们已经安全地进入 SSD。成功调用也可能短写，只返回小于 4096 的正数；程序必须继续写剩余部分。把它想成寄快递：柜台收件、货车出发、到达分拨中心和最终签收，是四个不同承诺。

## 1. 先画出全链路

```mermaid
flowchart LR
    A["用户态缓冲区"] --> B["write 系统调用"]
    B --> C["VFS（虚拟文件系统层）<br/>与具体文件系统"]
    C --> D["页缓存 / 脏页"]
    D --> E["writeback 与块层"]
    E --> F["设备驱动 / NVMe<br/>高速存储协议队列"]
    F --> G["控制器缓存"]
    G --> H["持久介质"]
```

从应用视角逐层看：

1. 程序把数据放在用户态内存中。
2. CPU 进入内核，内核校验文件描述符、地址和权限。
3. VFS（Virtual File System，虚拟文件系统）把通用文件操作分派给 ext4、XFS 等具体文件系统。
4. 普通 buffered I/O 往往先复制到页缓存，把页面标成 dirty。
5. 后台 writeback 或显式同步把脏页变成块 I/O 请求。
6. 块层合并、排队并提交请求，驱动把命令送入设备队列；NVMe（Non-Volatile Memory Express）是 SSD 常见的高速存储协议。
7. 控制器可能先确认自己的易失或持久缓存，之后才写入介质。

这条路径中还会出现权限检查、配额、日志、校验和、加密、Copy-on-Write、RAID 或远端复制。面试时不必一次背完所有名词，但必须先说清“成功”究竟发生在哪一层。

## 2. `write`、`fsync` 与原子性不是一回事

| 操作 | 通常保证什么 | 通常不保证什么 |
|---|---|---|
| `write` 返回成功 | 字节已被内核接受 | 已经掉电不丢 |
| `fdatasync` 成功 | 恢复文件数据所需的信息已同步 | 与数据无关的全部元数据 |
| `fsync` 成功 | 文件数据及所需元数据已请求持久化 | 父目录中的新文件名必然持久化 |
| 临时文件 + `rename` | 同一文件系统内切换名称可原子可见 | 崩溃后目录项必然存在，除非同步目录 |

常见的安全更新协议是：写临时文件，`fsync` 临时文件，`rename` 覆盖目标，再 `fsync` 父目录。它解决的是“要么看到旧版本，要么看到新版本”，不是所有文件系统与设备上都免费的魔法。

`O_DIRECT` 也不是“自动更快”。它试图绕开页缓存，但会带来对齐约束、较小 I/O 难以合并、同步等待等成本。先量出缓存污染或双重缓存确实是瓶颈，再决定是否使用。

## 3. 一个带数字的 Agent 日志例子

假设 10,000 个并发沙箱，每个沙箱每秒写 20 条 512 B 日志：

```text
逻辑吞吐 = 10,000 × 20 × 512 B ≈ 97.7 MiB/s
操作次数 = 200,000 writes/s
```

如果每条日志都单独 `fsync`，系统面对的是 20 万次同步屏障，而不只是约 98 MiB/s 的顺序写。把 100 条日志合并为一个批次，逻辑字节数几乎不变，同步次数却可降约 100 倍。代价是崩溃时可能丢失一个批次，所以批大小必须由恢复目标决定。

这就是系统面试常见的 trade-off：吞吐、尾延迟、数据丢失窗口三者不能只挑优点。

## 4. 瓶颈怎样逐层定位

| 现象 | 先看什么 | 可能原因 |
|---|---|---|
| `write` 本身慢 | syscall 延迟、缺页、锁等待 | 内存压力、文件系统锁、脏页节流 |
| 吞吐高但尾延迟尖刺 | dirty/writeback、I/O 队列深度 | 集中回写、GC、设备拥塞 |
| CPU 高、设备不忙 | 拷贝、校验和、压缩、日志格式化 | 小 I/O、序列化或锁竞争 |
| 设备利用率高但吞吐低 | IOPS、请求大小、随机度 | 大量 4 KiB 随机写或同步屏障 |
| 共享卷偶发长尾 | 客户端、网络、服务端与副本分别打点 | 拥塞、重试、慢副本、元数据热点 |
| `ENOSPC` 但磁盘似乎还有空间 | inode、配额、保留空间 | 不只是字节容量耗尽 |

压测必须记录请求大小、读写比例、同步语义、并发度、数据集是否超过缓存、设备型号和运行时长。只报一个 MB/s 数字几乎不能复现。

## 5. 沙箱存储为什么更难

Agent 会创建大量小文件、下载依赖、解压仓库、编译、生成日志，再突然删除整个环境。传统服务常见的“稳定热点数据”假设不一定成立：

- 镜像层适合只读共享，工作层需要租户隔离。
- 临时块设备追求快速创建与销毁，共享卷追求并发访问与一致性。
- 快照要记录磁盘状态与运行时状态的对应关系，不能把两个时间点拼在一起。
- 删除 API 成功不等于所有副本、缓存和备份中的敏感数据立即消失。
- 某个 Agent 的日志洪水不能耗尽整台宿主机的 inode 或写回带宽。

DeepSeek 已公开的 3FS 是面向 AI 训练与推理负载的分布式文件系统，可用于理解解耦存储、强一致性、元数据服务和高带宽共享存储；但不能据此推断 DSec 的临时块设备或共享卷一定采用 3FS。

## 6. 典型失败路径

一个常见事故链是：某任务产生海量小日志，页缓存迅速变脏，内核开始节流写入；同机其他沙箱的文件操作被拖慢，心跳超时，控制面误判节点失联并触发迁移，进一步增加读写压力。

修复不能只“加大超时”，而应同时考虑：每租户字节与 inode 配额、日志限速与批处理、独立 I/O cgroup、脏页与设备指标、心跳和数据面负载隔离，以及过载时停止接收新任务。

## 7. DeepSeek Agent Infra 面试怎么问

**题目：请从 `write()` 一直讲到数据落盘。**

**30 秒答法：**普通 buffered write 会从用户缓冲区经系统调用进入 VFS 和具体文件系统，数据通常先进入页缓存成为脏页；writeback 再通过块层、驱动和设备队列把它写到控制器与持久介质。`write` 成功不等于掉电安全，需要按恢复语义使用 `fdatasync`、`fsync`，创建或重命名文件时还可能同步父目录。定位瓶颈要把应用、页缓存、文件系统、块层、设备及远端副本分别观测。

可能继续追问：

1. 为什么每条日志 `fsync` 会让吞吐骤降？怎样批处理又控制丢失窗口？
2. `mmap` 写、buffered I/O、direct I/O 的路径有何不同？
3. 共享卷增加了哪些确认点？副本 quorum 如何改变延迟？
4. 如果 p99 突然升高，你会按什么顺序收集证据？

## 8. 本章速记

- `write` 成功、可见、原子和持久是四件事。
- 先画用户态、内核、页缓存、块层、设备；远端存储再加网络与副本。
- 小写入的瓶颈常是 IOPS 与同步次数，不只是字节吞吐。
- 任何优化都要绑定崩溃恢复语义。
- Agent 沙箱要隔离容量、inode、I/O 带宽和日志洪水。
