# 容器、用户态内核与 microVM：隔离不是二选一

> 难度：必会。JD 明确要求大规模 VM、容器隔离与多样操作系统环境；具体产品名属于备考方案，不是官方内部选型事实。

把宿主机想成一栋公寓。普通容器像共用楼体和物业系统的独立房间；虚拟机像在楼内再建一套有自己物业的小楼；用户态内核则像在房门内增加一层翻译与门卫。三者都能隔开住户，但成本、兼容性和攻击面不同。

## 1. 容器到底隔离了什么

容器通常由多种 Linux 机制组合而成：

- namespace 改变进程“能看见什么”，例如 PID、mount、network、IPC、UTS、user。
- cgroup 规定进程“最多能用多少”，例如 CPU、内存、I/O 和进程数。
- capability 把 root 权限拆小。
- seccomp 过滤系统调用。
- LSM（如 SELinux、AppArmor）限制对象访问。
- OCI runtime 负责按规范创建进程、挂载与 namespace。

容器里的进程仍直接调用宿主机内核。镜像不是安全边界，Kubernetes namespace 也不是 Linux namespace；前者主要组织 API 对象，不能替代运行时隔离。

## 2. VM 增加了哪一层

VM 中，工作负载调用自己的 guest kernel，再通过虚拟设备和 hypervisor/VMM 访问宿主资源。硬件虚拟化提供了更清晰的内核边界，也能运行不同内核或操作系统。

microVM 仍然是 VM，只是刻意减少虚拟设备和传统 BIOS 等通用功能，以缩小启动成本和攻击面。Firecracker 是公开的典型实现：它使用 KVM，目标是安全、多租户、低开销的 serverless 工作负载。这里把它作为学习案例，不代表 DSec 的实现。

## 3. 用户态内核位于中间地带

gVisor 通过 Sentry 在用户态实现 Linux 风格的系统接口，让大量系统调用不直接进入宿主内核；`runsc` 又保持 OCI 运行时接口。它不等同于 VM，也不只是 syscall allowlist。

代价是兼容性与性能需要按负载验证。gVisor 官方生产指南明确提醒文件 I/O 和网络往往受影响较大。对编译、包管理、海量小文件等 Agent 负载，这正是必须实测的部分。

## 4. 面试决策矩阵

| 维度 | 普通容器 | 用户态内核 | microVM |
|---|---|---|---|
| 内核边界 | 共享宿主内核 | 多数接口由用户态内核处理 | 独立 guest kernel |
| 启动与密度 | 通常最好 | 居中，依实现而定 | 通常成本更高，可用快照优化 |
| Linux 兼容性 | 高 | 需验证 syscall、文件与网络行为 | guest 支持范围内高 |
| 异构 OS | 很弱 | 主要是 Linux 接口 | 强 |
| 攻击面 | 宿主内核接口较大 | 宿主接口被明显收窄 | VMM、虚拟设备与宿主层 |
| 运维复杂度 | 较低 | 中等 | 镜像、内核、快照与网络更复杂 |
| 适用示例 | 可信内部批任务 | 不可信 Linux 用户代码 | 强隔离、异构内核、高风险任务 |

实际平台可以分层：低风险、短任务使用高密度运行时；涉及未知二进制、内核特性或更强租户边界的任务使用 microVM；极高风险操作直接拒绝或要求专用节点。

## 5. 快照与冷启动

快照像暂停一间已经整理好的房间，下一位租户从这个状态恢复。它可以绕过重复引导和依赖初始化，但会引入新的正确性问题：

- 恢复后的机器 ID、随机数状态、网络身份和凭证必须唯一或刷新。
- 内存快照与磁盘快照必须来自一致时间点。
- 基础镜像升级后，旧快照如何失效？
- 快照是否含前一个租户的秘密或缓存？
- 恢复失败时能否退回冷启动，而不是无限重试？

假设冷启动 800 ms、快照恢复 80 ms，每秒新建 2,000 个沙箱，则仅启动等待时间对应的并发在稳态分别约为 `2000 × 0.8 = 1600` 与 `2000 × 0.08 = 160`。这是 Little's Law 的教学估算，不是任何产品的真实性能数据。

## 6. 资源隔离不等于安全隔离

只限制内存而不限制进程数，fork bomb 仍可耗尽 PID；只限制 CPU 配额而不控制 I/O，写回洪水仍会干扰邻居；只分 network namespace 而不设出口策略，沙箱仍能访问不该访问的网络。

反过来，强安全边界也不自动提供公平性。microVM 仍需 CPU、内存、I/O 与网络调度，还要防止宿主级缓存、NUMA 和共享设备上的 noisy neighbor。

## 7. 典型失败路径

平台从一个“干净快照”批量恢复 VM，但忘记刷新其中的短期访问令牌和实例身份。数百个实例带着同一身份访问制品服务，审计无法区分来源，令牌吊销又同时击穿全部任务。

正确做法是把身份视为恢复后的注入项：启动时通过受控通道获取按 run 绑定、短有效期的凭证，并在快照制作流程中扫描和禁止秘密。

## 8. DeepSeek Agent Infra 面试怎么问

**题目：为什么不全部用容器，或者全部用 VM？**

**30 秒答法：**普通容器密度高、兼容性好，但工作负载直接共享宿主内核；VM 用 guest kernel 和硬件虚拟化加强边界并支持异构 OS，不过启动、内存和运维成本通常更高；gVisor 一类用户态内核处于中间位置，收窄宿主系统接口但需要验证兼容性及 I/O、网络开销。我会根据代码可信度、所需内核能力、租户风险和 SLO 分级选型，并用相同真实 Agent 工作负载测启动、密度、p99、逃逸面和故障恢复，而不是只看单项基准。

可能追问：

1. namespace、cgroup、capability、seccomp 各解决什么问题？
2. microVM 快照恢复时哪些状态必须重置？
3. 怎样做运行时灰度升级和快速回滚？
4. 如何设计一个既衡量性能又覆盖安全的对比实验？

## 9. 本章速记

- namespace 管可见性，cgroup 管资源；两者都不是完整沙箱。
- 容器共享宿主内核，VM 有 guest kernel，用户态内核重实现部分系统接口。
- 隔离强度、兼容性、启动、密度和运维要一起权衡。
- 快照优化冷启动，也会复制身份、随机状态和秘密风险。
- 具体运行时是方案推断，不是 DeepSeek JD 明示事实。
