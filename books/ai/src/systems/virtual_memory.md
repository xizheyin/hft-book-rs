# Agent 的内存隔离与容量

一个 Agent 沙箱“最多可用 4 GiB”不等于它始终占用 4 GiB，也不等于一台 256 GiB 的机器一定能稳定运行 64 个沙箱。任务会有峰值，共享页会影响统计，内存回收还会先让延迟变差，最后才可能发生 OOM。

本章回答：**平台怎样限制一个沙箱的内存，又怎样估算一台机器能安全承载多少任务？**

如果虚拟地址、物理页、缺页或 Copy-on-Write 还不熟悉，先读第一册的[虚拟内存](../../rust-hft/foundations/virtual_memory.html)。这里不重复页表结构，只讨论 Agent 平台需要做的资源决策。

## 1. 先分清五个量

| 名称 | 它是什么 | 为什么在 Agent 场景需要它 |
|---|---|---|
| request | 调度器为任务预留的预计内存 | 用来选择节点，不是强制上限 |
| limit | 系统允许任务使用的最大内存 | 防止单个任务无限增长 |
| RSS | 当前驻留在物理内存中的进程页面总量 | 能看到实际驻留，但共享页可能在多个进程中重复计算 |
| PSS | 把共享页按共享者数量分摊后的估算 | 比简单相加 RSS 更适合估算多进程合计占用 |
| working set | 最近持续被任务使用、很难回收的那部分内存 | 更接近任务稳定运行真正需要的容量 |

request、limit 和实际用量解决三个不同问题：**放到哪里、最多允许多少、真实用了多少**。把它们设成同一个数字通常既浪费容量，也无法吸收峰值。

## 2. cgroup 提供什么边界

cgroup 是 Linux 对一组进程进行资源记账和限制的机制。Agent 平台把整棵沙箱进程树放进同一个 cgroup，才能覆盖子进程，而不是只限制入口进程。

内存控制至少要理解三种信号：

- 当前记账值说明边界内大约正在使用多少内存；
- 压力阈值可以提前触发回收或节流，告诉平台任务正在挤压资源；
- 硬上限无法满足时可能触发 cgroup 范围内的 OOM 处理。

OOM 是 Out Of Memory，表示系统已经无法在既定边界内满足必要内存分配。它不是正常的流量控制手段。健康平台应在持续压力和延迟恶化阶段就限制新任务，而不是等 OOM 杀进程后才行动。

## 3. 为什么只看 RSS 会算错

假设 100 个沙箱都加载同一份 200 MiB 只读运行时文件，并各自使用 300 MiB 私有内存。每个进程的 RSS 可能都包含那 200 MiB 共享页：

```text
简单相加 RSS ≈ 100 × (200 + 300) MiB = 50,000 MiB
更接近物理占用的粗略值 ≈ 200 + 100 × 300 MiB = 30,200 MiB
```

第二个数仍不是容量结论，因为还缺少内核内存、页缓存、峰值、内存碎片和宿主机安全余量。这个例子只说明：共享页存在时，简单相加 RSS 会重复计算；PSS 能提供更合适的分摊视角。

反过来，只看 PSS 也不够。容量设计还需要关注随时间变化的 working set 和高分位峰值，否则平均值会掩盖少量超大任务。

## 4. 快照与 COW 为什么先省、后涨

快照保存某个时刻可恢复的运行状态。多个沙箱从同一快照启动时，可以先共享相同页面；当某个沙箱修改页面时，Copy-on-Write（COW，写时复制）再为它创建私有副本。

这会产生一个重要容量曲线：

```text
刚恢复：共享页多，物理占用较低
开始执行：发生缺页并载入工作集
持续写入：COW 共享逐渐被打破，私有页增加
集中恢复：许多沙箱同时缺页，可能形成内存和存储突发
```

所以“快照大小”不能直接当作“每个恢复任务的内存成本”。平台必须测量恢复后不同时间点的 PSS、working set、缺页和延迟。

## 5. noisy neighbor 怎样出现

noisy neighbor 指共享宿主机上的一个工作负载占用过多共享资源，导致其他工作负载变慢。即使每个沙箱都有硬上限，邻居影响仍可能通过以下路径发生：

- 大量首次访问触发缺页，争用内存带宽和存储；
- 一个任务扫描大量文件，把其他任务需要的页缓存挤出；
- 持续内存压力触发全机回收，让多个任务一起停顿；
- 多个任务同时恢复快照，造成突发而非稳定负载。

隔离上限防止“无限使用”，但不能保证“性能完全互不影响”。因此调度器还要看节点整体压力，并保留安全余量。

## 6. 从容量估算到准入控制

准入控制是“系统决定是否现在接收新任务”的机制。它存在的原因是：过载时继续接收任务只会让排队、回收和超时互相放大。

一个初始估算可以写成：

```text
可用于沙箱的内存 = 机器总内存 - 操作系统预留 - 平台预留 - 故障余量
初始并发上限 ≈ 可用于沙箱的内存 / 单任务高分位 working set
```

这里使用高分位而不是平均值，是为了覆盖大多数真实峰值；具体选择 p95 还是 p99 要根据任务是否允许排队、是否可驱逐以及服务目标决定。

上线后还要用反馈修正：

1. 按任务类型记录 request、峰值 RSS/PSS、working set、结果和 OOM。
2. 比较预测与实际，找出经常低估的任务类型。
3. 当节点内存压力持续升高时暂停准入，而不是继续装箱。
4. 对可重试任务做安全驱逐；对不可重试任务优先保护。
5. 将 OOM、回收和延迟一起分析，不能只统计“机器还剩多少 GiB”。

## 7. OOM 后怎样恢复

进程因 OOM 退出时，平台至少要记录：run、attempt、节点、内存 limit、峰值、发生时间和已完成步骤。attempt 表示同一个 run 的一次具体执行尝试；区分二者，才能在重试时保留历史证据。

随后根据副作用语义决定：

- 纯计算且输入可重放：可以提高资源申请或换节点重试；
- 已写 checkpoint：从最近一致 checkpoint 恢复；
- 外部工具可能已成功：先用 operation ID 查询结果，再决定是否重试；
- 连续多次超限：停止自动重试，避免 OOM 风暴。

OOM 不应只显示成“退出码异常”。它是容量预测、资源边界或输入异常中的至少一个需要修正的信号。

## 8. 常见误区

1. **“虚拟地址空间很大，所以已经占用同样多 RAM。”** 地址范围和已驻留物理页不是一回事。
2. **“所有进程 RSS 相加就是机器用量。”** 共享页会被重复计算。
3. **“设置 limit 后沙箱性能互不影响。”** 内存带宽、页缓存和回收仍然共享。
4. **“快照能让每个实例永远共享内存。”** 写入会通过 COW 逐步产生私有页。
5. **“OOM 后无限重试即可。”** 相同资源条件会重复失败并放大压力。

## 9. 30 秒面试答案

> 我会区分调度 request、强制 limit 和真实 working set。整棵沙箱进程树进入同一 cgroup，平台持续记录 RSS/PSS、working set、压力事件和 OOM。容量不能简单用总内存除以 limit，因为共享页、COW、峰值和集中恢复都会改变实际占用。我会用单任务高分位 working set 加宿主机余量做初始装箱，并在持续内存压力时停止准入。OOM 后按 run 和 attempt 保存证据，再依据 checkpoint 与外部副作用决定是否安全重试。

## 本章小结

- 内存调度、强制边界和实际用量需要不同指标。
- RSS、PSS 与 working set 的统计语义不同，不能混用。
- 快照和 COW 延迟复制成本，但不会消灭后续私有写入。
- cgroup 限制单个边界，节点级压力仍会影响邻居。
- 容量设计需要高分位工作集、安全余量和准入控制。
