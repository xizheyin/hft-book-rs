# Agent 的数据库、WAL 与可恢复状态

worker 完成了工具调用，却在写回任务状态前崩溃。调度器只看到 `RUNNING`，不知道该重试、继续等待，还是先查询工具结果。这个问题的中心不是磁盘型号，而是：**哪些状态是权威事实，哪些写入已经持久化，重启后如何恢复到一个可解释的状态。**

如果文件、页缓存、`write()` 和 `fsync()` 还不熟悉，先读第一册的[一次文件写入](../../rust-hft/foundations/file_write_path.html)。本章不再展开文件系统内部结构或设备队列，只讨论 Agent 控制状态需要的数据库语义。

## 1. 先给状态分类

| 状态 | 例子 | 需要怎样保存 |
|---|---|---|
| 权威控制状态 | task 当前状态、有效 attempt、lease epoch | 必须可持久恢复，并由明确事务更新 |
| 可重建状态 | 缓存、派生索引、临时统计 | 丢失后可以从权威状态重新生成 |
| 大对象 | checkpoint、模型输出、构建产物 | 通常放对象存储，数据库保存引用、大小和校验值 |
| 外部副作用 | 邮件、支付、第三方工单 | 不一定由本地数据库控制，需要 operation ID 和对账 |

**权威状态**是其他组件发生争议时最终相信的记录。系统必须明确只有一个权威来源；同时把数据库、缓存和队列都叫“真相”会让恢复逻辑互相矛盾。

## 2. WAL 是什么，为什么需要它

WAL 是 Write-Ahead Log，中文常译为预写日志。数据库先把“准备怎样修改”按顺序写入可恢复日志，再把修改逐步应用到数据页。

它存在的原因是数据库一次事务可能修改多个位置。如果机器在只写完一部分时崩溃，WAL 让数据库重启后能够重做已提交修改，或忽略未提交修改，而不是留下无法解释的半成品。

可以用下面的心智模型理解：

```text
事务产生修改
→ 追加 WAL 记录
→ WAL 达到数据库承诺的持久边界
→ 返回提交成功
→ 数据页可以稍后刷新
→ 重启时根据 WAL 恢复
```

这里的“提交成功”以数据库和存储配置实际承诺为准。应用不能把一次普通文件 `write()` 返回自行解释成数据库事务已经断电安全。

## 3. 事务保护业务不变量

事务把一组数据库操作视为一个提交单位。Agent 控制面使用事务，不是为了展示数据库名词，而是为了保护业务不变量。

例如领取任务时应一起完成：

```text
确认 task 仍为 PENDING
创建新的 attempt
写入 owner 与 lease epoch
把 task 改为 RUNNING
```

如果这些步骤分成多个独立提交，崩溃可能留下 `RUNNING` 但没有 owner，或者已经有 attempt 但 task 仍显示 `PENDING`。事务让其他读者看到修改前或修改后的完整状态，而不是中间组合。

事务的隔离级别决定并发事务能看到什么。面试阶段不必背所有数据库的级别差异，但要能先说出需要保护的不变量，再选择条件更新、唯一约束或更强隔离来保证它。

## 4. 状态机让恢复有依据

状态机明确哪些状态转换合法。例如：

```text
PENDING → STARTING → RUNNING → SUCCEEDED
                    ├────────→ FAILED
                    └────────→ CANCELLING → CANCELLED
                                      └──→ UNKNOWN
```

每次转换还应保存：

- task 和 attempt 标识；
- 旧状态与新状态；
- 触发原因和操作者；
- 时间、版本号或 epoch；
- 关联的 checkpoint、产物和 operation ID。

版本号让更新可以带条件：“只有我读到的版本仍是当前版本时才写入”。这样旧 worker 不能覆盖新 attempt 的结果。

## 5. checkpoint 到底承诺什么

checkpoint 是任务运行中的一个可恢复保存点。它不只是一个文件，还需要描述这个文件对应的执行位置和外部状态。

一个可用 checkpoint 至少包含：

- checkpoint ID 与所属 attempt；
- 数据对象的位置、大小和校验值；
- 代码、模型、依赖和配置版本；
- 已完成到哪个 step 或事件序号；
- 哪些外部副作用已经确认；
- 创建是否完整，能否被恢复程序读取。

安全发布通常采用“先写内容，验证完整，再原子地把元数据指针切到新版本”。这样崩溃发生在内容上传中时，旧 checkpoint 仍然有效；只有新内容验证成功后，读者才会发现它。

checkpoint 与数据库事务往往跨越两种存储，无法靠一个本地事务同时提交。平台需要显式的中间状态和后台对账，而不是假装两个写入永远一起成功。

## 6. Outbox 解决“状态已改，消息没发”

假设数据库把 task 改成 `SUCCEEDED` 后，进程在向消息队列发布事件前崩溃。下游永远收不到通知。

Outbox 模式把“业务状态更新”和“待发布事件”写入同一个数据库事务。后台发布器读取 outbox 发送消息，成功后标记已发送。这样崩溃后仍能继续发布。

队列可能重复投递，所以消费者仍需用事件 ID 去重。Outbox 提供的是“不会因提交与发送之间崩溃而永久漏消息”，不是自动的全世界 exactly-once。

## 7. 重启后的恢复流程

控制面重启或 worker 失联后，可以按以下顺序恢复：

1. 数据库先用 WAL 完成自身恢复，得到已提交的权威状态。
2. 找出 lease 已过期或长时间停在中间状态的 attempt。
3. 查询沙箱、对象存储和外部工具，收集实际证据。
4. 完整 checkpoint 可继续使用；未发布完整的临时对象可延迟清理。
5. 确认可重放的任务创建新 attempt；结果不确定的任务进入 `UNKNOWN` 并对账。
6. 重放未发送 outbox 事件，消费者按事件 ID 去重。

恢复程序必须可以反复运行。它在中途再次崩溃时，下一次执行仍应得到相同或继续前进的结果；这种性质就是幂等。

## 8. 持久化不等于业务完成

需要区分四个完成点：

1. 应用把数据交给客户端库；
2. 数据库事务提交成功；
3. checkpoint 内容和元数据达到各自承诺的持久边界；
4. 用户能观察到完整、可恢复的业务结果。

例如数据库已经写入 `SUCCEEDED`，但结果对象随后校验失败，业务仍不完整。因此状态转换应在验证结果可读后发生，或使用 `FINALIZING` 一类中间状态表示还在完成发布。

## 9. 常见误区

1. **“数据库提交就是所有外部操作一起提交。”** 第三方 API 和对象存储通常不在同一事务内。
2. **“WAL 是一份完整数据库备份。”** WAL 记录恢复所需变化，不替代独立备份和恢复演练。
3. **“checkpoint 文件存在就能恢复。”** 还要有完整标记、版本、校验值和执行位置。
4. **“队列会保证消息只来一次。”** 崩溃恢复常会造成重复投递，消费者仍需去重。
5. **“失败任务直接重试即可。”** 外部副作用结果不确定时应先查询和对账。

## 10. 30 秒面试答案

> 我先划分权威控制状态、可重建缓存、大对象和外部副作用。任务领取和状态转换在数据库事务中保护不变量，WAL 让已提交事务能在崩溃后恢复。checkpoint 由内容、校验值、版本和执行位置共同组成，先写并验证内容，再发布元数据指针。数据库更新与消息发送之间用 outbox，消费者按事件 ID 去重。重启后以数据库为权威来源，对账沙箱、对象存储和外部工具；无法确认的结果进入 UNKNOWN，而不是盲目重试。

## 本章小结

- 先定义权威来源，才能设计一致的恢复流程。
- WAL 和事务让数据库从崩溃中恢复，并保护业务不变量。
- checkpoint 必须包含内容完整性、版本和执行位置。
- 跨存储操作需要中间状态、Outbox、幂等和对账。
- 持久化、发布和用户可见的业务完成是不同阶段。
