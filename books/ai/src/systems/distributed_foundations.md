# Agent 控制面的分布式系统基础

一台机器上的函数调用要么返回，要么进程崩溃；跨机器调用还会出现更难判断的情况：调用方超时了，服务端却可能已经完成。Agent 控制面由 API、调度器、worker、数据库和对象存储共同组成，因此必须面对“各组件看到的事实不完全相同”。

本章回答高频系统设计问题：**在消息可能延迟、节点可能失联的情况下，怎样决定当前 owner、保存一致状态，并从不确定结果中恢复。**

## 1. 分布式系统难在哪里

分布式系统是由多台通过网络通信的机器共同提供一个服务。网络没有提供一个“立刻告诉所有人真相”的按钮，所以会出现 **部分失败**：系统的一部分正常，另一部分失败或暂时无法联系。

一次 RPC 超时至少有三种可能：

1. 请求没有到达服务端；
2. 服务端收到并执行了，但响应没有回来；
3. 服务端仍在执行，只是超过调用方的等待时间。

因此超时只证明“调用方没有按时得到回答”，不证明操作没有发生。Agent 平台需要 request ID、attempt ID 和 operation ID，分别识别用户请求、执行尝试和外部副作用。

## 2. 时间不能直接充当真相

不同机器的日历时钟会有误差，也可能在校时后发生跳变。日志时间戳适合帮助排查，却不能单独证明两个跨机器事件的因果顺序。

工程上先记两种时间用途：

- **wall clock** 表示日历时间，用于展示“事情发生在几点”；
- **monotonic clock** 只要求在本机持续向前，更适合测量“经过了多久”和计算 timeout。

跨服务顺序应优先依靠数据库版本、消息序号、attempt 或递增 epoch，而不是比较两台机器的日志毫秒数。

## 3. 先定义一致性承诺

一致性描述“客户端能观察到怎样的读写结果”，不是一个笼统的开关。

- **线性一致性**：一次写成功返回后，之后开始的读取都应看到它或更新的值。它适合当前 task owner、余额等不能读旧值的对象。
- **最终一致性**：停止新写且系统恢复通信后，各副本最终收敛。它适合允许短时间陈旧的统计和缓存。

更强的一致性通常需要更多同步，可能增加跨区域延迟；更弱的一致性减少协调，却把冲突处理交给应用。选择时应先说用户能否接受旧数据，再谈数据库或缓存产品。

## 4. 复制提高容错，也引入新状态

复制是把同一份数据保存在多个故障域。故障域是“可能被同一个故障一起影响的一组资源”，例如同一台机器或同一个机房。把副本放到不同故障域，可以在一处故障后继续服务，但也会产生落后副本、并发写冲突和恢复追赶。

多数派写入的直觉是：只让超过半数副本确认的决定生效，那么任意两个多数集合至少有一个共同成员。这个交集有助于保留已确认决定，但**仅有多数数字还不够**；系统仍需定义谁能写、日志顺序、版本比较和读取规则。

同步复制等待更多副本确认，承诺更清晰但写入更慢；异步复制先向客户端返回，延迟更低，却存在主副本故障后丢失最新确认状态的窗口。面试答案应把选择与允许的数据丢失和恢复时间联系起来。

## 5. 共识解决“采用哪一个决定”

共识协议让多台可能故障的机器对一串决定达成一致。Raft 是常见例子，它使用：

- leader：当前接收并排序命令的节点；
- term：一次领导任期的递增编号；
- log：所有节点按相同顺序复制的命令记录；
- majority：足够多节点确认后，命令才能成为已提交决定。

最小路径是：

```text
客户端命令
→ leader 追加日志
→ 复制到多数节点
→ 标记 committed
→ 各节点按相同顺序应用到状态机
```

面试中不必背选举超时公式或日志边界条件，但必须说清它**没有**解决什么：Raft 决定命令顺序，不会自动让支付接口幂等，也不会自动阻止旧 worker 操作共享存储。

## 6. lease 与 fencing 防止旧 owner 写入

调度器给 worker 的临时所有权通常称为 lease。lease 到期后，调度器可以把任务交给新 worker；但旧 worker 可能只是暂停，恢复后仍以为自己有权写。

fencing token 是单调递增的授权编号：

```text
worker A 获得 epoch 41
lease 到期后，worker B 获得 epoch 42
存储只接受 epoch ≥ 42 的写
worker A 恢复并提交 41 → 被拒绝
```

lease 让平台能够重新分配，fencing 让资源端拒绝旧 owner。两者缺一，就可能出现两个 worker 同时推进同一 task 的“脑裂”。

## 7. 网络分区时必须选择行为

网络分区表示一些节点之间暂时无法通信。此时系统不能同时对所有请求承诺“永远返回成功”以及“永远读写同一个最新值”。这就是 CAP 讨论的实际问题。

不要背“任意三选二”。面试时应对具体操作说明：

- task owner 变更：无法联系多数派时拒绝写，保护单一 owner；
- 只读历史日志：可以返回带版本和时间的旧数据；
- 新任务提交：可以暂存或明确失败，但不能谎报已经调度；
- 外部副作用：结果未知时进入 `UNKNOWN`，恢复后对账。

正确答案不是所有操作都选同一侧，而是每类数据有明确的失败语义。

## 8. 跨服务事务为什么困难

本地数据库事务可以原子更新多行数据，但数据库和第三方 API 通常不能共享同一个提交点。跨服务设计常用：

| 方法 | 它是什么 | 适合什么问题 |
|---|---|---|
| 幂等键 | 同一业务意图使用稳定 ID | 防止超时重试重复产生副作用 |
| Outbox | 业务更新与待发布事件写入同一数据库事务 | 防止状态已提交但事件永久漏发 |
| Saga | 长流程拆成多个步骤，并为可补偿步骤定义反向业务动作 | 处理无法一次原子提交的长事务 |
| 对账 | 定期比较两个系统的权威记录 | 修复未知结果和长期漂移 |

Two-Phase Commit（两阶段提交）让多个支持事务协议的参与者先准备、再统一提交，但会引入协调状态和阻塞恢复，而且无法把任意外部 HTTP 操作自动纳入事务。面试阶段理解这个取舍即可，不需要背数据库命令。

补偿也不是时间倒流。退款无法让用户忘记已经看到的扣款通知，所以 Saga 必须把补偿失败和人工处理当作正常状态。

## 9. 分片解决容量，也制造热点

分片是按照 key 把数据分给不同存储组；key 是用来定位一条记录的标识，例如 task ID。分片让系统超出单机容量，但跨分片查询、事务和再平衡会更复杂。

Agent 平台选择分片键时要从访问模式出发：

- 只按 `tenant_id` 分片，超大租户可能压满一个分片；
- 只按随机 task ID 分片，查询某租户全部任务可能访问所有分片；
- 组合键或大租户单独拆分能折中，但路由规则必须版本化。

迁移分片时，旧 owner 和新 owner 可能同时存在，所以路由版本与 fencing 仍然需要。不要把“数据复制完成”误认为“写权限已经安全切换”。

## 10. 一个 Agent 控制面恢复流程

worker 与调度器失联后，平台可以这样处理：

1. 到达 deadline 前不从一次心跳缺失直接断言 worker 已死。
2. lease 到期后，由共识或强一致存储创建更高 epoch 的新 attempt。
3. checkpoint 存储只接受新 epoch 后续写入。
4. 新 worker 从最后一个完整 checkpoint 恢复。
5. 对每个外部 operation ID 查询结果，避免重复执行。
6. 后台对账残留沙箱、对象和 task 状态。

这个流程把“重新获得推进权”“恢复本地计算”和“确认外部副作用”分成三件事，因此每一步都能独立验证。

## 11. 常见误区

1. **“超时等于失败。”** 它只表示调用方没有及时收到结果。
2. **“时间戳更大就一定后发生。”** 不同机器的时钟不能直接提供因果顺序。
3. **“有三个副本就不会丢数据。”** 还要看同步方式、确认规则和故障域。
4. **“用了 Raft 就不会重复执行。”** 共识日志与业务副作用是两层问题。
5. **“lease 过期后旧 worker 自动消失。”** 资源端还需要 fencing token。
6. **“CAP 是产品永久三选二。”** 真正问题是分区时每类操作选择拒绝、等待还是返回旧值。
7. **“Saga 能无损回滚世界。”** 补偿本身也会失败，外部观察不能抹除。

## 12. 30 秒面试答案

> 分布式系统首先面对部分失败：超时不证明操作没发生，跨机器日志时间也不天然给出因果顺序。我会先为每类数据定义线性一致或允许陈旧的承诺，再选择同步复制或共识。Agent 所有权用 lease 允许重新分配，同时用递增 fencing token 让存储拒绝旧 worker。跨服务副作用用 operation ID、Outbox、Saga 和对账处理。网络分区时，我会逐类说明哪些写入拒绝、哪些读取可降级，而不是只背 CAP 三选二。

## 本章小结

- 部分失败让结果可能不确定，系统必须保留可查询身份。
- 一致性是客户端观察承诺，选择必须绑定业务需要。
- 复制和共识维护决定，但不能替代业务幂等。
- lease 负责重新分配，fencing 负责拒绝旧 owner。
- 跨服务恢复依靠状态机、幂等、Outbox、补偿和对账。
