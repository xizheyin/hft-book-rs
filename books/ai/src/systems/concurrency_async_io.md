# Agent 任务的领取、取消与背压

两个 worker 同时看到任务状态是 `PENDING`，随后都开始执行。每一行代码单独看都没有错误，任务却产生了两次外部副作用。这个问题不是“线程语法”问题，而是平台没有定义谁拥有任务、何时失去所有权，以及过载时谁应该等待。

本章回答三个 Agent 平台高频问题：**如何只让一个有效 owner 推进任务，如何让取消有明确边界，以及如何在处理不过来时停止继续堆积。**

锁、原子操作、异步 I/O、futex、epoll、io_uring 和 Tokio 的通用机制见系统子书的[并发基础](../../rust-hft/foundations/concurrency.html)、[异步 Rust](../../rust-hft/foundations/async_rust.html)和[网络 I/O 模型](../../rust-hft/network/io_models.html)。本章只增加任务所有权、取消与平台背压协议。

## 1. 先定义业务对象

- **task**：等待平台完成的一项业务工作。
- **attempt**：同一 task 的一次具体执行尝试。失败重试会产生新的 attempt。
- **worker**：领取并执行 attempt 的进程或服务实例。
- **queue**：保存等待任务的有序或带优先级集合。
- **不变量**：系统无论怎样并发都必须成立的规则，例如“同一时刻最多一个有效 owner 可以提交结果”。

并发表示多个任务的执行时间重叠，它们的步骤可能交错。问题的核心不是“用了几条线程”，而是交错后业务不变量是否仍然成立。

## 2. “先查再改”为什么会重复领取

下面两步如果分开执行，就存在空隙：

```text
1. 查询 task 是否为 PENDING
2. 如果是，把状态改为 RUNNING
```

两个 worker 都可能在第 1 步读到 `PENDING`，然后各自通过第 2 步。正确做法是让“检查条件并修改”成为一个不可分割的数据库操作：

```sql
UPDATE tasks
SET state = 'RUNNING', owner = :worker, attempt = attempt + 1
WHERE id = :task_id AND state = 'PENDING';
```

只有受影响行数为 1 的 worker 领取成功。这里的“原子”是业务语义：其他并发操作不能观察到检查和修改之间的半成品；它不要求应用自己实现 CPU 原子指令。

队列可能重复投递消息，所以“收到消息”也不等于“获得所有权”。worker 必须以权威状态存储中的条件更新结果为准。

## 3. 长任务为什么需要 lease

如果 worker 运行数小时后失联，平台不能永远等待；但网络短暂变慢也不能证明 worker 已经死亡。常见做法是给所有权设置 **lease**，也就是带到期时间的临时授权。

一个简化流程是：

1. worker 原子领取 task，并获得递增的 attempt 或 epoch。
2. worker 在仍健康时定期续租。
3. lease 过期后，调度器可以创建新 attempt。
4. 提交结果时，存储只接受当前有效 attempt；旧 worker 即使恢复也不能覆盖新结果。

第 4 步使用的是 fencing 思想：资源端用单调递增的编号拒绝旧 owner。只设置过期时间而不校验编号，会让暂停很久的旧 worker 恢复后继续写入。

这里的 epoch 是“第几代所有权”的编号。每次重新分配都增大，所以资源端能够区分当前 owner 与过期 owner。

lease 解决“谁现在有权推进”，不解决“外部支付是否已执行”。外部副作用仍需要幂等键和结果查询。

## 4. 取消是一种协议

取消不是瞬间删除任务，而是多个组件共同停止推进的协议：

```mermaid
flowchart LR
    A["收到取消"] --> B["状态改为 CANCELLING"]
    B --> C["不再派发新步骤"]
    C --> D["通知正在运行的 worker"]
    D --> E["停止本地进程树"]
    E --> F["释放许可与临时资源"]
    F --> G["确认外部副作用"]
    G --> H["CANCELLED 或 UNKNOWN"]
```

`CANCELLED` 应表示平台已经完成约定的停止和清理；如果外部操作结果未知，就应进入 `UNKNOWN`，不能为了状态好看而谎报取消成功。

structured concurrency（结构化并发）是一种组织任务生命周期的方法：子任务不能在父任务结束后无边界地继续存活，父任务负责等待或取消它们。这里需要它，是为了让 run 结束时能证明没有遗留的异步读取者、定时器或子任务。

## 5. deadline 怎样向下传递

deadline 是端到端操作最晚完成的时刻。每一层都应接收同一个 deadline，并用“deadline 减当前时间”得到剩余预算。

假设用户只愿等 30 秒：

```text
调度排队 4 秒后，剩余 26 秒
沙箱启动 6 秒后，剩余 20 秒
工具调用最多只能从这 20 秒中继续分配
```

如果调度器、沙箱和工具服务各自重新设置 30 秒 timeout，用户等待时间就会被无意放大。清理过程可以有独立的内部上限，但它不能阻止 API 按约定返回，也不能变成无限后台任务。

取消只表示“不要再推进”，不表示已经发出的请求没有生效。因此异步任务对象被丢弃、线程停止或进程被杀，都不能代替业务对账。

## 6. 背压让慢消费者能够拒绝

背压是下游把“我处理不过来”传回上游的机制。假设每秒进入 100 个任务，worker 每秒只能完成 80 个：

```text
每秒积压 20 个
一分钟积压 20 × 60 = 1,200 个
```

无界队列没有增加处理能力，只是推迟失败，并让等待中的任务先消耗内存和 deadline。Agent 平台通常组合使用：

- **有界队列**：达到上限后拒绝或延后新任务；
- **并发许可**：限制同时运行的沙箱或工具调用数量；
- **每租户配额**：避免一个用户占满全部容量；
- **准入控制**：依据 CPU、内存和队列年龄决定是否接收新任务；
- **明确的过载响应**：告诉调用方何时可重试，而不是让所有请求一起超时。

队列长度还不够。平台应同时看最老任务等待时间，因为 100 个 10 毫秒任务和 100 个 10 分钟任务占用的是完全不同的未来容量。

## 7. 异步在这里解决什么

异步允许少量线程同时等待许多网络和文件事件，适合 Agent 平台大量“等待工具响应”的工作。它不让 CPU 计算自动变快，也不提供业务层 exactly-once。

应用层只需记住三条边界：

1. CPU 密集或不受控的阻塞调用要放入受限线程池或独立进程，不能堵住事件循环。
2. 每个异步任务必须有 owner、deadline 和清理路径。
3. channel 和 semaphore 都应有容量上限；“异步发送”不代表队列可以无限增长。

底层该选 epoll、io_uring 还是某个 runtime，是测量和工程生态问题，不是本章面试答案的中心。

## 8. 一个最小正确方案

一次任务执行可以采用下面的协议：

1. API 写入 task 和幂等键；重复请求返回同一 task。
2. 调度器通过条件更新创建 attempt，并发放带 epoch 的 lease。
3. worker 只有在 epoch 仍有效时才能写 checkpoint 或最终结果。
4. 所有子步骤继承 run deadline；队列和工具调用都有容量上限。
5. 超时后停止新步骤、取消进程树并释放许可。
6. 外部副作用按 operation ID 查询；无法确认时标记 `UNKNOWN`。

这个方案没有承诺“所有事情只发生一次”。它提供的是可证明的当前 owner、可去重的请求、可恢复的 attempt 和诚实的不确定状态。

## 9. 常见误区

1. **“用了线程安全容器就没有竞态。”** 多步业务操作仍可能在步骤之间竞态。
2. **“队列消息只会投递一次。”** 网络和消费者崩溃都可能导致重复投递。
3. **“lease 过期证明旧 worker 已死。”** 它只表示授权到期，所以资源端还要校验 epoch。
4. **“取消 future 会撤销 HTTP 请求。”** 已经发送的副作用可能继续完成。
5. **“异步等于更高吞吐。”** CPU 阻塞、无界队列和下游容量仍是硬约束。

## 10. 30 秒面试答案

> 我先定义不变量：同一 task 同一时刻最多一个有效 owner 能提交结果。worker 通过数据库条件更新领取 attempt，长任务用可续租 lease；提交端校验递增 epoch，拒绝恢复后的旧 worker。所有子步骤继承端到端 deadline，取消时先阻止新工作，再停止本地执行并核对外部副作用。容量侧使用有界队列、并发许可、租户配额和准入控制，让过载尽早变成明确拒绝，而不是无界排队和集体超时。

## 11. 做题方法：推演领取、续租、取消和背压

1. 为任务维护 `READY → LEASED → RUNNING → SUCCEEDED/FAILED/CANCELLED`，领取必须是带条件的单次状态转移，而不是“先 SELECT 再 UPDATE”。记录 owner、lease generation 和到期时间。
2. 让 worker A 领取后暂停，lease 到期后 worker B 接管，再让 A 恢复。A 的完成写必须携带旧 generation 并被存储拒绝；只检查本地时间不足以防止双写。
3. 把总 deadline 分给排队、启动、模型调用、工具调用和收尾。每次下游调用只取得剩余预算，取消本地 Future 后仍把远端结果标成可能 UNKNOWN。
4. 对每个 async task 记录持有的 permit、队列槽和子任务。正常完成、错误、timeout、取消与 panic 路径都必须归还 permit；否则并发度会在故障后永久下降。
5. 让消费者暂停，计算队列以 `到达率-消费率` 增长并何时达到上限；满时的拒绝、降级或重试必须写进调用方协议。

验算点：任一 generation 只有一个有效 owner；终态条件更新最多成功一次；deadline 不会在每一层重新开始；取消后无 permit 泄漏；队列满不会悄悄变成无界内存。

## 12. 章末自测

1. 为什么“查询后更新”会让两个 worker 同时领取任务？
2. 队列消息与任务所有权为什么不是一回事？
3. lease 和 fencing epoch 分别解决什么问题？
4. deadline 为什么应向下传递剩余时间？
5. 无界队列如何把短暂过载变成长时间故障？
6. 取消本地进程后，为什么仍可能进入 `UNKNOWN`？

### 参考答案与解答

<details>
<summary>展开答案</summary>

1. **查询和更新之间存在竞态窗口。** 假设 A、B 都先读到 `PENDING`，随后二者都执行更新并开始工作，任务就被领取两次。正确做法是把条件和修改合成一次原子操作，例如“仅当状态仍为 `PENDING` 且 version 未变时改为 `RUNNING`”；只有影响一行的 worker 获得所有权，另一个看到影响零行后重新读取。
2. **队列只证明消息可见，不证明业务授权唯一。** 消费者取到消息后可能在确认前崩溃，队列于是再次投递；同一消息也可能因网络重试重复出现。任务所有权必须由权威存储中的条件更新、Attempt 和 lease 决定，队列只负责通知“可能有工作”。
3. **lease 决定“何时可以接管”，epoch 决定“谁的写仍有效”。** lease 到期后调度器可以给新 worker 分配任务，但它不能证明旧 worker 已停止。每次授权递增 epoch，资源端只接受当前 epoch，旧 worker 恢复后携带旧值的写入会被拒绝，这就是 fencing。
4. **因为 deadline 是整条调用链共享的完成时刻。** 若每一层都重新给 10 秒，三层串行调用最坏可能耗时约 30 秒，违反调用方的 10 秒承诺。正确推演是 `剩余预算 = 总 deadline - 当前时间`，下游 timeout 不能超过剩余预算，还要为清理和返回结果保留时间。
5. **积压会在过载结束后继续消耗系统。** 若到达率为每秒 120、消费率为每秒 100，持续 60 秒就积压 `(120-100)×60=1,200` 个任务。流量恢复到每秒 80 后，净消化速度只有 `100-80=20` 个/秒，还要 60 秒才能清空；若请求在排队期间超时并重试，实际积压会更大。有限队列让系统在边界处拒绝或降级，而不是无限占用内存并放大超时。
6. **杀掉本地进程只能证明本地不再继续执行。** 请求可能已到达远端，远端也可能已经完成，只是响应尚未写回本地。缺少远端收据时，系统既不能判成功，也不能判失败，只能保存同一个 operation ID 并进入 `UNKNOWN`，随后查询或对账；直接重试可能产生第二次副作用。

</details>

## 本章小结

- 并发正确性的中心是业务不变量，而不是某个同步工具的名字。
- 条件更新、lease 和 fencing 共同定义当前有效 owner。
- 取消需要覆盖子任务和资源，但不能自动回滚外部副作用。
- deadline 必须沿调用链传递，不能在每层重新计时。
- 有界队列、配额和准入控制让过载保持可控。
