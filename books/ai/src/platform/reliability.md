# 可靠性与事故响应：让历史故障不能原样重演

可靠性不是“组件永不坏”，而是坏了以后影响可控、能够恢复、证据完整，同一种根因不会无限复发。消防系统不会承诺永不着火，而会限制火势、报警、疏散并改进建筑规范。

先把黑话翻译成人话：**error budget** 是 SLO 允许失败的总额度；**blast radius** 是一次故障能影响多大范围；**canary** 是先给少量真实流量验证新版本；**cell 架构**把系统拆成可重复、相对独立的小单元以限制故障范围；**bulkhead（舱壁隔离）**把资源池分开，防止一个故障淹没全部；**load shedding** 是过载时主动拒绝低优先任务，**brownout** 是暂时关闭非关键功能。`cordon → drain` 表示节点先停止接新任务，再排空旧任务。这些机制分别解决限损、恢复和防复发，不能被“多部署几个副本”概括。

## 1. 从 SLO 开始

SLI（Service Level Indicator，服务水平指标）是测量，例如“成功启动的沙箱比例”；SLO（Service Level Objective，服务水平目标）是内部或团队目标，例如 30 天窗口内达到 99.9%；SLA（Service Level Agreement，服务水平协议）是对外合同，通常还包含未达标后的责任。

在明确采用 30 天窗口且把所有分钟等权计算时，99.9% 可用性对应约 43.2 分钟不可用预算。若一次发布造成 30 分钟故障，已经消耗约 69% 的该窗口预算。真实 SLO 还要定义哪些请求属于有效事件、怎样统计部分失败以及维护窗口是否计入。error budget 能把“继续高速发布还是先修可靠性”变成可讨论的规则。

Agent 平台应避免只用 HTTP 200 定义成功。一个 run 可能 API 成功、沙箱也启动，却因工具越权被安全层拒绝；不同 SLO 要分别定义。

## 2. 故障域与 blast radius

把节点、机架、可用区、区域、运行时版本、镜像、租户和控制面分片视为故障域。副本都放在同一机架，数量再多也挡不住机架断电；所有区域同时自动升级，等于主动消灭隔离。

控制 blast radius 的方法包括：分片、租户配额、cell 架构、canary、逐批发布、每批健康门槛和全局动作速率限制。

## 3. 超时、重试、退避与抖动

没有超时会永久占资源；超时太短会把正常长尾当故障。重试可以掩盖瞬时失败，也会放大负载。

若连续 4 层都独立地最多总尝试 3 次（初次 + 2 次重试），最坏尝试数会达到 `3^4 = 81`。若每层是“初次之外再重试 3 次”，最坏则是 `4^4 = 256`。通常应在最了解业务语义的一层控制总预算，并使用指数退避、随机抖动和全链路 deadline。

重试必须消耗同一个时间/次数/成本预算。用户只给 30 秒 deadline，内部不能每层各等 30 秒。

## 4. 熔断、隔离与降级

- 熔断器在依赖明显失效时快速失败，避免继续堆积。
- bulkhead 把资源池按依赖或租户隔开，避免一个故障淹没全部。
- load shedding 在过载时拒绝低优先级新任务，保护已运行任务。
- brownout 暂停非关键功能，例如详细内容 trace、预热或低优先级评测。

降级要预先设计并演练。事故中临时决定“关哪个开关”通常既慢又危险。

## 5. 节点自动上下线

上线门禁可包含：内核/运行时版本、cgroup 与安全策略、自检沙箱、网络、卷、时钟、磁盘健康和观测上报。只有所有关键检查通过才接新任务。

下线采用 cordon → drain → cleanup → remove：先停止新任务，再等待/迁移，回收秘密与资源，最后移出服务。强制下线必须记录被中断任务，并走 checkpoint 或安全重试。

自动修复要有“停止条件”。如果 20% 节点同时失联，逐台重启可能摧毁剩余容量；系统应先冻结大动作并升级人工响应。

## 6. RTO、RPO 与 checkpoint

- RTO（Recovery Time Objective，恢复时间目标）：从故障到服务恢复允许多久。
- RPO（Recovery Point Objective，恢复点目标）：按时间或提交点表示最多允许丢失多少已确认数据。

Agent 长任务每 5 分钟 checkpoint，最坏可能重做近 5 分钟；checkpoint 本身若需 20 秒，太频繁又损失吞吐。应根据任务价值、失败率、checkpoint 大小和恢复时间计算，而不是固定“一分钟一次”。

控制面数据库声称有备份不等于能恢复。要定期在隔离环境恢复，并验证 schema、对象存储、密钥和 DNS 等依赖一起可用。

## 7. 发布与回滚

发布单元要包含模型、Prompt、Harness、工具 schema、运行时、镜像和策略版本。只记录 Git commit 不足以还原 Agent 行为。

canary 比较技术指标和任务质量；影子流量不执行真实副作用，或把副作用导向模拟环境。回滚也可能不兼容：新版本已经写入新 schema 或新快照，旧版本能否读取必须提前验证。

## 8. 事故响应流程

1. 发现并声明事故，建立负责人和统一频道。
2. 先止血：限流、隔离、回滚、禁用高风险工具。
3. 建立时间线和影响范围，保护证据。
4. 恢复并验证，不因指标短暂回落就宣布结束。
5. 事后复盘系统条件，不写“某人不够小心”。
6. 行动项有 owner、截止日期和验证方式。

“添加告警”通常不是完整防复发。更强的修复是把不变量变成代码、策略、测试、发布门禁或自动回滚。

## 9. 典型失败路径

节点 agent 新版本造成 2% 启动失败。自动修复器把失败解释为宿主异常并重启节点；重启后的节点再次升级并失败，最终形成大规模滚动重启。

防线应包括小批 canary、按版本聚合失败、自动化动作预算、同因失败熔断、保留上一版本和一键停止 rollout。复盘要新增“版本相关启动失败不得触发节点级无限自愈”的不变量测试。

## 10. 章末面试问题

**题目：如何确保前人的事故不会重演？**

**30 秒答法：**我会先把事故从人的失误还原为缺失的系统防线，形成可执行不变量；近期用限流、回滚和隔离止血，中期把根因变成回归测试、配置校验、canary 门槛和自动化动作上限，长期调整架构故障域。每个行动项有 owner、期限和验证证据；发布后用与事故同形的故障注入确认防线有效。告警只负责发现，不能代替预防和限制 blast radius。

可能追问：

1. 依赖超时时重试几次？如何避免重试风暴？
2. 控制面数据库区域故障时 RTO/RPO 如何定？
3. 什么指标触发自动回滚，如何避免误回滚？
4. 什么时候必须人工介入而不是继续自动修复？

## 11. 本章速记

- SLO 和 error budget 把可靠性变成可度量取舍。
- 副本要跨真实故障域，发布也要限制 blast radius。
- deadline 是全链路预算；重试要幂等、退避、有抖动。
- 自动化既能救火，也能高速扩大故障，必须有动作预算。
- 复盘的终点是可验证防线，不是“以后小心”。
