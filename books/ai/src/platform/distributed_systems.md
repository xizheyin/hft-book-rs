# 分布式系统取舍：重复、乱序、分区和“恰好一次”幻觉

> 难度：必会。官方 JD 明确要求理解大规模分布式系统的组织方式、瓶颈来源与 trade-off。

一台机器失败通常是“开或关”；分布式系统更麻烦：请求可能已经执行，但回包丢了。调用方看到超时，不知道该重试还是等待。把它想成给餐馆下单：电话断线时，厨房可能没听见，也可能已经做了两份。

## 1. 先接受部分失败

网络可能丢包、延迟、乱序或分区；进程可能暂停、重启；磁盘和时钟也可能表现异常。超时只能说明“在期限内没收到结果”，不能证明远端没有执行。

Agent 平台尤其容易遇到长任务：模型调用、仓库下载、编译和外部工具各有独立故障域。系统必须记录每一步的身份与状态，而不是把整条链当作一个不会中断的函数。

## 2. 投递语义与幂等

| 语义 | 系统承诺 | 应用代价 |
|---|---|---|
| at-most-once | 最多执行一次，失败时可能丢 | 适合可丢的遥测 |
| at-least-once | 最终至少尝试一次，可能重复 | 副作用必须幂等或去重 |
| exactly-once effect | 业务结果只生效一次 | 需要把去重与副作用放进同一原子边界 |

“消息只取一次”不等于“业务恰好生效一次”。消费者可能写完数据库、还没确认消息就崩溃；重启后消息再次投递。

为工具调用生成稳定 `operation_id`，服务端保存 `(operation_id, result)`，重复请求返回旧结果，是常见去重方式。但若操作会调用一个不支持幂等的第三方系统，内部去重记录和外部副作用之间仍有缝隙。

## 3. Agent 工具的幂等分类

- 纯读取：通常可安全重试，但要考虑快照时刻和速率限制。
- 覆盖写：带版本条件时可幂等，例如“把配置从 v7 改到 v8”。
- 追加写：重复会产生两条记录，需要幂等键。
- 不可逆动作：付款、发布、删除生产数据，应审批并查询状态，不能盲重试。

重试策略必须与操作语义绑定。HTTP 500 不说明副作用未发生，连接超时也不说明请求没到达。

## 4. 复制与 quorum 小例子

有 3 个副本，写入等待 W 个、读取查询 R 个。若 `W + R > 3`，读写集合至少有交集，有机会读到新版本；但还需要版本比较、故障修复等机制。

选择 `W=2, R=2` 能容忍一个副本不参与常规读写，但写和读都至少等待两个响应。选择 `W=1, R=1` 延迟更低，却可能从不同副本读到旧值。CAP 不是让你在 C、A、P 中永久勾选两个，而是网络分区发生时具体操作如何在一致性与可用性间决策。

## 5. 共识不等于业务正确

Raft/Paxos 一类共识可以让多个节点同意一条日志顺序，仍不能替你回答：取消和完成同时发生谁赢；超时任务能否提交结果；配额是按全局还是区域扣减；旧节点能否继续写卷。

业务要定义 generation、条件更新和不变量，再用事务、共识或租约实现。

## 6. 事务、消息与 Outbox

“写数据库后发消息”有两个失败窗口：写成功、消息没发；消息发了、数据库回滚。Transactional Outbox 把业务更新和待发事件写进同一数据库事务，异步发布器再至少一次发送 outbox。消费者仍要去重。

它牺牲了端到端即时性，换来可恢复的事实来源。对“run 已创建，需要调度”这类控制面事件通常很合适。

## 7. 分片与热点

按 run ID 哈希可平均分散普通任务，但大租户、热门基础镜像或共享项目仍会形成跨维度热点。按租户分片便于配额和隔离，大租户却可能压垮单分片；一致性哈希减小扩容迁移量，却不自动解决热 key。

面试时应先给出访问模式，再选 key：查询主要按 run、租户、节点还是时间？是否需要跨 key 事务？热点能否拆分或缓存？重分片期间怎样双读/双写并验证？

## 8. 时钟、租约与 fencing

墙钟会跳变，不适合直接判断精确持续时间；单机超时用单调时钟。跨节点租约仍需考虑最大时钟偏差或由一致性服务确定顺序。

租约过期后，旧持有者不一定立刻停止。数据面必须检查单调递增 fencing token，拒绝旧 token 的写。否则网络分区恢复时就会出现双主。

## 9. 典型失败路径

工具执行器超时后自动重试“创建共享卷”。第一次其实已成功，只是回包丢失；第二次创建了另一块卷。两个卷分别被计算节点和清理器引用，最终一个泄漏、另一个被误删。

修复是让创建请求带稳定 operation ID，让资源 ID 由请求确定或由服务保存去重结果；后续挂载按 generation 和 fencing；孤儿扫描器只作为最后防线。

## 10. DeepSeek Agent Infra 面试怎么问

**题目：怎样保证一个 Agent 工具只执行一次？**

**30 秒答法：**网络下无法仅靠客户端重试保证真正 exactly-once。我会先分类副作用，给每个逻辑操作稳定幂等键；服务端在与业务更新相同的原子边界中记录键和结果，重复请求返回已有结果。跨外部系统时用状态查询、条件写、outbox/saga 或人工审批缩小不确定窗口，并明确 unknown 状态而不是盲重试。执行租约配合 fencing 防旧 worker 继续提交。

常见追问：

1. 消费消息、写数据库、确认消息之间如何处理崩溃？
2. 强一致、最终一致和线性一致分别适合哪些平台状态？
3. 跨区域分区时，配额与新任务创建继续吗？
4. 热分片怎样发现和迁移？

## 11. 本章速记

- 超时是未知，不是失败证明。
- at-least-once 加幂等，比空喊 exactly-once 更现实。
- 共识解决顺序，不替代业务不变量。
- outbox 修复数据库与消息的双写缝隙，消费者仍需去重。
- 租约会过期，fencing 才能让旧主人失去写权。
