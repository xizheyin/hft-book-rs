# 压测与容量规划：别让平均值替你撒谎

> 难度：必会。官方 JD 要求熟练使用压测与可观测工具，定位跨多个系统层级的复杂问题。

容量规划像设计高速公路：知道每天总车流还不够，还要知道早高峰到达率、车辆类型、入口排队、事故与绕行。Agent 工作负载既有几秒小任务，也有数小时长程任务，平均值尤其危险。

## 1. 先定义 workload

至少记录：

- 到达过程：稳定、突发、定时批量还是事件触发。
- 任务长度：step、Token、工具次数、沙箱时长的分布。
- 资源向量：CPU、内存、GPU、磁盘字节/IOPS、网络与外部 API。
- 数据局部性：镜像和仓库命中率、工作集大小。
- 安全等级与 runtime class。
- 成功、取消、超时与重试比例。

压测流量应来自脱敏 trace 或明确构造的代表性混合。只测“一个 hello world 容器启动”无法预测真实 checkout、安装、编译和测试。

## 2. Little's Law 是第一把尺

稳态下：

```text
系统内平均任务数 L = 到达率 λ × 平均停留时间 W
```

每秒 100 个任务，平均端到端 40 秒，系统内平均约 4,000 个任务。若服务时间升到 60 秒而到达率不变，平均在途变成 6,000；资源不变时队列还会继续增长。

它不替代排队模型，却能快速检查架构图是否数量级自洽。

## 3. 利用率接近 100% 为什么危险

服务时间有波动时，利用率越接近 100%，排队延迟通常非线性上升。共享池必须保留处理突发、故障和长尾的余量。

“CPU 只有 50%”也不证明容量充足：可能卡在内存带宽、GPU 显存、I/O、单锁、网络端口、外部 API 限额或某一个分片。资源向量需要逐项看饱和度。

## 4. 延迟指标先统一口径

- queue time：准入后等待资源。
- sandbox startup：分配到健康运行。
- TTFT：模型请求到首 Token。
- TPOT：首 Token 后每个 Token 的时间。
- tool latency：含排队、网络和执行。
- end-to-end：用户提交到最终可用结果。

p99 不能由各阶段 p99 直接相加，也不能把不同时间窗的分位数平均。保留 histogram 或原始样本，用统一 trace 分解。

详情可复用 Rust/HFT 篇的[指标与分位数](../../rust-hft/infrastructure/metrics.html)和[基准测试方法](../../rust-hft/optimization/benchmarking.html)。

## 5. 开环与闭环压测

闭环客户端等上一个请求返回才发下一个。系统变慢时，客户端自然降速，可能掩盖过载。开环压测按外部到达率发请求，更接近真实突发，但必须设置有界队列和停止条件。

还要避免 coordinated omission：服务卡住期间测试器没发出的请求，也代表真实用户本来会到达的等待。记录计划发送时间，而不只记录实际发送后的服务时间。

## 6. 五类测试

| 测试 | 回答什么 |
|---|---|
| load | 目标流量下是否达 SLO |
| stress | 从哪里开始饱和，怎样降级 |
| spike | 突发与恢复会不会形成风暴 |
| soak | 数小时/数天后是否泄漏、碎片化、GC 抖动 |
| fault injection | 节点、网络、卷、控制面失败时是否可控 |

结果必须写明硬件、版本、数据、预热、并发、到达模型、缓存状态、运行时长和误差。否则“提升 20%”无法复现。

## 7. 一个跨层容量表

假设峰值 500 runs/s，平均 50 s，p95 180 s；每 run 平均 2 vCPU、3 GiB、启动读 300 MiB、日志写 20 MiB。

粗略平均在途为 25,000 runs，需要约 50,000 vCPU 和 75,000 GiB 内存，尚未乘余量。仅启动读流量为 `500×300 MiB/s ≈ 146 GiB/s`，日志写约 `9.8 GiB/s`。这说明镜像缓存和启动错峰可能与 CPU 容量同等重要。

平均数仍不够：180 秒长任务占用资源会让短任务排队，应按 workload class 分池或做公平调度。

## 8. 自动扩缩容信号

只按 CPU 扩容可能太晚。领先信号可以是准入到达率、队列年龄、可调度资源缺口、启动槽位和镜像拉取带宽；落后信号是 CPU/内存利用率与 SLO 违约。

扩容有准备时间，必须提前量；缩容要确认没有长任务、缓存价值和故障余量，并设置冷却期，避免来回震荡。

## 9. 典型失败路径

团队用闭环客户端证明平台能承受 1,000 并发。生产突发 300 requests/s 时，服务变慢但到达不减，无界队列增长，数分钟后所有请求超时并同时重试。

正确压测应复现开环到达率和重试策略，设置队列上限，观察 queue age 与拒绝率，验证过载时优先保护在运行任务并返回明确重试提示。

## 10. DeepSeek Agent Infra 面试怎么问

**题目：你会怎样证明沙箱平台能承受目标规模？**

**30 秒答法：**先从真实 trace 建 workload 分布，按到达率、任务时长和 CPU/内存/磁盘/网络向量用 Little's Law 做数量级预算；再用开环流量分别做 load、stress、spike、soak 和故障注入。全链路 trace 分解排队、调度、启动、模型、工具和存储延迟，关注 p50/p95/p99、队列年龄、饱和点与恢复时间。压测必须固定硬件、版本、数据、缓存和重试；达到过载点时应有界排队、限流和降级，而不是把请求都拖到超时。

可能追问：

1. 如何测启动冷缓存和热缓存两种情况？
2. CPU 不高但 p99 很差，按什么顺序排查？
3. 怎样估算 burst 所需余量和扩容提前量？
4. 压测系统本身如何避免成为瓶颈？

## 11. 本章速记

- workload 分布比一个平均 QPS 更重要。
- `L=λW` 先做数量级检查。
- 高利用率会放大排队；CPU 低也可能是别处饱和。
- 开环测试更能暴露过载，队列必须有界。
- 报性能必须带环境、版本、数据和统计口径。
