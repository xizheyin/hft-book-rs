# 压测与容量规划：Agent 平台如何接住真实任务

> 难度：必会。官方 JD 要求熟练使用压测与可观测工具，定位跨多个系统层级的复杂问题。

本章不再重复 Little 定律、分位数、开环/闭环模型和 Linux 性能工具的基础定义。第一次接触这些概念，请先读[性能与跨层诊断](../systems/performance_diagnostics.md)。这里专门讨论它们在 Agent Infra 中怎样落地：一个平台如何同时接住交互请求、代码沙箱、长任务和批量评测，并在过载时保持可控。

可以把平台想成机场。CPU 和内存像跑道，镜像与仓库数据像行李，沙箱启动槽位像登机口，外部模型和 API 又像其他机场。只统计“有多少架飞机”远远不够；任何一处先塞住，都会让总队列增长。

## 1. 先把任务分成 workload class

不要用一个“平均 Agent 任务”代表所有流量。至少分开这些类别：

| 类别 | 常见特征 | 最先关注的容量 |
|---|---|---|
| 交互式工具调用 | 短、延迟敏感、突发明显 | 排队年龄、热沙箱、外部 API 限额 |
| 代码沙箱 | 启动要拉镜像和仓库，CPU/内存差异大 | 启动槽位、镜像缓存、磁盘与网络 |
| 长程 Agent | 持续数十分钟或数小时，可暂停或等待人类 | 租约、checkpoint、占用时长、公平性 |
| 批量评测 | 吞吐优先，可计划、规模大 | 批次准入、低优先级资源池、成本上限 |
| GPU 推理或训练工具 | 显存是硬约束，设备型号也有差异 | GPU 拓扑、显存、模型驻留与装载带宽 |

每类都要记录分布，而不是只有平均数：

- 到达方式与峰值：稳定、突发、定时批量还是事件触发；
- 任务长度：step 数、Token、工具次数、沙箱运行时间；
- 资源向量：CPU、内存、GPU、临时盘、IOPS、网络和外部 API 配额；
- 启动数据：镜像大小、仓库大小、依赖下载量和缓存命中率；
- 结果：成功、取消、超时、抢占和重试比例；
- 隔离要求：租户、安全等级、网络策略和 runtime class。

压测流量可以来自脱敏后的真实 trace，也可以人工构造，但必须保留这些相关性。例如“大仓库通常编译更久”就是相关性；分别随机抽仓库大小和任务时长，可能制造出生产中根本不存在的任务。

## 2. 先分清 task、attempt 和 sandbox

容量表中最常见的低级错误，是把三种对象混成一个数字：

- **task**：用户认为的一次任务；
- **attempt**：task 的一次执行尝试，失败重试会产生新的 attempt；
- **sandbox**：承载 attempt 的运行环境，可能预热后等待，也可能被回收。

因此要分别统计：

```text
accepted tasks -> queued attempts -> starting sandboxes -> running attempts
                                      -> draining sandboxes -> released resources
```

一个 task 因超时同时存在两个 attempt，资源消耗就接近两份；一批空闲热沙箱没有运行 attempt，也仍在占内存和磁盘。只看“活跃 task 数”会漏掉这两部分。

## 3. 用资源向量做容量表

先把统计对象说清楚。假设在一个队列不再持续增长的稳态窗口中：

- 平台平均接收 `500 tasks/s`，逻辑 task 的平均端到端停留时间为 `50 s`，p95 为 `180 s`；
- 重试后平均启动 `550 attempts/s`，每个运行中 attempt **固定**占 `2 vCPU`、`3 GiB`，平均实际运行 `40 s`；
- 热池复用后平均只需新启动 `300 sandboxes/s`，每次启动读取 `300 MiB`；
- 稳态下平均完成 `550 attempts/s`，每个 attempt 在整个生命周期共产生日志 `20 MiB`。

这样才可以分别计算：

```text
端到端在途 task：500 tasks/s × 50 s = 25,000 tasks
运行中 attempt：550 attempts/s × 40 s = 22,000 attempts
教学版 CPU 需求：22,000 × 2 vCPU = 44,000 vCPU
教学版内存需求：22,000 × 3 GiB = 66,000 GiB
启动读带宽：300 sandboxes/s × 300 MiB/sandbox ≈ 87.9 GiB/s
日志写入率：550 attempts/s × 20 MiB/attempt ≈ 10.7 GiB/s
```

`25,000` 包含排队和等待中的逻辑 task，不能拿它直接乘运行资源。启动带宽必须乘 **sandbox 启动率**，日志总量必须乘 **attempt 完成率或实际日志产生率**，不能都用一个含义模糊的 `runs/s`。

上面的 CPU/内存乘法还故意假设每个 attempt 在整个运行期都固定占相同资源。真实任务的资源量会与时长相关，应按 workload class 分开计算并求和，或使用 `attempt 到达率 × E[资源量 × 实际占用时间]`。峰值若只持续几秒，也不能冒充稳态平均率；还要单独验证队列如何吸收突发。所有结果都只是带明确假设的基线估算，尚未加入故障余量、系统守护进程、热沙箱和资源碎片。镜像缓存、仓库快照或日志管道仍可能比 CPU 更早饱和。

一张可执行的容量表至少应包含：

| 项目 | 需求侧输入 | 供给侧输入 | 需要保留的余量 |
|---|---|---|---|
| CPU / 内存 | 各类并发量与每 attempt 用量 | 可调度节点资源 | 节点故障、系统开销、突发 |
| GPU / 显存 | 模型、设备类型、同时驻留数 | 各型号设备与拓扑 | 单机故障、碎片化 |
| 启动槽位 | 每秒启动数、启动耗时 | 并行拉取/解压/挂载能力 | 冷缓存和镜像发布 |
| 临时盘 | 工作集与日志峰值 | 节点可用空间、回收速度 | 泄漏、延迟清理、checkpoint |
| 网络 / 存储 | 拉取、checkout、制品和日志流量 | 链路、对象存储与卷吞吐 | 重试和跨区恢复 |
| 外部服务 | 模型/API 调用数和 Token | 限额、并发与预算 | 限流、供应商故障 |

最终容量由最先耗尽的那一维决定，而不是由 CPU 一项决定。

## 4. 准入和队列也是容量组件

“机器还能创建”不等于“请求应该继续收”。控制面在准入时应检查：

1. 租户和全局并发配额；
2. 对应 runtime class 是否有可调度资源；
3. 启动槽位、镜像带宽和外部 API 是否接近上限；
4. 队列是否已达到长度或年龄上限；
5. 任务的截止时间是否还可能满足。

队列必须有界。超出安全水位时，应明确拒绝、降级或延后批量任务，而不是让所有请求排到超时。面试时不要只说“设置最大长度”，还要说明策略：

- 交互任务可获得较短队列和较高优先级；
- 批量任务可等待更久，但要限制占用份额；
- 同一租户不能用大量长任务饿死其他租户；
- 重试要有退避、随机抖动和总预算；
- 取消的 task 要及时从队列和资源预留中清除。

队列长度只表示“有多少”，**最老任务年龄**更直接反映用户已等多久。两者应与拒绝率、可调度资源缺口一起观察。

## 5. 多资源调度：总量够，也可能放不下

假设节点各剩 2 vCPU 和 8 GiB 内存，而新任务需要 4 vCPU 和 2 GiB。集群总空闲 CPU 可能很多，但没有单台节点能容纳它。这叫资源碎片，GPU 型号、显存和本地盘会让问题更明显。

应对方法包括：

- 按 runtime class 和任务大小建立有限的资源池；
- 调度时同时考虑 CPU、内存、GPU、磁盘与拓扑；
- 给常见小任务保留可用形状，避免被大任务切碎；
- 对大任务使用排队、预约或 gang scheduling，而不是无限反复试调度；
- 用 requested、allocated、actually used 三套指标识别过度申请。

不要把所有 workload 都永久拆成独立集群，那会浪费共享余量。更实际的做法通常是少量隔离池加公平调度，并根据安全边界和资源形状决定是否分池。

## 6. 冷启动是一条独立容量链

沙箱从“已接受”到“可执行工具”可能经过：

```text
调度 -> 拉镜像 -> 解压/挂载 -> 创建隔离环境
     -> checkout 仓库 -> 注入凭据与策略 -> 健康检查
```

每一步都有独立的并发上限。扩了节点却没有扩镜像仓库出口，结果可能只是更多节点同时抢同一条链路。

常见优化要连同代价一起回答：

- **热沙箱池**降低启动时间，但会长期占资源，还要安全地清理上一个任务的数据；
- **节点镜像缓存**减少网络读取，但镜像发布时会出现大面积冷缓存；
- **仓库快照或依赖缓存**减少 checkout 和安装时间，但缓存键必须包含版本与权限边界；
- **启动限速**保护存储和网络，但会把等待转移到启动队列，因此必须暴露启动队列年龄。

容量压测要分别覆盖全热、部分命中和全冷三种状态。只在预热后的环境中测一次，无法证明新区域启动或镜像升级时还能工作。

## 7. 长任务需要“可让路”的设计

长程 Agent 会持续占用资源，并放大节点维护、发布和故障带来的影响。平台至少要决定：

- 等待模型、外部 API 或人工确认时，沙箱是否继续整份占用；
- 能否 checkpoint 后释放资源，之后恢复；
- 节点排空时是等待、迁移、抢占还是重启 attempt；
- checkpoint 的时间、大小和恢复成功率是否已计入容量；
- 单租户的长任务份额如何限制。

如果任务不能暂停，就要给扩缩容和节点维护留出最长任务时长。若任务可以 checkpoint，就要压测“保存—回收—恢复”完整路径，不能只验证保存接口返回成功。

## 8. 扩缩容要看领先信号和准备时间

CPU、内存利用率通常在任务已运行后才升高，单独依赖它们容易扩得太晚。Agent 平台常用的领先信号包括：

- 准入到达率和各 workload class 的到达率；
- 队列年龄与可调度资源缺口；
- 正在启动的 sandbox 数和启动槽位占用；
- 镜像拉取带宽、缓存未命中率；
- 未来批量任务的已知计划。

一个实用估算是先问：“从决定扩容到新 sandbox 可运行，要多久？”如果节点准备、镜像拉取和健康检查一共需要 5 分钟，扩容器就不能等到 SLO 已违约才行动。

缩容同样有状态：先停止接新任务，再排空或 checkpoint，最后回收节点。还要保留故障余量和有价值的缓存，并设置冷却时间，避免刚扩出的节点又被立即删除。

## 9. 把压测做成场景矩阵

基础章已经解释 load、stress、spike、soak、开环流量和 coordinated omission。本章直接把这些方法映射到沙箱场景：

| 维度 | 至少要覆盖的取值 |
|---|---|
| 缓存 | 热镜像、部分命中、全冷 |
| 仓库 | 小仓库、大仓库、大量小文件 |
| 任务 | 短工具、编译测试、长程 Agent、批量评测 |
| runtime | 普通容器、强隔离沙箱、GPU 类别 |
| 网络 | 正常、限速、高延迟、外部 API 限流 |
| 生命周期 | 正常完成、取消、超时、重试、checkpoint 恢复 |
| 平台状态 | 稳态、突发、发布、节点排空、单区故障 |

不必把所有组合都穷举。先从生产最常见、资源最重和风险最高的组合中挑选，再补边界情况。

一轮完整验证可以这样安排：

1. **目标负载**：确认正常峰值下 SLO 和资源预算；
2. **寻找饱和点**：逐步增加到达率，记录最先耗尽的资源和降级行为；
3. **突发与恢复**：验证队列不会无限增长，流量回落后能在目标时间内清空；
4. **长时间运行**：观察内存、文件描述符、临时盘、僵尸 sandbox 和缓存是否持续增长；
5. **故障注入**：在有边界的测试环境中验证节点、网络、卷、控制面或外部服务失败。

每次结果都要记录硬件、软件版本、数据集、租户混合、缓存状态、到达模型、重试策略、运行时长和停止条件。否则两次“500 runs/s”可能根本不是同一个实验。

## 10. 压测器不能成为隐藏瓶颈

压测流量最好从与被测集群分离的机器发出，并同时监控压测器自身的 CPU、网络、连接数和事件循环延迟。否则可能把“压测器发不动了”误判为“服务稳定承载”。

压测前写清安全边界：

- 只使用测试租户、无真实凭据的镜像和可丢弃数据；
- 给请求数、费用、并发、运行时间和日志量设置硬上限；
- 当错误率、队列年龄、成本或共享依赖压力越线时自动停止；
- 把负载生成、系统指标和 trace 放到统一时间轴；
- 避免让压测流量误入生产外部 API。

如果压测环境与生产规模不同，要说明怎样外推，以及哪些共享瓶颈无法线性外推。例如对象存储限额、控制面 leader 和单个镜像仓库出口通常不是“节点翻倍，容量就翻倍”。

## 11. 故障注入要验证恢复闭环

故障注入不是“随机杀进程看热闹”，而是带假设的实验。例如：

> 假设：一个工作节点失联后，控制面会在租约到期后把 attempt 标为待恢复；旧节点即使重新联网，也会被 fencing token 阻止提交旧结果；队列年龄在 10 分钟内恢复到水位以下。

实验要事先写明：

1. 注入对象和最小爆炸半径；
2. 预期告警、状态迁移和用户可见结果；
3. 停止条件与回滚方法；
4. 成功指标，包括数据对账和恢复时间；
5. 实验结束后的残留资源、重复 attempt 和账单检查。

先在隔离环境和单个测试租户中进行，再逐步扩大范围。仅看到服务进程重新启动，不代表任务状态、外部副作用和资源账目已经恢复正确。

## 12. 一条典型失败路径

团队用预热环境和固定 1,000 并发完成了压测。生产中每秒突然到达 300 个请求，恰逢新镜像发布导致全冷缓存：

1. 镜像出口先饱和，sandbox 启动时间上升；
2. 压测中没有出现过的启动队列持续增长；
3. 用户超时后同时重试，产生更多 attempt；
4. 控制面按低 CPU 判断无需扩容；
5. 临时盘又被未完成拉取和日志占满，故障扩散。

修复不只是“加机器”，而是把冷缓存加入压测矩阵，对启动槽位和镜像带宽做准入，用队列年龄和资源缺口触发扩容，限制重试预算，并验证取消与失败拉取能清理临时数据。

## 13. DeepSeek Agent Infra 面试怎么答

**题目：你会怎样证明沙箱平台能承受目标规模？**

**30 秒答法：**我会先从脱敏 trace 建立 workload class，区分 task、attempt 和 sandbox，并按 CPU、内存、GPU、磁盘、网络、启动槽位及外部 API 做容量表。然后用基础章的方法估算并发下界，在开环到达率下覆盖热/冷缓存、短/长任务、突发、长稳和故障场景。观测准入、排队、调度、启动、运行、checkpoint 和回收全链路；过载时要求有界队列、公平限流和明确拒绝。扩缩容同时看队列年龄、资源缺口等领先信号，并把节点准备时间算进去。最后还要对账重复 attempt、残留 sandbox、外部副作用和成本，证明恢复的不只是进程。

可能追问：

1. 为什么总空闲资源很多，任务仍可能调度失败？
2. 热沙箱减少延迟后，会增加哪些安全和容量责任？
3. 如何避免批量评测饿死交互请求？
4. CPU 不高但启动 p99 很差，你按什么顺序查？
5. 节点扩容需要五分钟，怎样决定提前量？
6. 怎样证明压测器本身没有成为瓶颈？

## 14. 本章速记

- 平台容量由 workload 分布和最紧张的资源维度决定，不是一个平均 QPS。
- task、attempt、sandbox 必须分别计数，重试和热池都会额外吃资源。
- 队列、准入、启动槽位、镜像缓存和外部限额都是容量系统的一部分。
- 长任务要考虑 checkpoint、排空、公平性和缩容时间。
- 压测必须覆盖冷缓存、突发、长稳、取消/重试和恢复闭环。
- 扩缩容要结合领先信号与资源真正可用前的准备时间。
