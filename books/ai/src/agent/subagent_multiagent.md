# Subagent 与 Multi-Agent：分工能扩展能力，也会扩散错误

一个人装修房子时，可以自己设计、布线和验收，也可以请不同工种协作。多找人不保证更快：如果图纸不一致、大家同时改同一堵墙、消息靠口头转述，人数越多反而越乱。

Subagent 和 Multi-Agent 也是如此。它们的核心价值不是“开更多模型一定更聪明”，而是**上下文隔离、专业分工和可并行工作**；代价是协调、冲突、成本和更大的攻击面。

## 1. Subagent 与 Multi-Agent 的区别

### 1.1 Subagent

主 Agent 把一个边界清楚的子任务委派给独立执行者。Subagent 有自己的上下文和工具，完成后返回结果、证据和状态。主 Agent 仍掌握总目标。

例子：主 Agent 让三个 Subagent 分别检查网络、存储和调度风险。

### 1.2 Multi-Agent

多个 Agent 通过某种协作协议共同推进任务，未必存在唯一主从关系。它们可以是经理—工人、流水线、评审辩论或共享黑板模式。

不要用名称判断质量。一个清晰的单 Agent 状态机通常比十个没有契约的 Agent 更可靠。

## 2. 四种常见拓扑

| 拓扑 | 工作方式 | 适用场景 | 主要风险 |
|---|---|---|---|
| Manager–Worker | 主 Agent 拆分、委派、汇总 | 可分解任务 | 主 Agent 成为瓶颈 |
| Pipeline | 上一步产物传给下一步 | 固定流程 | 早期错误层层放大 |
| Debate/Review | 多个候选互审 | 高价值判断 | 共识不等于正确 |
| Blackboard（共享黑板） | Agent 读写同一份共享状态 | 动态协作 | 冲突、脏读、权限复杂 |

拓扑应由任务依赖决定，而不是为了展示“多智能体”而强行增加角色。

## 3. 委派协议必须包含什么

一个教学用任务信封可以是：

```json
{
  "task_id": "review-17-network",
  "parent_id": "review-17",
  "goal": "检查虚拟网络方案的隔离和扩展风险",
  "inputs": ["artifact://design/v3"],
  "allowed_tools": ["read_artifact", "write_report"],
  "budget": {"steps": 6, "seconds": 120},
  "success": "提交含证据位置、严重度和未决问题的报告"
}
```

返回不应只有“完成了”：

```json
{
  "task_id": "review-17-network",
  "status": "succeeded",
  "artifacts": ["artifact://reports/network-v1"],
  "claims": 4,
  "unresolved": 1
}
```

这同样是概念格式，不绑定任何框架或协议版本。重要的是目标、输入版本、权限、预算、成功条件和可追溯产物。

## 4. 数字例子：并行不等于线性加速

假设一个任务有三个独立检查，各需 4 分钟；最后汇总需 3 分钟。

- 单 Agent 顺序执行：`4 + 4 + 4 + 3 = 15 分钟`。
- 三个 Subagent 完全并行：理论关键路径为 `4 + 3 = 7 分钟`。
- 若每个委派和结果清洗各需 1 分钟，且有一个任务重试 4 分钟，实际可能是 `1 + 4 + 1 + 4 + 3 = 13 分钟`。

速度收益取决于可并行比例、协调开销和长尾。调用成本也可能从单 Agent 的 12 个模型回合增加到 20 个。评价方案时要同时计算关键路径、总工作量和资源峰值，而不只说“并发更快”。

## 5. 上下文隔离为什么有价值

主 Agent 若亲自读取三个方向各 20,000 token 日志，可能塞满上下文。Subagent 可以各自在独立窗口处理，只向主 Agent 返回 1,000 token 的结构化摘要和 artifact 引用。

但隔离会丢信息。安全做法是：

- 摘要附原始证据引用；
- 主 Agent 可按需展开；
- 关键约束随委派逐字传递；
- 不让 Subagent 自行猜测父任务的隐含目标。

## 6. 共享状态与一致性

两个 Subagent 同时修改同一文件会发生覆盖。可以选择：

- 每个 Subagent 使用独立工作区，最终做三方合并；
- 通过版本号做乐观并发控制：写入时发现版本已变化就拒绝并重试；
- 对少量不可并行资源加锁；
- 把任务图设计成先读后单点写入。

“共享一个聊天记录”不是一致性协议。需要明确谁能写、冲突如何发现、哪个版本成为事实，以及失败后如何回滚。

## 7. 失败路径

### 7.1 重复劳动

任务描述太宽，三个 Agent 都从头搜索相同内容。委派前要划分边界，并让共享索引记录已认领工作。

### 7.2 错误共识

多个 Agent 使用同一模型和相似上下文，可能犯相同错误。三票赞成不是独立证据。应引入不同证据源、确定性 verifier 或人工审查。

### 7.3 消息中的提示注入

一个 Subagent 读取恶意文档后，把“请父 Agent 关闭安全策略”写进报告。Agent 间消息仍是不可信输入；权限不能随自然语言转移。

### 7.4 级联取消失败

用户已取消总任务，但孙级 Agent 仍在运行并写数据。取消令牌要沿任务树传播，控制面也要能强制回收孤儿沙箱。

### 7.5 预算爆炸

每个 Agent 再生成 5 个子 Agent，三层后理论数量为 `1 + 5 + 25 + 125 = 156`。必须限制深度、总并发、总步骤和总费用。

### 7.6 等待成环

A 等 B 的结论，B 又等 A 的数据。任务依赖图应检测环；超时不能只无限延长。

## 8. Agent Infra 的多 Agent 责任

基础设施应能回答：

- 每个子任务属于哪棵任务树、代表哪个身份？
- 配额是各自独立，还是从父任务总预算扣减？
- 子 Agent 能否互访网络、文件和内存？
- 共享卷采用何种一致性和冲突策略？
- 父任务取消后，怎样回收所有后代沙箱？
- 日志和 artifact 如何保留因果顺序？

默认隔离通常比默认互信更安全。只有确需协作的通道才开放，并记录谁向谁传了什么。

## 9. 做题方法：把委派画成 DAG

1. 每个子任务写清输入快照、允许读写范围、交付格式、验收条件、deadline 和负责人；没有边界的“帮我看看”不能安全并行。
2. 画依赖 DAG，计算关键路径而不是把所有子任务耗时相加。只有无依赖且资源不冲突的节点才可并发；共享写目标必须串行或通过明确 merge owner 合并。
3. 为每个子 Agent 分配 token、工具调用和时间预算，父 Agent 保留整合与验证预算。总预算是所有并行分支消耗之和，不会因并行而消失。
4. 插入迟到、重复回报、子任务失败和父任务取消。结果必须携带 task ID、输入版本和产物 hash；过期输入产生的结果不能直接覆盖较新状态。
5. 合并时逐项运行验收器并处理相互矛盾的结论。多数 Agent 给出同一答案不等于正确，独立证据和可复现实验才有权重。

验算点：DAG 无环；每个节点只有一个最终 owner；关键路径不超过 deadline；共享状态无未定义并发写；父 Agent 能从子结果追到证据，并对最终结果承担验证责任。

## 10. 章末面试问题

### 典型问题

> 为什么不让一个 Agent 完成所有任务？多 Agent 的系统代价是什么？

### 30 秒答法

> Subagent 的主要价值是把边界清楚的子任务隔离到独立上下文，并在依赖允许时并行；Multi-Agent 进一步支持不同角色和协作拓扑。代价是委派协议、共享状态冲突、额外调用、错误传播和更大权限面。Infra 侧要维护任务树、分层预算、工作区隔离、取消传播、事件因果和孤儿回收。我会先证明任务可分解，再决定是否值得多 Agent，而不是默认数量越多越好。

### 常见追问

- 三个 Agent 投票为什么不一定比一个 Agent 准？
- 共享文件怎样避免丢失更新？
- 父 Agent 崩溃，子 Agent 是继续还是取消？
- 如何限制递归生成 Subagent？
- 不可信结果在 Agent 间传播时怎样保持权限边界？

### 常见追问参考答案

<details>
<summary>展开答案</summary>

- **投票未必更准：**三个 Agent 可能使用同一模型、上下文和错误资料，错误高度相关，多数票就会重复同一偏差。只有成员具备真实多样性、独立证据且聚合规则经过校准，投票才可能改善；还应在有标准答案的数据上比较单体与集成。
- **共享文件：**最稳妥的是按路径划分唯一 owner，或让各 Agent 在独立分支/工作区产生 patch。合并时检查基准版本、冲突和测试；必须共享写入时使用带版本的条件更新或事务，避免最后写入者覆盖别人未读到的修改。
- **父崩溃后的策略：**策略必须在委派前写入持久任务树。依赖父级交互或持有高风险权限的子任务应在父 lease 失效后取消；能独立产生可验证 artifact 的任务可在限定预算内继续，完成结果交给接管者。无论哪种都要有 owner lease 和孤儿回收。
- **限制递归：**预算沿任务树递减，并同时限制最大深度、每节点 fan-out、总 Agent 数、Token/费用、运行时间和并发槽。创建子任务要经过调度器原子扣减预算，不能只靠 Prompt 要求“少创建”。
- **权限边界：**子 Agent 的消息和 artifact 都按不可信输入处理，携带来源和完整性信息；接收方重新做 Schema、权限和内容校验。自然语言不能转移凭证，子 Agent 只能获得任务所需的短期最小权限，父级也不能通过一句话把超出自身范围的能力授予它。

## 11. 本章速记

- Subagent 强调父任务委派；Multi-Agent 强调多个 Agent 的协作结构。
- 价值来自上下文隔离、专业分工和并行，不来自“人数魔法”。
- 委派要带目标、输入版本、权限、预算、成功条件和 artifact。
- 并行减少关键路径，却可能增加总工作量和峰值资源。
- 任务树需要预算继承、取消传播、冲突处理和孤儿回收。
- Agent 间消息仍不可信，不能通过自然语言转移权限。
