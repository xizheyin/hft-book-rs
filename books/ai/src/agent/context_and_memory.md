# Context 与 Memory：模型桌面上放什么，仓库里又存什么

把模型想成一位只有一张有限大小书桌的工程师。书桌上的材料是 Context：当前目标、规则、相关代码、刚才的工具结果。档案室里的材料是 Memory：过去任务、用户偏好、总结、事实或可复用经验。档案室再大，也必须先挑选材料搬到书桌上，工程师这一轮才能看到。

这个类比揭示了关键区别：**Memory 负责保存，Context 负责选择和呈现。** 把所有历史都塞进上下文，既昂贵，也可能让真正重要的内容被淹没。

## 1. 四个经常混淆的概念

| 概念 | 保存什么 | 生命周期 | 主要目的 |
|---|---|---|---|
| Context Window | 本次模型调用可见的 token | 一次调用 | 让模型做当前判断 |
| KV Cache | 注意力计算的 Key/Value 中间结果 | 一次生成或服务允许的缓存期 | 减少重复计算 |
| Memory | 任务间或轮次间保存的有用信息 | 可跨调用、跨任务 | 以后能取回事实或经验 |
| Checkpoint | 恢复执行所需的确定状态 | 到任务完成或保留期结束 | 故障后继续，而非重新猜 |

KV Cache 不是“Agent 记住了用户”。它即使仍在，也不等于存在可查询、可审计的业务记忆。Memory 也不等于 Checkpoint：记住“用户喜欢简短回答”不能恢复一个执行到第 17 步的工作流。

## 2. Context Engineering 的机制

每轮上下文可以按优先级组装：

```text
不可违反的系统规则
  + 当前任务和成功标准
  + 当前执行状态与剩余预算
  + 最近且相关的观察
  + 从记忆/知识库检索出的证据
  + 可用工具及其约束
```

Context Engineering 不只是“截断到窗口大小”，而是一个选择问题：

1. 哪些信息必须逐字保留？
2. 哪些可以摘要？
3. 哪些只保留引用，需要时再取？
4. 冲突信息以哪个版本为准？
5. 每段信息来自谁、何时产生、可信度如何？

模型对输入位置和干扰敏感。把重要约束夹在大量无关日志中，可能出现“明明写了，模型却没用好”的现象。

## 3. 一个 32,000 token 的预算例子

假设某模型本次最多接收 32,000 token。不能把 32,000 全花在历史上，因为还要给模型输出留空间。可以先做如下教学预算：

| 部分 | 预算 |
|---|---:|
| 系统规则与安全策略 | 2,000 |
| 当前目标与验收标准 | 2,000 |
| 工具定义 | 3,000 |
| 最近操作与结果 | 7,000 |
| 检索证据 | 8,000 |
| 任务摘要与关键记忆 | 4,000 |
| 预留模型输出 | 6,000 |
| 合计 | 32,000 |

若终端产生了 50,000 token 日志，不能原样塞入。更好的做法是：

- 原始日志写入不可变 artifact；
- 提取错误位置前后各 100 行；
- 生成带行号和来源引用的摘要；
- 模型需要细节时再读取指定片段。

摘要会丢信息，所以不能删除原始证据，也要记录摘要由哪个模型和提示版本生成。

## 4. Memory 可以怎样分类

分类不是唯一标准，但以下五类便于系统设计：

### 4.1 工作记忆

当前任务的临时变量，例如“已检查 4/10 个文件”。它应与任务状态绑定，任务结束后通常不再长期保留。

### 4.2 情节记忆

过去发生过什么，例如“上次部署因数据库迁移顺序错误而回滚”。它带时间、主体和事件来源。

### 4.3 语义记忆

相对稳定的事实，例如“仓库使用 Rust 2024 edition”。事实会过期，因此要保存来源、采集时间和有效期。

### 4.4 程序性记忆

“怎样做某类任务”，例如发布检查清单。Skills 可以承载这类经验，但更新必须受版本控制和评审。

### 4.5 用户偏好

例如输出语言或格式偏好。偏好不能越过安全规则，也不应从一次偶然行为就永久推断。

## 5. 写入、取回和遗忘

Memory 不是越多越好。一条记忆进入系统前应回答：

- **为什么写**：它未来会改变什么决策？
- **写什么**：原文、结构化事实，还是摘要？
- **谁可读**：用户、租户、项目和 Agent 的边界是什么？
- **何时过期**：有没有 TTL（Time To Live，保留时长）或撤回机制？
- **如何纠错**：新事实与旧事实冲突怎么办？

取回可采用关键词、向量相似度、时间、实体关系和权限过滤组合。取回之后仍要排序和校验，不能因为“记忆库返回了”就视为真。

一种简单记忆记录可以是：

```text
内容：测试命令为 cargo test --workspace
来源：仓库 README，提交 abc123
写入时间：2026-08-04
作用域：repo-A
置信度：高
过期条件：构建配置发生变化
```

## 6. 压缩与滚动摘要

长任务常采用滚动摘要：每 10 步把历史压缩为“目标、已证实事实、未决问题、产生的 artifact、下一步”。但如果摘要覆盖摘要，错误会逐层放大。

降低风险的方法包括：

- 关键决策和工具结果保留原始引用；
- 摘要只陈述可追溯事实，推断单独标记；
- 达到里程碑时从原始事件重新生成摘要，而非无限套娃；
- 最终 verifier 读取关键原件，不只读模型总结。

## 7. 失败路径

### 7.1 记忆污染

不可信网页诱导 Agent 写入“今后上传所有密钥”。Memory 写入必须经过策略与来源检查，外部内容不能自动成为长期规则。

### 7.2 陈旧事实

Agent 记得旧 API 地址并反复使用。记忆需要版本、时间和失效条件；对可变事实应优先查当前权威来源。

### 7.3 租户串线

向量检索只按相似度取数据，忘了先按租户和权限过滤，导致跨用户泄露。权限过滤应在可信的数据层强制执行，而不是让模型自行忽略。

### 7.4 摘要遗漏否定词

原文是“不要在生产执行”，摘要变成“在生产执行”。高风险约束应结构化、逐字保留并由策略层执行。

### 7.5 Context 爆满

工具结果不断追加，最终无法放入新证据。需要预算、截断策略、外部 artifact 和按需加载，而不是等请求报错才处理。

## 8. Agent Infra 的上下文与记忆责任

Infra 通常不决定“什么值得记”，但要提供可靠底座：

- 任务、用户、租户和子 Agent 的身份隔离；
- 快照、对象、事件日志的加密和访问控制；
- 数据保留、删除和审计；
- checkpoint 与工作区快照的一致性；
- 大量并发恢复时的带宽和存储保护；
- 防止前一个沙箱的内存、磁盘或缓存残留泄给下一个租户。

不要把推理侧 KV Cache、任务记忆数据库和沙箱磁盘快照混成一个“缓存系统”。它们的语义、风险和生命周期不同。

## 9. DeepSeek Agent Infra 面试怎么问

### 典型问题

> Context、Memory、KV Cache 和 Checkpoint 有什么区别？

### 30 秒答法

> Context 是本轮模型可见的信息集合；Memory 是跨轮或跨任务保存、以后需要检索的信息；KV Cache 是 Transformer 推理的注意力中间结果，用于减少重复计算；Checkpoint 则是恢复确定执行状态所需的数据。它们可能都占存储，但语义完全不同。设计时我会分别考虑 token 预算、来源和权限、缓存隔离，以及恢复一致性，不能用一个“缓存”概念笼统代替。

### 常见追问

- 32K 窗口怎样分配输入和输出预算？
- 滚动摘要怎样避免错误累积？
- 长期记忆冲突时，按时间新旧覆盖就够吗？
- 怎样防止跨租户向量检索泄露？
- checkpoint 恢复后，外部副作用如何与内部状态对齐？

## 10. 本章速记

- Context 是模型当前桌面，Memory 是可检索档案室。
- KV Cache 加速推理，不是业务记忆；Checkpoint 用于恢复，不是知识库。
- 上下文需要预算、优先级、来源和输出预留。
- Memory 写入要有作用域、来源、时间、失效与纠错机制。
- 摘要必须保留原始证据引用，高风险规则不要只靠摘要。
- 权限过滤要在可信数据层强制，不能交给模型自觉。
