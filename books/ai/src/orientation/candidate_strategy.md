# 候选人作战地图：把 Rust、可靠性与 Agent Infra 串成一条线

这一章解决的不是“怎样把简历从头背到尾”，而是一个更重要的问题：**面试官为什么应该相信，你过去解决的问题能迁移到 AI Agent 基础设施？**

先用一个通俗比喻。大模型像一位知识很多、动作很快，但偶尔会误解指令的实习生；Agent Infra 则像实验室和生产车间的总管，要为它准备工具、限制权限、记录过程、检查结果，并在失败时安全收场。候选人的优势并不是“我用过某个聊天界面”，而是长期在编译器、静态分析、低延迟系统和 Agent 评测里做同一类事情：**把隐含假设变成明确边界，把不确定输出放进可验证的执行流程。**

> 事实边界：本章只使用简历中可以核实的经历。某量化机构保持匿名；Reaper 的状态是 **OOPSLA 2026 Revision**；SkillFuzz 与 Rust 生态漏洞传播工作均为 **ICSE 2027 Under Review**，都不能说成“已录用”。岗位能力矩阵是面试准备框架，不代表任何公司的内部评价标准。

## 1. 30 秒答法

面试开场可以这样说：

> 我的主线是可靠执行。我长期参与 rustc 和 Rust 安全研究，习惯用类型、所有权、不变量和测试控制系统风险；在生产级高频期货系统的 C++ 到 Rust 迁移中，我又把这种方法用于关键数据路径，用 replay、影子验证和逐事件对齐，在所覆盖样本上验证语义一致性，并为 Coding Agent 设置上下文、工具和验证门禁。我的 SkillFuzz 研究进一步把 Agent Skill 当作可测试的软件制品，通过 verifier、配对运行和轨迹审查区分 Skill 缺陷与模型能力不足。因此我希望做的 Agent Infra，不只是“让 Agent 能调用工具”，而是让它可隔离、可观测、可恢复、可验证。

这段话有四个组成部分：定位、证据、方法、岗位迁移。不要在 30 秒里罗列所有论文和奖项。

## 2. 岗位能力矩阵

表中的“证据等级”不是给人贴标签，而是提醒自己：哪些能力可以直接拿经历证明，哪些只能说“我正在补”。

| 能力 | 面试官真正关心什么 | 简历中的可核实证据 | 证据等级 | 面试策略 |
|---|---|---|---|---|
| 系统编程 | 能否管理内存、并发、生命周期和性能边界 | Rust/C++ 生产迁移；rustc 长期贡献；unsafe API 检查 | 强 | 用一个具体不变量和一次性能测量说明，不只谈语言特性 |
| 文件与 Linux I/O | 能否讲清 `write`、页缓存、文件系统、块层、持久化与排障 | 简历未直接给出完整文件写入链路证据 | 证据缺口 | 作为主岗核心系统知识补齐，并通过 `strace`/I/O 实验验证 |
| 虚拟化与容器 | 能否比较 namespace/cgroup、容器、用户态内核、VM 与快照 | 简历未证明大规模 VM/沙箱生产经验 | 明显缺口 | 从隔离边界和实测取舍回答，不把练习方案说成经历 |
| 沙箱存储与网络 | 能否设计临时块设备、共享卷、虚拟网络和租户隔离 | 简历未直接证明相关生产运营经验 | 明显缺口 | 补齐一致性、fencing、MTU、conntrack、出口和故障语义 |
| Agent 执行可靠性 | Agent 跑偏时如何发现、停止、恢复 | Coding Agent harness、工具约束、验证门禁；SkillFuzz verifier 与轨迹审查 | 方法证据强；生产运营缺口 | 把 Agent 描述成“不可信执行者”，同时明确没有通用平台 SLA/恢复率证据 |
| 评测与实验设计 | 怎样证明改进来自方案本身 | SkillFuzz 有/无 Skill 配对；参考解准入；误报审查 | 强 | 主动讲因果归因、随机性、误报和结论边界 |
| 安全 | 是否理解输入、内存、工具和权限的攻击面 | Reaper、RustSec 研究、Vec unsafe API 检查、供应链研究 | 软件安全方法证据强；沙箱运营缺口 | 说明方法可迁移但机制不同，不能把 Rust 安全研究等同于沙箱运营 |
| 低延迟与性能 | 是否会测量，而非凭感觉优化 | 离线 replay 的 p50/p99 改善 10%-20%；rustc-perf | 中强 | 必须补齐基线、硬件、样本、预热和个人贡献范围 |
| 大型代码库协作 | 能否在复杂项目中拆解并落地变更 | rust-lang/rust 106 PR、83 merged；Buck2 3 个上游 PR | 强 | 讲评审反馈、拆 PR 依据和兼容性，而非只报数量 |
| 数据与后端基础设施 | 能否处理流、图、存储与增量更新 | Crates-Pro；Kafka、PostgreSQL、TuGraph、OpenAPI | 中 | 补充幂等、背压、一致性、故障恢复；不要虚构线上指标 |
| 分布式任务系统 | 是否理解队列、租约、重试和部分失败 | 简历未直接给出完整生产平台证据 | 证据缺口 | 用系统设计题展示方法，并明确哪些是练习设计 |
| 模型推理基础 | 是否理解 token、prefill/decode、KV Cache、批处理 | 简历未明确写出 | 证据缺口 | 面试前补课；不能用 Rust 经历代替模型系统知识 |
| GPU 与模型服务 | 是否理解显存、调度、并行和吞吐/延迟权衡 | 简历未明确写出 CUDA、GPU 服务或推理框架 | 明显缺口 | 坦诚边界，先掌握原理和容量估算，再谈可迁移能力 |
| 生产运维 | 是否做过发布、监控、回滚、值班和事故处理 | 简历有构建、验证和数据链路，但没有 SLA/值班指标 | 证据缺口 | 准备一个故障演练设计；不声称不存在的 on-call 经历 |
| 沟通与教学 | 能否把复杂问题讲清并推动合作 | Rust 教材 10 万余字；多学期助教；课程评分 4.68→4.91 | 强 | 用通俗解释展示，不把奖项变成主叙事 |

### 2.1 备考权重

面向该系统基础设施岗位，本书后续练习按下面比例分配时间，而不是平均用力：

- **核心系统 60%**：先补 CPU/内核、进程线程、虚拟内存、并发与 TCP/RPC，再进入 Linux I/O、容器/VM、临时存储、虚拟网络、控制面、可靠性、HA、压测和事故响应。
- **Agent 20%**：Agent loop、工具协议、状态、verifier、上下文、评测和安全执行边界。
- **简历 20%**：HFT、rustc/Buck2、Crates-Pro 与研究工作的事实核验和事件级故事。

LLM 与 GPU 知识用于理解上游负载，不应挤占主岗明确要求的系统基础。

## 3. 三条主叙事

### 3.1 第一条：从“内存安全”走向“Agent 行为安全”

Rust 的所有权系统不能直接阻止模型产生错误指令，但两类问题的工程方法很相似：

1. 先定义谁拥有资源、谁可以修改、资源活多久。
2. 把隐式约定写成接口、类型、权限或状态机。
3. 在边界做检查，而不是相信调用者一定正确。
4. 为违规留下可复现证据，并让失败安全终止。

可以把简历中的三段经历连起来：

- Reaper 研究 safe API 背后的 unsafe 实现是否真的守住契约。
- 生产迁移把裸指针、共享对象和回调的隐式依赖变成 Rust 模块与所有权边界。
- Agent Infra 则要把模型生成的意图变成经过 schema、权限、沙箱和 verifier 检查的动作。

高分点是说明“方法可以迁移，机制并不相同”。不要说“用了 Rust，Agent 就安全了”。

### 3.2 第二条：从“结果能跑”走向“结果可证明”

Agent Demo 很容易令人兴奋：模型读代码、改文件、测试通过，看上去任务完成了。但生产系统关心的是：测试是否覆盖关键语义？工具是否越权？失败能否回放？答案是否由错误的 verifier 放行？

候选人可以用两组事实回答：

- 高频系统迁移中，Rust 与 C++ 参考实现做 replay 和影子验证，逐事件对齐解析、订单簿、特征与 Alpha 输出。
- SkillFuzz 先执行参考解和 verifier，过滤无确定答案的任务；再做有/无 Skill 配对，并审查轨迹，最终从 79 个候选中排除 31 个误报，确认 48 个严格缺陷。

这里最重要的不是数字大，而是说明**验证链条会主动怀疑自己**。

### 3.3 第三条：从“个人研究原型”走向“大型工程落地”

Agent Infra 岗位通常不只看研究想法，还看变更怎样进入复杂系统。可以用 rustc 和 Buck2 证明：

- 在 rustc 诊断框架中处理状态生命周期和不变量，变更随 Rust 1.90 发布。
- 为 Vec 多个 unsafe API 添加可选 UB 前置条件检查，并用 run-fail 路径与 rustc-perf 控制正确性和性能风险。
- Buck2 RISC-V 支持按依赖拆为 3 个 PR，在 RISC-V Debian 验证，最终被上游导入。

这条主线要回答“怎样降低合入风险”：缩小变更面、先建立测试、按依赖顺序落地、尊重评审者的上下文。

## 4. 强项怎样讲得可信

### 4.1 用“不变量”替代空泛形容词

不要说：“我特别重视可靠性。”

可以说：“我会先写出不能被破坏的条件。例如逐事件迁移中，同一输入序列经过 C++ 和 Rust 后，订单簿状态、特征值和 Alpha 输出必须在定义好的比较规则下对齐；Agent 产物必须通过为任务配置的验证门禁，再由人类作最终审计。”这里不额外声称简历没有记录的具体门禁组合。

### 4.2 用“决策与取舍”证明是本人做的

面试官会特别关注 20 万行迁移中，人、团队和 Agent 分别做了什么。答案应该区分：

- 人负责：业务语义、架构边界、风险判断、验收标准和最终审计。
- Agent 可负责：受约束的代码理解、迁移、验证和测试任务。
- 验证系统负责：用固定版本、可审计且尽量确定的检查拒绝不满足条件的产物；不稳定结果不能自动放行。

只有简历已经证明“累计迁移与验证约 20 万行”和“负责关键路径”。具体个人代码量、团队人数、模型名称、成功率和成本若没有记录，就不要现场猜。

### 4.3 主动讲限制，反而更专业

例如 Reaper 的告警级精确率是 51.6%。不要绕开这个数字。可以解释静态分析通常在召回和误报之间取舍，然后继续回答：误报来自哪些近似？如何排序？真实使用者能否在合理时间内审查？哪些结论只适用于评测数据？如果论文没有给出某项细分结果，就明确说需要回到实验记录核对。

## 5. 证据缺口怎样处理

### 5.1 模型与推理系统

简历没有明确证明 GPU 推理服务经验。正确说法是：

> 我的直接生产证据集中在 Rust 系统、可靠性和 Agent 执行验证，而不是 GPU kernel 或大规模模型服务。我会把两者分开。对理解 Agent 上游负载所需的 token、prefill/decode、KV Cache 和批处理，我正在按系统问题补齐；只有通过脱稿推导和模拟追问后，我才会说自己已经掌握。如果问题进入 CUDA kernel 的实现细节，我会先说明经验边界，再给出验证思路。

错误说法是：“底层系统都一样，所以我很快就会。”可迁移能力需要现场通过推导证明，不能靠口号。

### 5.2 分布式系统与线上运维

Crates-Pro 能证明接触过 Kafka、PostgreSQL、图数据库和增量更新，但简历没有 QPS、SLA、值班或事故数据。回答时应从已知事实出发，再给出设计方法：幂等键、offset、背压、死信队列、重放、监控和一致性检查。练习方案必须标成“如果由我设计”，不能伪装成过去已经上线的实现。

### 5.3 当前量化实习的可核验性

**面试前阻塞项：HFT 测量卡。** “约 20 万行”和“p50/p99 改善 10%-20%”会带来高强度追问。以下项目必须用本人真实记录填写；任何一项不知道就标为“未记录/不能公开”，不能补造数字：

- 哪些组件在统计范围内；
- “迁移与验证”而非“个人手写”的准确含义；
- 输入数据、交易日和交易组合怎样抽样；
- p50/p99 测的是什么阶段、采用什么时钟和预热；
- C++ 与 Rust 的编译选项和运行环境是否可比；
- 一次语义不一致怎样被发现并定位；
- 仍未覆盖的情况是什么。

在这张卡填写并完成一次五层追问前，10%-20% 只能按简历原句陈述，不能归因于某项优化。若受保密协议限制，可以解释方法与匿名化例子，但不能用“保密”代替所有技术细节。

## 6. 面试定位：一句主张，三根支柱

建议把整场面试压缩成如下结构：

```text
主张：我擅长把不确定的 Agent 行为装进可靠的系统边界。

支柱 A：系统边界
Rust/C++、所有权、rustc、低延迟关键路径

支柱 B：验证证据
replay、影子验证、verifier、配对评估、轨迹审查

支柱 C：安全执行
unsafe 契约、供应链风险、工具权限、沙箱、人工门禁
```

遇到陌生问题时，也可回到四步：

1. 先澄清成功标准与风险。
2. 画出状态、数据、信任边界。
3. 给出可观测、可恢复的执行路径。
4. 用实验或 verifier 说明怎样证明它有效。

## 7. 常见失分点

- 把 Under Review、Revision 说成已录用，属于事实性硬伤。
- 用 PR 数量代替技术深度，却说不出一个关键设计取舍。
- 将“累计迁移与验证约 20 万行”讲成“我手写了 20 万行”。
- 只说 Agent 提效，不说错误率、验证成本、人工责任和失败案例。
- 把 `unsafe`、`RefCell` 或 C++ 描述成“坏技术”；真正问题是证明责任和边界是否清晰。
- 声称 Rust 天然解决 prompt injection、越权调用或模型幻觉。
- 没有测量口径就复述 10%-20% 性能提升。
- 对不熟悉的 GPU、Kubernetes 或模型训练细节强行包装成已有经验。
- 一被问到保密项目就完全停止解释；应准备匿名的数据流、故障类型和验证方法。
- 把整场面试讲成论文报告，忽略用户需求、工程成本和故障恢复。

## 8. 本章速记

- 核心定位：**可靠执行，而非简单工具调用。**
- 最强证据：Rust/rustc、生产迁移、SkillFuzz、Reaper、replay/verifier。
- 最大缺口：文件写入、VM/容器、临时存储、虚拟网络、完整分布式沙箱平台和生产运维指标；模型推理属于相邻知识缺口。
- 事实红线：某量化机构匿名；Reaper 是 Revision；两篇 ICSE 2027 是 Under Review。
- 回答公式：**问题 → 不变量 → 设计 → 验证 → 结果 → 限制。**
- 下一步：用[简历深挖](../interview/resume_drill.md)准备事实追问，再用[系统设计](../interview/system_design.md)练习把能力迁移到 Agent 平台。
