# Linux 开发与排障：从崩溃、卡住和变慢找到证据

程序出问题时，“可能是网络”“可能是锁”“重启试试”都不是诊断结论。可靠排障要先把症状分成三类：**crash（进程异常退出）、hang（进程仍在但没有按预期推进）、slow（仍能完成但耗时或吞吐恶化）**。三类问题使用的证据不同，但都遵循同一条链：固定对象和时间窗，保留现场，提出可证伪假设，用最小实验验证，修复后加入回归检查。

本章用一个名为 `worker` 的普通 Linux 服务串起 shell、`/proc`、权限、GDB、core dump、`strace`、`perf`、Sanitizer、网络与内存证据。命令中的进程号和路径只是示例；在生产环境附加调试器、抓取参数或生成 core 前，必须确认权限、性能影响与敏感数据要求。

## 1. 先分清你观察到的是什么

| 现象 | 最先确认 | 典型证据 |
|---|---|---|
| crash | 退出时间、退出码或终止信号、二进制版本 | 服务管理器记录、stderr、core、崩溃线程栈 |
| hang | 进程是否仍活着、线程在运行还是等待、外部依赖是否推进 | 线程栈、`wchan`、系统调用、锁与队列指标 |
| slow | 哪个指标变差、从何时开始、影响哪些请求 | 分阶段 trace、CPU/Off-CPU profile、磁盘和网络队列 |

“请求超时”不一定是 hang。服务可能仍在计算，只是 deadline 太短；也可能服务已经完成，响应卡在网络；还可能请求根本没有到达。先给出可观察定义，例如：

```text
对象：worker 进程 18420，构建提交 abc123
窗口：10:03:00—10:08:00
症状：健康检查仍成功，但 93% 业务请求超过 2 s
正常基线：相同请求 p99 为 80 ms
```

有了对象、版本、时间窗和基线，后面的日志、栈和指标才能互相对齐。

## 2. Shell 负责组织程序，不是内核本身

输入下面的命令时，shell 解析引号、通配符、重定向和管道，再创建相应进程：

```bash
./worker --config 'config with spaces.toml' >worker.out 2>worker.err
```

- 单引号让带空格文本成为一个参数；
- `>` 把标准输出 file descriptor（fd，文件描述符）1 写入文件；
- `2>` 把标准错误 fd 2 写入另一个文件；
- `./worker` 中的 `./` 表示当前目录；若只写 `worker`，shell 通常按 `PATH` 搜索。

管道 `|` 把左侧进程的标准输出连接到右侧进程的标准输入：

```bash
printf '%s\n' alpha beta gamma | rg 'beta'
```

管道两侧通常是不同进程，它们可以并发推进。左侧退出不代表右侧成功；若脚本依赖整条管线结果，应了解当前 shell 的 `pipefail` 规则并逐步验证输入输出。

查看上一条简单命令的退出状态可使用 `$?`。按惯例 0 表示成功，非 0 表示某类失败，但精确含义由程序文档定义。被信号终止时，shell 和服务管理器可能用不同形式显示状态，因此排障记录应直接保存信号名称和原始服务日志，不只抄一个数字。

### 2.1 权限位在回答“谁能做哪种访问”

```bash
ls -l ./worker ./config.toml
namei -l /srv/app/config.toml
```

普通文件的 `r/w/x` 分别表示读、写、执行；目录的 `x` 更接近“允许穿过并访问已知名字”，目录 `r` 则与列出名字有关。访问 `/srv/app/config.toml` 需要路径上每级目录都允许相应穿过，不能只看最终文件一行权限。

```bash
id
stat ./worker ./config.toml
getfacl ./config.toml
```

`id` 显示当前 uid（user ID，用户编号）、gid（group ID，组编号）与附加组；`stat` 显示文件元数据；系统若使用 ACL，还要用 `getfacl` 查看普通三组权限位之外的规则。容器、挂载选项、Linux Security Module 和服务管理器沙箱也可能进一步拒绝访问。`chmod 777` 会扩大攻击面并掩盖真正身份问题，不是通用修复。

## 3. `/proc` 把内核中的进程视图暴露成文件

Linux 的 procfs 通常挂载在 `/proc`。`/proc/<pid>/` 中的许多文件由内核动态生成，不是磁盘上的普通持久文件。

```bash
app_pid=18420
readlink "/proc/$app_pid/exe"
tr '\0' ' ' <"/proc/$app_pid/cmdline"
sed -n '1,45p' "/proc/$app_pid/status"
ls -l "/proc/$app_pid/fd"
```

这些命令分别帮助确认实际二进制、参数、进程状态与打开 fd。命令行、环境变量、fd 目标和 core 都可能包含秘密；不要把完整输出直接贴入公开工单。

常用字段要结合语义：

- `State` 表示当前瞬时状态；一次采样看见 sleeping 不代表进程永久卡住；
- `Threads` 是线程数量；持续增长可能意味着泄漏，也可能是正常线程池扩容；
- `VmSize` 是虚拟地址范围量级，`VmRSS` 是当前驻留物理页量级；二者都不等于应用独占内存；
- `/proc/<pid>/fd` 显示 fd 引用的对象，但打开很多 fd 是否异常要与连接、文件和上限基线比较。

`ps` 提供更适合批量阅读的快照：

```bash
ps -o pid,ppid,user,stat,wchan:32,etime,%cpu,%mem,cmd -p "$app_pid"
ps -L -o pid,tid,stat,wchan:32,pcpu,comm -p "$app_pid"
```

`wchan` 表示内核观察到的睡眠等待位置，只是线索，不是完整调用栈。线程在 `futex` 等待可能是在等 mutex、condition variable 或运行时内部同步，需要结合用户栈和应用状态才能判断。

## 4. Crash：先保存退出原因和崩溃现场

假设 `worker` 被 `SIGSEGV` 终止。`SIGSEGV` 表示进程进行了无效内存访问等受保护操作；它指出故障表现，不自动告诉你是哪一行业务逻辑造成了坏指针。

第一步保存：

1. 发生时间和请求/任务标识；
2. 精确二进制、调试符号、源代码提交和动态库版本；
3. 退出状态、信号、stderr 与服务管理器日志；
4. core dump，或无法生成 core 的明确原因；
5. 触发输入的脱敏副本和最小复现步骤。

### 4.1 为什么需要调试符号

编译器把源代码变成机器指令。调试符号保存机器地址到函数、文件、行和变量等信息的映射。没有匹配符号时，core 里仍有寄存器和内存，调用栈却可能只剩地址或不完整名称。

以 C++ 为例，可为诊断构建保留符号和帧指针：

```bash
c++ -std=c++20 -O1 -g -fno-omit-frame-pointer worker.cpp -o worker
```

`-O1` 仍会优化，变量可能被合并或消除；`-O0` 更接近源码但也可能改变时序和内存布局。生产 Release 可以把符号拆分并安全归档，不必把所有调试信息暴露给最终运行环境。符号必须与崩溃二进制逐字节对应，拿“差不多同一版本”的符号会得到误导栈。

### 4.2 用 GDB 复现崩溃

```bash
gdb --args ./worker --config config.toml
```

进入 GDB 后，常用的最小顺序是：

```text
(gdb) run
(gdb) bt
(gdb) thread apply all bt
(gdb) frame 0
(gdb) info args
(gdb) info locals
```

`bt` 查看当前线程回溯；并发程序还要看所有线程，避免只盯住接收信号的线程。切到可疑 frame 后检查参数、局部变量与源码。优化构建中的变量可能显示为 optimized out，这不是 GDB 损坏，而是机器代码已经不再保留对应独立值。

### 4.3 用 core 在进程退出后还原现场

core 是否生成受 shell 上限、内核 `core_pattern`、服务管理器和存储策略共同影响。开发机上可以先查看：

```bash
ulimit -c
cat /proc/sys/kernel/core_pattern
```

在允许生成且数据政策明确的隔离环境中，可为当前 shell 调整 core 大小上限后复现。使用 systemd-coredump 的机器常通过：

```bash
coredumpctl list worker
coredumpctl info worker
coredumpctl debug worker
```

另一类环境会得到 core 文件，再用匹配二进制打开：

```bash
gdb ./worker /path/to/core
```

core 可能包含内存中的凭证、用户数据和模型输入，应像生产数据一样限制访问、保留与传输。分析完成后也不能只写“空指针”；要继续追踪这个非法状态是怎样产生并跨过哪些检查的。

## 5. Hang：区分等待、死锁、忙循环与外部停滞

服务不返回时先问：CPU 在工作，还是线程都在等待？

```bash
top -H -p "$app_pid"
ps -L -o pid,tid,stat,wchan:32,pcpu,comm -p "$app_pid"
```

- 某线程持续接近一个核心的 CPU，可能是忙循环、大量计算或频繁重试；
- 多个线程长期睡眠，可能是在正常等队列，也可能在等永远不会发生的唤醒；
- `D` 状态常表示不可中断的内核等待，需继续看块设备、文件系统或驱动证据；
- 进程低 CPU 也可能是外部 RPC、锁或磁盘等待，不能直接说“机器不忙”。

### 5.1 `strace` 观察系统调用边界

```bash
strace -f -ttT -p "$app_pid"
```

- `-f` 跟踪线程/子进程；
- `-tt` 记录时间；
- `-T` 记录每次系统调用耗时；
- `-p` 附加到现有进程。

若一个线程长时间停在 `futex`，说明它在某类用户态同步等待；若停在 `epoll_wait`，可能只是事件循环没有可用事件；若 `read` 卡住，要判断 fd 是 socket、pipe 还是设备。系统调用名称只给出边界，最终仍要结合线程栈、fd、协议和队列状态。

附加 `strace` 需要相应 ptrace 权限；ptrace 是 Linux 允许一个进程观察或控制另一个进程的调试接口。跟踪还会扰动时序、捕获参数。高流量进程应缩小系统调用、线程和时间范围，并先在可控环境验证开销。

### 5.2 GDB 线程栈回答“用户代码在等谁”

```bash
gdb -p "$app_pid"
```

```text
(gdb) info threads
(gdb) thread apply all bt
```

附加调试器通常会暂时停止线程，所以不能在没有变更窗口的关键生产进程上随意执行。若多条栈形成 `A 持有 lock_x 等 lock_y，B 持有 lock_y 等 lock_x`，才有死锁证据。只看到线程在 mutex 上等待不够：它也可能很快被正常唤醒。

忙循环则可用短时间 CPU profile 找热点，并检查循环退出条件、错误重试、EOF 处理和时间比较。对队列系统还要记录生产、消费、容量和满载策略；“消费者没动”可能是上游根本没有发布数据。

## 6. Slow：先拆时间账，再定位 On-CPU 与 Off-CPU

一次请求的总耗时可以拆成：

```text
排队 + 用户态计算 + 内核/设备 I/O + 下游等待 + 返回与序列化
```

只测总耗时会把不同原因揉成一个数字。先用应用 trace 或阶段时间戳确定哪一段变化，再选择系统工具。

### 6.1 CPU 快照与计数器

```bash
pidstat -p "$app_pid" 1
perf stat -p "$app_pid" -- sleep 10
```

`pidstat` 观察随时间变化的 CPU、上下文切换等进程指标；`perf stat` 汇总指定窗口的硬件/软件事件。计数器可用性受硬件、内核和权限影响；cycles、instructions、cache-misses 要除以工作量或组合成 IPC、miss rate 等比例，不能只看原始大数。

采样调用栈：

```bash
perf record -F 99 -g -p "$app_pid" -- sleep 30
perf report
```

采样表示“定期观察正在执行哪里”，不是记录每一次调用。热点占比是当前采样窗口中的相对 CPU 时间；某函数从 20% 降到 10%，可能因为它变快，也可能因为其他函数变慢。优化前后必须用相同工作量、版本和环境比较绝对结果。

On-CPU profile 适合回答 CPU 时间花在哪里。请求大多在睡眠等待时，应看 Off-CPU 时间、调度、I/O 与锁证据；只做 CPU 火焰图可能看不到主要等待。

### 6.2 内存、磁盘和调度证据

```bash
sed -n '1,80p' "/proc/$app_pid/status"
cat "/proc/$app_pid/smaps_rollup"
vmstat 1
iostat -xz 1
```

- `status` 与 `smaps_rollup` 帮助区分虚拟地址、RSS、共享/私有页面等量级；
- `vmstat` 观察整机运行队列、内存回收、swap、I/O 与 CPU 状态；
- `iostat -xz` 观察块设备吞吐、等待与队列相关指标。

这些是不同层的指标。进程 RSS 上升不等于物理内存泄漏；页缓存和共享映射会影响记账。磁盘利用率高也不自动证明某个请求被它阻塞，需要用进程 I/O、trace 或系统调用把设备现象连接到目标工作。

内存持续增长时，先按对象类型和时间做 heap profile 或分配追踪；仅在 OOM 后看最终 RSS，无法说明哪些分配没有释放。分配 profiler 会改变布局和速度，应把诊断结果与生产性能测量分开。

## 7. 网络证据：连接存在不等于请求在推进

```bash
ss -tanp
ss -tinp
ip -s link
```

`ss` 可查看 TCP 状态、队列与部分内部信息；`ip -s link` 查看接口层收发和丢弃计数。使用端口、地址、进程和时间窗过滤输出，避免在大量无关连接中找故事。

排障时至少分四段：

1. 名称解析和目标地址是否正确；
2. 连接是否建立，TLS/应用握手是否完成；
3. 请求字节是否发送，接收队列或发送队列是否持续积压；
4. 远端是否处理并返回业务响应。

TCP `ESTABLISHED` 只表示连接状态，不保证应用线程正在读取，也不保证远端业务成功。大量 `TIME_WAIT` 可能来自正常的主动关闭，也可能说明连接没有复用；必须结合连接创建率、端口范围和业务设计判断。

抓包能提供包级证据，但可能包含用户数据和凭证，也会增加存储与分析成本。优先从应用 trace、socket 指标和有限过滤开始，只有确实需要协议证据时才按权限和脱敏要求抓取。

## 8. Sanitizer 让隐藏错误更早暴露

对 C/C++，编译器 Sanitizer 通过插桩发现一部分运行时错误：

```bash
c++ -std=c++20 -O1 -g -fno-omit-frame-pointer \
  -fsanitize=address,undefined worker.cpp -o worker-asan

c++ -std=c++20 -O1 -g -fno-omit-frame-pointer \
  -fsanitize=thread worker.cpp -o worker-tsan
```

- ASan 发现许多越界、释放后使用等内存问题；
- UBSan 检查一部分未定义行为，例如某些错误移位和有符号溢出；
- TSan 发现许多实际执行到的数据竞争。

通常分别运行 ASan/UBSan 与 TSan。插桩会改变内存布局、调度和速度，所以 Sanitizer 下的延迟不能代表生产性能；“本次通过”也不是没有所有内存或并发错误的证明。发现报告后应保留触发输入、完整栈和工具版本，定位第一次非法访问，而不是只修最终崩溃点。

Rust 的 Safe Rust 能排除一类内存错误，但 `unsafe`、FFI、数据竞争协议和业务边界仍需专门验证。相应方法见[Unsafe Rust](../foundations/unsafe_rust.md)、[模糊测试与属性测试](../testing/fuzzing.md)与[C++ 错误、异常和未定义行为](../cpp/errors_ub.md)。

## 9. 一个完整的三症状推演

### 9.1 Crash：解析请求时偶发 `SIGSEGV`

1. 从服务管理器确认 `SIGSEGV`、时间和构建 ID；冻结自动反复重启造成的日志覆盖。
2. 保存 core、匹配符号和脱敏输入；用 GDB 查看所有线程栈。
3. 栈显示 C++ 解析器访问已释放缓冲，但这只是表现；继续追踪缓冲所有者与异步回调的生命周期。
4. 用相同输入在 ASan 构建复现，报告定位第一次 use-after-free。
5. 修复所有权，让回调持有合法对象或只在所有者存活期执行；添加回归测试和取消交错测试。
6. 在未插桩 Release 上重新验证正确性与性能，不能把 ASan 结果当性能结论。

### 9.2 Hang：取消后任务永远不结束

1. 确认进程存活、目标任务状态停止推进，而其他任务是否正常。
2. `ps -L` 显示线程大多睡眠；有限时间 `strace` 看到一个线程长期等待 `futex`。
3. GDB 全线程栈显示主线程在 `join` 等子线程，子线程在等待一个只有主线程会发送的停止事件，形成循环等待。
4. 把取消协议改为先发布停止并唤醒，再等待线程退出；为每个等待增加状态和 deadline。
5. 测试“取消发生在启动前、工作中、完成同时”三种时序，并检查没有孤儿线程。

### 9.3 Slow：发布后 p99 从 80 ms 变成 900 ms

1. 对比同流量下的新旧版本；trace 显示多出的时间在结果序列化，不在网络。
2. `perf` 采样发现格式转换函数占 CPU 大头；工作量指标显示每请求转换次数增加约 20 倍。
3. 代码差异表明新日志在循环内重复把同一对象转换成 JSON，且即使日志级别关闭也先构造字符串。
4. 把格式化移到真正需要的分支，并缓存一次可复用结果；保持日志字段和错误路径不丢失。
5. 用固定数据验证输出等价，再在相同环境比较 CPU/request、吞吐和 p99；上线时观察错误率与队列，准备回滚。

## 10. Git 与 CI 只负责让证据可复现

Git 是分布式版本控制系统；CI（Continuous Integration，持续集成）是在共享环境中自动构建和验证改动的流程。它们不能替你找出根因，但能回答“哪些内容变了”、哪个版本首次失败，以及同一规则能否被重复执行：

```bash
git status --short
git diff --stat
git diff
git log --oneline --decorate -n 20
```

排障前先保存未提交改动，避免把实验修改误当生产版本。若存在稳定、快速且无副作用的自动判定，可以用 `git bisect` 在已知好版本与坏版本间二分查找首次引入回归的提交。判定脚本不稳定时，bisect 只会快速得到错误结论。

每次性能或崩溃记录至少绑定：commit、构建选项、编译器、依赖锁定文件、运行参数、机器/内核和输入摘要。CI 再把可重复规则自动执行，例如：

```text
格式/静态检查
→ Debug 与 Release 构建
→ 单元/集成测试
→ 分开的 ASan/UBSan/TSan 作业
→ 受控基准与回归阈值
→ 构建可识别、可追溯的产物
```

不要把波动大的微基准简单设成“一慢 1% 就失败”，也不要让 CI 只打印失败而丢弃符号、日志、测试输入和环境信息。发布与回滚见[生产环境部署](deployment.md)，CMake、编译器和 perf 贯通示例见[C++ 优化与诊断工具](../cpp/optimization_tooling.md)。

## 11. 常见误区

1. **“进程还在就是死锁。”** 它可能正常等 I/O、做长计算或因上游没有数据而空闲。
2. **“CPU 低说明服务没问题。”** 锁、网络、磁盘和下游等待都可能让 CPU 很低。
3. **“看到 `futex` 就证明 mutex 有 bug。”** futex 是多种用户态同步的内核等待机制，还需用户栈与所有权证据。
4. **“core 总会生成在当前目录。”** 上限、`core_pattern` 和服务管理器共同决定收集路径。
5. **“没有符号也可以用相邻版本猜栈。”** 不匹配地址映射可能把根因指向完全错误的函数。
6. **“火焰图最宽的函数一定有 bug。”** 它只说明采样窗口中 CPU 占比高；要结合必要工作量与绝对性能。
7. **“`ESTABLISHED` 证明 RPC 正常。”** 它只说明 TCP 连接状态，不说明应用请求与响应完成。
8. **“TSan 通过证明无锁算法正确。”** 它不枚举全部交错，也不证明业务不变量。
9. **“权限失败就 `chmod 777`。”** 这扩大访问范围并掩盖真正身份、路径或策略问题。
10. **“bisect 找到提交就等于找到根因。”** 提交只是首次可观察变化，还要解释机制并用回归测试证明。

## 12. 做题与排障方法：证据矩阵

1. 写明对象、版本、时间窗、症状和正常基线；缺一个就先补一个。
2. 把假设写成可证伪句子，例如“线程池全部等待同一把锁”，并列出支持或推翻它需要的栈、指标和实验。
3. Crash 题按“退出原因 → core/符号 → 崩溃栈 → 第一次非法状态 → 触发输入”逆推。
4. Hang 题先分 On-CPU 与等待；等待再按锁、I/O、队列、下游和定时器分类，并画出谁等谁。
5. Slow 题先拆阶段时间，再分别看 CPU、调度、内存、磁盘和网络；每个系统指标必须连接回目标请求或工作量。
6. 工具结论带边界：采样不等于逐次记录，附加会扰动，权限可能隐藏信息，优化会改变栈和变量。
7. 修复后同时完成最小回归测试、同条件对照实验、上线观察项和回滚条件；能解释根因不等于修复已安全上线。

## 13. 章末思考题与排障题

1. `./worker >out.log 2>err.log` 中 shell、fd 1 和 fd 2 分别做什么？
2. 为什么最终文件有读权限，程序仍可能因权限不足无法打开它？
3. `VmSize`、`VmRSS` 与应用独占物理内存为什么不能画等号？
4. 一个进程因 `SIGSEGV` 退出，完整的第一批现场应包含什么？
5. 为什么 core 必须配合完全匹配的二进制与调试符号？
6. `strace` 看到线程一直在 `futex`，可以直接宣布死锁吗？下一步是什么？
7. CPU 火焰图没有明显热点，但请求 p99 很高，你会怎样继续分层？
8. TCP 连接是 `ESTABLISHED`，为什么业务请求仍可能卡住？
9. ASan、UBSan 与 TSan 各主要发现什么？为什么不能把它们全部通过当成正确性证明？
10. 怎样安全使用 `git bisect` 定位性能回归？判定程序需要满足哪些条件？

1. shell 先解析命令和重定向，再启动 `worker`；它让子进程的 fd 1 指向 `out.log`，让 fd 2 指向 `err.log`。程序写 stdout/stderr 时内核经对应打开文件对象写入。两个 fd 分开，所以诊断信息不会自动和正常输出混在一起。
2. 路径解析要逐级穿过父目录，需要每级目录的相应执行/搜索权限；ACL、挂载只读、容器映射、SELinux/AppArmor 等策略也可能进一步限制访问。还要确认运行服务的实际 uid/gid，而不是当前登录用户。应沿完整路径与身份检查，不能只看末尾文件一行。
3. `VmSize` 包含尚未驻留、文件映射、共享库和保留地址等虚拟范围；`VmRSS` 统计当前驻留页，但共享页可能在多个进程视图中出现。独占物理内存还要区分私有/共享、PSS、页缓存和时间变化，因此三个量回答不同问题。
4. 至少保存退出时间、信号/退出状态、构建 ID 和 commit、精确二进制及动态库、匹配符号、stderr/服务日志、core、触发请求或输入摘要、运行参数和平台信息。先限制重启覆盖现场，再在敏感数据规则内收集。
5. core 主要保存当时寄存器和地址空间；符号把机器地址映射回函数、行和变量。编译或链接稍有变化，地址布局就可能不同，邻近版本的符号会产生错误函数名和栈。只有与 core 中二进制匹配的构建产物才能可靠解释地址。
6. 不可以。`futex` 说明线程在某类同步等待，正常 mutex、condition variable 和运行时也会这样。下一步查看所有线程用户栈、锁拥有者、等待持续时间和应用队列；只有形成不能自行打破的等待环，或所需唤醒路径已消失，才有死锁/永久等待证据。
7. 先用 trace 或阶段时间戳确认高 p99 花在排队、下游、磁盘、网络还是调度；再看 Off-CPU profile、线程状态、系统调用、运行队列、I/O 延迟与 socket 队列。CPU profile 只覆盖 On-CPU 样本，看不到大部分睡眠等待。
8. `ESTABLISHED` 只说明 TCP 状态机已建立连接。应用可能没有读取发送队列、线程在锁上等待、协议帧不完整、TLS/请求层仍未完成、下游数据库阻塞，或响应已生成却卡在发送缓冲。应沿 DNS/连接、握手、请求发送、服务处理和响应返回逐段找证据。
9. ASan 发现许多内存越界和释放后使用；UBSan 检查一部分未定义行为；TSan 发现许多实际执行到的数据竞争。它们依赖插桩、测试输入和本次线程交错，覆盖面不同，也不能证明状态机、锁自由进展或业务结果正确。应配合测试、审查、模糊测试和不变量推理。
10. 先固定机器、构建、输入和测试窗口，准备快速、确定、只读或可隔离回滚的好/坏判定；验证它在已知好、坏提交上能稳定分类，再设置边界运行 bisect。性能有噪声时应多次测量并采用预先定义阈值，不能用一次抖动判坏。找到首个坏提交后仍要解释代码变化如何造成指标变化，并添加回归测试。

## 14. 本章小结

- Crash、hang 与 slow 是三类不同症状，先固定对象、版本、窗口和基线。
- shell 组织参数、重定向和管道；权限要沿身份与完整路径检查。
- `/proc` 与 `ps` 提供进程视图，但一次快照不能替代时间证据。
- Crash 依赖退出原因、匹配符号、core、全线程栈和触发输入。
- Hang 先分忙循环与等待，再用系统调用和用户栈画等待关系。
- Slow 先拆阶段时间；CPU、Off-CPU、内存、磁盘和网络证据不能混为一层。
- Sanitizer 擅长发现不同类别错误，但插桩通过不是形式证明。
- Git 与 CI 的价值是保存版本、环境、回归测试和可复现证据。
