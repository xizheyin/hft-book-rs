# 为什么选择 Rust 编写系统程序

这里的**系统程序**，不是只指操作系统内核。凡是需要认真管理内存、文件、网络连接、线程或硬件资源的软件，都可以属于系统开发的一部分。例如：Web 服务器、数据库、消息队列、命令行工具、AI 推理服务和交易系统。

Rust 的特点可以概括为一句话：**它既允许程序员控制底层资源，又试图在编译阶段阻止常见的内存错误。**

这不表示 Rust 永远比其他语言快，也不表示所有项目都应该改用 Rust。选择语言是在正确性、开发效率、运行成本、现有代码和团队经验之间做取舍。本章先解释 Rust 提供了什么，再说明它的代价和适用边界。

## 1. 先从系统程序面对的问题说起

普通应用也会使用内存、文件和网络，但系统程序通常需要更明确地回答下面这些问题：

| 问题 | 一个具体例子 |
|---|---|
| 一块内存由谁负责释放？ | 解析请求时创建了缓冲区，请求结束后谁回收它？ |
| 资源可以被谁同时使用？ | 两个线程能否同时修改同一个连接状态？ |
| 资源何时释放？ | 文件写完后，文件描述符何时关闭？ |
| 数据如何表示？ | 内存中的结构体能否传给 C 库？ |
| 错误发生后怎么办？ | 读文件失败时，是重试、返回错误还是终止进程？ |

C 和 C++ 给程序员很大的控制力，但许多规则主要依靠程序员和代码评审维持。带追踪式垃圾回收器的语言会自动寻找不再使用的堆对象，减轻手动内存管理负担，但文件、锁和网络连接等资源仍然需要显式管理。

Rust 选择了另一条路：用类型系统和所有权规则描述“谁拥有资源、谁可以借用资源”，不满足规则的程序通常无法通过编译。

## 2. 内存安全到底在防什么

程序运行时会在内存中存放代码、变量和动态创建的数据。如果程序把某段内存释放后继续访问，或者写到了数组范围之外，结果可能是崩溃、数据损坏，甚至安全漏洞。

常见的内存错误包括：

- **悬垂引用**：引用指向的对象已经被释放；
- **重复释放**：同一块内存被释放两次；
- **越界访问**：读取或写入了数组范围之外的位置；
- **数据竞争**：多个线程在缺少正确同步时访问同一数据，并且至少一个线程在写。

在不使用 `unsafe` 的 Rust 代码中，编译器会通过所有权、借用、类型检查和运行时边界检查阻止这些问题中的很大一部分。数组或切片的动态下标仍可能需要运行时检查；下标越界时，程序会触发 panic，而不是悄悄读写未知内存。

“内存安全”不等于“程序一定正确”。Rust 仍然无法自动阻止错误的业务公式、死锁、无限循环、错误的权限判断或不合理的重试策略。

## 3. 所有权、移动与借用

### 3.1 所有权：谁负责这个值

在 Rust 中，每个值都有一个**所有者**。可以先把所有者理解为“负责在适当时候清理这个值的变量”。

```rust
fn main() {
    let message = String::from("hello");
    println!("{message}");
} // message 离开作用域，String 使用的堆内存在这里被释放
```

`String` 的文字内容通常存放在堆上。变量 `message` 拥有这块堆内存；当它离开花括号所表示的**作用域**时，Rust 会清理 `String`。

### 3.2 移动：把清理责任交给另一个变量

```rust
fn main() {
    let first = String::from("hello");
    let second = first;

    println!("{second}");
    // println!("{first}"); // 编译错误：所有权已经移动给 second
}
```

赋值没有复制字符串的堆内容，而是把所有权从 `first` **移动**给 `second`。编译器随后禁止继续使用 `first`，从而避免两个变量都认为自己应该释放同一块内存。

像整数这样的简单类型通常实现了 `Copy`，赋值时会复制值，所以移动规则看起来不同。关键不是“变量赋值后一定失效”，而是类型是否能够安全、便宜地按位复制。

### 3.3 借用：暂时使用，但不接管清理责任

函数如果只想读取字符串，没有必要取得它的所有权。可以传入引用 `&String`，这叫**借用**：

```rust
fn byte_length(text: &String) -> usize {
    text.len()
}

fn main() {
    let message = String::from("hello");
    let length = byte_length(&message);

    println!("{message} has {length} bytes");
}
```

引用不会负责释放 `message`。借用结束后，原所有者仍可以继续使用它。

Rust 的核心借用规则可以先记成两点：

1. 可以同时存在多个只读引用 `&T`；
2. 需要修改时使用可变引用 `&mut T`，同一段数据在这段借用期间不能再被其他引用访问。

这条规则把“读者可以共享，写者必须独占”的约束放进了类型系统。在线程之间共享数据时，还要配合互斥锁、原子类型或消息传递等同步手段，后续并发章节会详细解释。

### 3.4 生命周期：引用不能比被引用的数据活得更久

**生命周期**描述引用保持有效的范围。大多数生命周期由编译器自动推断，程序员并不需要给每个引用写标记。

下面的函数无法编译，因为它试图返回指向局部 `String` 的引用；函数结束后，局部值就会被释放：

```rust,compile_fail
fn broken_reference() -> &str {
    let temporary = String::from("hello");
    &temporary
}
```

编译器拒绝这段代码，是因为返回的引用会变成悬垂引用。生命周期标注可以表达多个输入引用与输出引用之间的关系，但不能把已经要被释放的数据“延长寿命”。

所有权的完整入门说明见 [The Rust Programming Language：Understanding Ownership](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)。

## 4. 没有追踪式 GC，不等于没有自动清理

**GC（Garbage Collector，垃圾回收器）**通常指运行时追踪堆上的对象，判断哪些对象已经无法访问，然后回收它们。Rust 默认不使用这种追踪式 GC。

Rust 仍然会自动清理资源，只是采用了不同机制：

1. 编译器根据所有权确定值的清理责任；
2. 值到达清理位置时，运行它的 `Drop` 实现；
3. `Drop` 可以释放堆内存，也可以关闭文件、释放锁或清理其他资源。

这种方式常被称为**基于作用域的资源管理**。它的价值不只在于内存：

```rust
use std::fs::File;
use std::io::{self, Write};

fn write_report() -> io::Result<()> {
    let mut file = File::create("report.txt")?;
    file.write_all(b"finished\n")?;
    Ok(())
} // file 离开作用域，它持有的文件描述符会被关闭
```

这里的 `?` 表示：如果创建或写入文件失败，就把错误返回给调用者。无论正常到达函数末尾，还是因为 `?` 提前返回，已经创建的 `file` 都会被清理。

不过仍要理解边界：

- `Drop` 中可以执行复杂或耗时的代码，所以自动调用不代表代价为零；
- `Rc` 或 `Arc` 通过引用计数共享所有权，循环引用可能需要额外设计；
- `std::mem::forget`、进程被强制终止或 `panic = "abort"` 等情况可能跳过正常析构；
- 内存安全代码仍然可能持有资源过久，例如把大对象一直保存在全局缓存中。

因此更准确的说法是：Rust 让许多资源具有明确的所有者，并在正常控制流中按作用域清理，而不是“Rust 会在任何情况下立即释放一切”。

## 5. 底层控制力从哪里来

Rust 适合系统开发，不只是因为安全检查，也因为它保留了对机器和操作系统的直接表达能力。

### 5.1 分配是可见的选择

局部整数、固定大小数组等值可以直接存放在栈帧或被编译器放进寄存器。`Box<T>`、`String` 和 `Vec<T>` 等类型会在需要时使用堆。程序员能够从类型和代码结构中看见很多分配行为，而不是所有对象都默认在堆上创建。

但不要把“看见类型”误解成“只看源码就能知道全部机器行为”。编译器会优化代码，容器也可能增长并重新分配；真正关心资源消耗时仍要使用测试和分析工具验证。

### 5.2 抽象可以在编译期展开

Rust 的泛型通常通过**单态化**实现：编译器为实际用到的具体类型生成代码。例如 `largest::<i32>` 和 `largest::<f64>` 可以分别生成适合对应类型的机器代码。

这让迭代器、泛型容器和 trait 等高级表达方式有机会被优化掉额外层次。不过“零成本抽象”是设计目标，不是每段代码的自动保证。动态分发、堆分配、边界检查和较大的生成代码仍可能存在。

### 5.3 可以直接使用操作系统能力

Rust 标准库提供线程、文件、TCP/UDP 网络、进程等常用接口。平台专用能力也可以通过第三方库或系统调用绑定访问。

这种控制力带来责任：平台接口可能具有复杂的错误码、并发规则和生命周期要求。Rust 类型可以包装这些规则，但包装本身必须写对。

## 6. `unsafe` 与 FFI：把无法自动证明的部分圈起来

有些合法的系统操作无法由编译器完全证明安全，例如解引用裸指针、调用某些 C 函数或实现底层并发结构。Rust 用 `unsafe` 标记这些操作。

`unsafe` 的含义不是“关闭所有检查”，也不是“让代码更快”。它表示：**这一小段代码需要程序员自己证明额外的安全条件成立。** 其余类型检查和借用规则仍然存在。

**FFI（Foreign Function Interface，外部函数接口）**让 Rust 调用其他语言编译的函数，最常见的是 C ABI。ABI 是二进制层面的约定，包括参数怎样传递、返回值放在哪里以及符号怎样命名。

与 C 交换结构体时，经常需要 `#[repr(C)]`：

```rust
#[repr(C)]
pub struct Point {
    pub x: f64,
    pub y: f64,
}
```

`#[repr(C)]` 让字段布局遵循 C 兼容规则，但它不会自动解决所有跨语言问题。接口设计还必须说明：

- 指针能否为空、指向多少个元素，以及保持有效多久；
- 内存由哪一侧创建，又由哪一侧释放；
- 字符串采用什么编码，是否以 `\0` 结尾；
- C++ 异常或 Rust panic 能否跨过边界；
- 两边使用的结构体版本与 ABI 是否一致。

好的做法是把 `unsafe` 和 FFI 集中在较小模块中，为外部提供经过校验的安全接口，并用测试覆盖边界条件。更详细的规则可查阅 [Rustonomicon：FFI](https://doc.rust-lang.org/nomicon/ffi.html)。

## 7. 工具链也是语言选择的一部分

语言不仅是一套语法。一个项目还需要构建、测试、依赖管理和代码检查工具。Rust 官方工具链提供了较一致的工作流：

| 工具 | 作用 |
|---|---|
| `rustup` | 安装与切换 Rust 工具链、目标平台和组件 |
| `rustc` | 把 Rust 源代码编译成机器代码或库 |
| `cargo` | 创建项目、管理依赖、构建、测试和生成文档 |
| `rustfmt` | 按统一规则格式化代码 |
| `clippy` | 发现常见错误和不清晰的写法，并给出提示 |
| `rustdoc` | 从源码注释生成 API 文档，也能运行文档中的示例测试 |

例如，一个常见的本地检查流程是：

```bash
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

它分别检查格式、静态提示和测试。工具不能替代设计与评审，但统一入口能降低项目成员之间的环境差异。工具的具体用法可从 [Cargo Book](https://doc.rust-lang.org/cargo/) 和 [Rust 官方工具页](https://www.rust-lang.org/tools) 开始。

## 8. Rust 的代价与不适用场景

只讲优势会导致错误的技术选择。Rust 常见的成本包括：

- **学习成本**：所有权和生命周期要求读者改变一部分编程习惯；
- **编译时间**：大型泛型项目和复杂依赖树可能需要较长的构建时间；
- **生态覆盖不均**：通用系统开发生态已经很丰富，但特定厂商 SDK、桌面框架或行业库可能仍以其他语言为主；
- **底层代码仍需审查**：依赖中的 `unsafe`、FFI 和系统调用包装不会因为外层是 Safe Rust 就自动正确；
- **迁移成本**：重写成熟系统会引入兼容、验证和人员培训风险。

以下选择都可能比采用 Rust 更合理：

- 团队已经拥有稳定的 C++ 平台和丰富的诊断经验；
- 产品依赖只提供 Java、C# 或 Python 接口的成熟框架；
- 任务是短期数据分析脚本，开发速度比资源控制更重要；
- 系统瓶颈来自数据库查询或网络架构，换语言不能解决根因；
- 项目生命周期很短，学习和迁移成本无法收回。

正确的问题不是“Rust 是否最好”，而是“Rust 的安全边界、资源控制和工具链，能否抵消当前项目中的学习、生态与迁移成本”。

## 9. 三类应用怎样使用这些能力

前面的机制不属于某一个行业。不同系统只是强调点不同：

| 场景 | Rust 能解决的通用问题 | 仍需额外考虑 |
|---|---|---|
| 传统互联网后端 | 网络连接、并发状态、资源清理、可靠部署 | 数据库设计、服务治理、团队已有框架 |
| AI Infra | 模型服务、数据处理、Python/C++ 扩展、内存与设备资源封装 | GPU 软件栈、张量库成熟度、与研究代码协作 |
| HFT | 二进制协议、进程与线程控制、与已有 C/C++ 系统集成 | 交易正确性、风险控制、行情与交易所规则 |

Rust 在三类场景中提供的是同一组语言能力。是否采用它，应当由具体系统的约束决定，而不是先假设某个行业天然需要某种语言。

## 本章小结

Rust 用所有权表达资源责任，用借用限制并发访问，用生命周期防止引用越过数据的有效范围。它不依赖追踪式 GC，而是让许多资源在正常控制流中按作用域清理；同时，它保留了系统接口、内存表示和 FFI 等底层能力。

这些特性减少了一类错误，却不会自动保证业务正确、性能优秀或项目成功。学习 Rust 最重要的不是记住“安全且快”的口号，而是能说明每个机制解决什么问题、不能解决什么问题，以及它是否符合当前项目的真实约束。

## 做题方法

分析一段 Rust 代码为什么能或不能通过编译时，先画“所有权变化表”，每条语句占一行：

| 步骤 | 值/资源 | 当前所有者 | 活跃借用 | 本步之后能否使用原绑定 |
|---|---|---|---|---|
| 创建 | 堆上字符串 | `s` | 无 | 能 |
| `let t = s` | 同一个字符串 | `t` | 无 | `s` 不能 |
| `let r = &t` | 同一个字符串 | `t` | `r: &String` | `t` 可只读 |

具体推演按以下顺序进行：

1. 先判断类型是否实现 `Copy`；实现 `Copy` 的赋值复制值，否则通常转移所有权。
2. 为每个 `&T` 和 `&mut T` 标出从创建到最后一次使用的边界；边界重叠时检查“多个只读”或“唯一可写”规则。
3. 遇到函数调用，把参数传递也当成一次移动、复制或借用；返回值再决定资源的新所有者。
4. 走到作用域结束时，按局部变量的销毁规则标出 `Drop`，检查资源是否恰好释放一次。
5. `unsafe` 题不要删掉这张表，而要另外写出编译器无法证明、由程序员承担的前置条件。

验算点是：任意时刻一个非 `Copy` 值只能有一个负责销毁它的所有者；可变借用活跃时不能还有能访问同一值的其他引用。若违反，先定位到具体重叠区间，而不是只背“借用检查器不允许”。

## 思考题与面试题

1. `String` 从变量 `a` 移动到变量 `b` 后，为什么默认不能再使用 `a`？这条规则避免了什么错误？
2. `&T` 与 `&mut T` 分别允许什么操作？为什么 Rust 不允许同一时刻既有可变引用又有其他引用访问同一数据？
3. 为什么“Rust 没有追踪式 GC”不能直接推出“程序不会突然变慢”或“所有资源一定及时释放”？
4. Safe Rust 能阻止数据竞争，为什么仍然可能出现死锁和业务逻辑竞态？
5. 调用 C 函数时，为什么只写 `unsafe` 还不够？请列出调用方必须确认的三个安全条件。
6. 如果一家团队已经有成熟的 C++ 服务，你会收集哪些证据，再决定新模块使用 Rust 还是继续使用 C++？

## 参考答案与解答

<details><summary>展开答案</summary>

1. `String` 拥有堆分配；`let b=a` 把唯一销毁责任移给 b，a 失效。若两者都继续当所有者，会发生 double free；若都不负责，则泄漏。
2. `&T` 允许共享读取，`&mut T` 允许独占修改。同一数据同时存在可写和其他可访问引用会使读写交错、引用失效和优化别名假设冲突。
3. Rust 仍可能有大对象 Drop、分配器慢路径、锁等待、页错误和调度暂停；RAII 只在所有权正常离开作用域时运行，进程 abort/断电也不会完成外部清理。
4. 数据竞争是未同步的冲突内存访问，类型系统可阻止 Safe Rust 中的 UB；死锁是合法锁操作形成等待环，业务竞态是合法同步下事件顺序不符业务预期，二者仍可能发生。
5. 至少确认 ABI/签名与布局、指针范围/对齐/有效位模式、生命周期与所有权/释放责任；还要处理错误码、线程安全和 panic/异常边界。
6. 收集现有 C++ 团队能力与库复用、模块安全风险、FFI 边界/迁移成本、性能与延迟基线、部署/调试工具、长期维护和招聘、故障历史。用小型原型比较正确性、产物、端到端性能与运维，不因语言标签直接决定。
