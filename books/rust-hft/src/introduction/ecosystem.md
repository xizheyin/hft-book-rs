# 怎样为 Rust 项目选择工具与依赖

刚开始学习 Rust 时，很容易被大量库名淹没。实际上，大多数项目都应该按这个顺序开始：

1. 先把要解决的问题说清楚；
2. 查看 Rust 语言和标准库是否已经提供所需能力；
3. 如果确实缺少功能，再比较第三方依赖；
4. 引入后，用测试验证它在本项目中的行为。

库是否合适取决于输入、并发方式、错误处理、部署平台和团队维护能力。因此，依赖选择需要从项目组成、功能缺口、维护状态和验证方法逐步推导，不能依赖一张固定的“必装库”名单。

## 1. 先认识 Rust 项目的几个基本概念

### 1.1 标准库

Rust **标准库**随 Rust 工具链一起提供。它包含常用类型与操作，例如：

- `Vec`、`String`、`HashMap` 等集合；
- `Option` 和 `Result` 等状态与错误表达；
- 文件、TCP/UDP、线程、锁、原子变量和进程接口；
- 时间、路径、环境变量和命令行参数处理。

标准库的优势是无需增加第三方依赖，文档与兼容策略也由 Rust 项目统一维护。能用标准库清楚解决的问题，没有必要为了“看起来专业”而增加一个库。

标准库也不会包办一切。例如，它提供 `Future` 这个异步计算接口，却没有内置完整的异步任务调度器；它能够建立 TCP 连接，却没有内置完整的 HTTP Web 框架。

### 1.2 package、crate 与 module

这三个词经常同时出现，但含义不同：

- **package（包）**：由一个 `Cargo.toml` 描述的项目单位；
- **crate**：Rust 编译器一次编译的代码单位，可以是库，也可以是可执行程序；
- **module（模块）**：用 `mod` 组织 crate 内部代码的命名空间。

一个 package 可以包含一个库 crate、多个二进制 crate 和示例、测试等目标。日常交流中，人们也常把发布到公共仓库的第三方库简称为 crate。

### 1.3 Cargo 与 registry

**Cargo** 是 Rust 官方的构建与包管理工具。它负责读取 `Cargo.toml`、解析依赖、调用编译器、运行测试和生成文档。

**registry（注册表）**是存放 package 元数据和发布版本的索引服务。[crates.io](https://crates.io/) 是 Rust 社区默认使用的公共 registry，但团队也可以使用私有 registry 或直接依赖 Git 仓库和本地路径。

Cargo 解析出的具体版本会记录在 `Cargo.lock` 中，从而让后续构建尽量使用同一组依赖版本。`Cargo.toml` 表达允许的版本范围，`Cargo.lock` 记录一次解析得到的精确结果。

完整术语与项目布局见 [The Rust Programming Language：Packages and Crates](https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html)。

## 2. 怎样读一个最小的 `Cargo.toml`

```toml
[package]
name = "example-service"
version = "0.1.0"
edition = "2024"

[dependencies]
serde = { version = "1", features = ["derive"] }
```

逐行理解：

- `[package]` 描述当前 package；
- `name` 是包名，`version` 是当前项目版本；
- `edition` 选择 Rust 语言版本的兼容规则；它不是编译器版本；
- `[dependencies]` 列出正常构建和运行需要的第三方 package；
- `version = "1"` 使用 Cargo 的版本要求语法，允许兼容的 `1.x` 版本；
- `features = ["derive"]` 打开 Serde 的可选功能，以便使用派生宏生成部分实现。

**feature** 是 crate 作者提供的条件编译开关。它可以启用额外协议、平台支持或集成能力。feature 不是越多越好：打开不需要的功能可能带来更多传递依赖、编译时间和可审查代码。

项目还可能使用：

```toml
[dev-dependencies]
proptest = "1"
```

`dev-dependencies` 通常只在测试、示例或基准等开发目标中使用，不会因为普通依赖关系自动成为最终程序的运行功能。具体语法应以 [Cargo Book：Specifying Dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html) 为准。

## 3. 引入依赖前先问八个问题

### 3.1 它解决的具体问题是什么

不要从“大家都用 Tokio”或“这个库号称零拷贝”开始。先写出需求，例如：

> 服务需要同时等待数千个网络连接，大部分连接多数时间没有数据；线程不能在每个空闲连接上单独阻塞。

明确需求后，才知道应研究异步运行时，而不是任意并发库。

### 3.2 标准库或一小段本地代码是否已经够用

如果只是读取一个配置文件或启动一个线程，标准库往往足够。另一方面，不要为了避免依赖而自己重写密码学、HTTP 协议或复杂解析器；这些领域包含大量不容易察觉的边界条件。

判断标准不是“依赖数量必须为零”，而是引入的复杂度是否小于自己实现和维护的复杂度。

### 3.3 API 的语义是否匹配需求

API（Application Programming Interface，应用程序编程接口）不只是函数名。还应确认：

- 输入归谁所有，返回值能保持多久；
- 操作失败时返回错误、等待、丢弃还是 panic；
- 队列是否有容量限制，满了以后发生什么；
- 函数是否会阻塞当前线程；
- 是否会创建后台线程或持有全局状态。

一个库即使基准成绩很好，只要错误或容量语义不符合系统要求，就不是合适选择。

### 3.4 项目是否仍在维护

可以查看最近发布、提交记录、issue 响应和维护者说明。但“最近没有提交”不一定代表项目坏了：一个范围很小且已经稳定的库可能本来就不需要频繁变化。

更有用的问题是：发现安全漏洞或新平台问题时，是否有人负责发布修复？如果停止维护，团队能否替换或自行接管？

### 3.5 安全记录与 `unsafe` 边界怎样

第三方库与本项目代码一样，可能包含缺陷。可以检查：

- 是否发布过安全公告；
- 是否大量使用 `unsafe`，以及安全条件是否有文档和测试；
- 是否解析不受信任的网络或文件输入；
- 是否能使用 `cargo audit` 等工具对照 [RustSec Advisory Database](https://rustsec.org/) 检查已知公告。

工具只能发现数据库中已经记录的问题，不能证明依赖完全安全。

### 3.6 传递依赖与 feature 是否可控

A 依赖 B，B 又依赖 C，C 就是 A 的**传递依赖**。传递依赖越多，需要下载、编译、升级和审查的代码通常也越多。

可以用 `cargo tree` 查看依赖树，用 `cargo tree -e features` 查看 feature 怎样被启用。不要只数依赖个数；一个经过广泛使用的大库可能比若干自制小库更可靠。重点是团队是否理解并能维护这棵依赖树。

### 3.7 平台、许可证和最低 Rust 版本是否合适

采用前应确认：

- 目标操作系统和 CPU 架构是否受支持；
- crate 要求的最低 Rust 版本是否符合构建环境；
- 许可证能否用于项目的发布方式；
- 是否依赖系统库、C 编译器或特殊运行环境；
- WebAssembly、嵌入式或无标准库环境是否可用。

### 3.8 怎样验证与退出

为重要依赖准备测试，而不是只相信 README。还要考虑退出方案：能否把它包装在本项目定义的接口后面，以便将来替换？数据格式是否被某个库的私有表示永久锁定？

## 4. 按“问题”认识常见工具

下表提供的是搜索起点，不是默认选型。链接指向项目主页或官方文档；实际使用前还要核对当前版本与维护状态。

| 要解决的问题 | 首先考虑 | 何时研究第三方工具 | 采用前确认 |
|---|---|---|---|
| 集合、文件、线程、锁、TCP/UDP | [Rust 标准库](https://doc.rust-lang.org/std/) | 标准库缺少所需协议、调度方式或平台能力 | 是否真的缺功能 |
| 应用错误的上下文 | `Result`、自定义错误类型 | [anyhow](https://github.com/dtolnay/anyhow) 可简化应用层错误汇总；[thiserror](https://github.com/dtolnay/thiserror) 可生成结构化错误实现 | 调用者是否需要匹配具体错误类型 |
| 结构化数据转换 | 手写明确的数据结构与解析 | [Serde](https://serde.rs/) 支持多种数据格式的统一序列化接口 | 外部输入校验、格式兼容与版本演进 |
| 大量等待型 I/O | 阻塞线程和标准库网络是否足够 | [Tokio](https://tokio.rs/) 提供异步运行时、网络、定时器和任务调度 | 阻塞代码、取消、超时与关闭流程 |
| 并发通道和数据结构 | `std::sync::mpsc`、锁、原子类型 | [Crossbeam](https://github.com/crossbeam-rs/crossbeam) 提供多类并发工具 | 生产者/消费者数量、容量和断开语义 |
| 字节缓冲区 | `Vec<u8>`、`&[u8]` | [bytes](https://github.com/tokio-rs/bytes) 便于共享、切片和组合网络字节 | 切片仍引用底层存储，何时可以复用 |
| 日志与执行过程观测 | 简单输出或项目已有日志接口 | [tracing](https://github.com/tokio-rs/tracing) 用 span 和 event 表达嵌套操作 | 日志级别、字段隐私、输出与采样策略 |
| 命令行参数 | `std::env::args` | [clap](https://github.com/clap-rs/clap) 提供参数声明、校验和帮助信息 | 参数兼容、二进制大小和 feature |
| 自动生成多组测试输入 | 普通单元测试 | [proptest](https://github.com/proptest-rs/proptest) 可按规则生成输入并缩小失败案例 | 生成规则是否覆盖真实约束 |
| 测量一小段代码 | `std::time::Instant` 和端到端测试 | [Criterion.rs](https://github.com/bheisler/criterion.rs) 提供带统计分析的微基准 | 基准是否代表真实工作，结果是否被优化掉 |
| 调用 C/C++ | 手写很小且稳定的 C ABI 声明 | [bindgen](https://github.com/rust-lang/rust-bindgen) 生成 C 绑定；[cxx](https://cxx.rs/) 约束 Rust/C++ 桥接 | ABI、所有权、异常、panic 与销毁责任 |

这里出现的术语会在后续章节展开。例如：

- **异步运行时**负责保存并推进暂时不能完成的异步任务；
- **序列化**把内存中的数据结构转换成适合存储或传输的格式；
- **span**表示一段有开始和结束范围的操作，event 表示其中某个时刻发生的事件；
- **微基准**只反复测量很小的代码片段，不能自动代表整个服务。

## 5. 三个最容易被名字误导的概念

### 5.1 异步不等于并行

异步主要解决“任务等待 I/O 时，线程可以推进其他任务”。并行表示多个 CPU 核心在同一时间执行计算。

写成 `async fn` 不会自动让 CPU 计算变快。如果在异步任务中直接执行很长的阻塞操作，还可能阻止同一执行线程上的其他任务继续运行。完整机制见[Async Rust 与 Tokio](../foundations/async_rust.md)。

### 5.2 零拷贝通常只是少了一次明确的复制

一个解析器返回 `&[u8]`，可以避免把输入内容再复制到新的 `Vec<u8>`。但这并不代表整个系统完全没有数据搬运：设备、内核、驱动和协议层仍可能复制数据。

借用原缓冲区还有代价：只要结果仍引用它，生产者就不能随意修改或复用那块存储。看到“zero-copy”时，应问清楚省掉的是哪一步复制，以及谁负责维持底层数据的生命周期。

### 5.3 无锁不等于不会等待

**lock-free（无锁）**是一种算法进展保证：系统整体能够继续完成操作，但某一个线程仍可能不断重试。它不表示操作永远立即完成，也不表示队列不会满。

无锁结构通常比普通锁更难验证。只有线程模型和瓶颈证据明确时，才应承担这份复杂度。完整推导见[无锁数据结构](../infrastructure/lock_free.md)。

## 6. 一个可重复使用的选择流程

假设你需要让程序读取 JSON 配置。可以按以下步骤工作：

1. **写需求**：输入来自本地文件；字段固定；未知字段是否允许；错误需要显示给操作人员。
2. **看标准库**：标准库能读文件，但没有通用 JSON 解析器。
3. **找候选**：研究 Serde 与具体 JSON 格式实现，查看文档、维护状态和许可证。
4. **做最小实验**：用一份正确配置和若干错误配置验证字段、默认值和错误信息。
5. **包住边界**：让业务代码调用自己的 `load_config`，不要在各处散落第三方库细节。
6. **锁定与检查**：提交可复现的依赖解析结果，并在持续集成中运行测试和安全检查。
7. **记录理由**：说明为什么标准库不够、为什么选该实现，以及以后怎样替换。

同一流程也适用于网络框架、数据库驱动、并发队列和 FFI 工具。工具名称会变化，“需求—候选—验证—维护”的思路不会变化。

## 8. 三类项目怎样使用生态

同一个 Rust 生态可以服务不同方向，选型的起点始终是问题：

| 场景 | 常见问题 | 可能研究的工具类别 |
|---|---|---|
| 传统互联网后端 | HTTP、数据库、身份验证、日志、任务调度 | 异步运行时、Web 框架、数据库驱动、`tracing` |
| AI Infra | 模型服务、数据管道、Python/C++/GPU 组件连接 | 网络运行时、序列化、FFI、内存与设备封装 |
| HFT | 二进制协议、进程间通信、硬件接口、回放验证 | 字节缓冲、并发工具、FFI、测量与测试工具 |

表中的工具类别只是候选。例如传统后端不一定需要异步，AI Infra 不一定需要 Rust 重写模型计算，HFT 也不一定需要无锁队列。先确定系统结构，再选择库。

## 本章小结

标准库是默认起点，Cargo 负责构建与依赖管理，crate 是编译单位，package 是由 `Cargo.toml` 描述的项目单位。第三方依赖能够节省大量实现和维护工作，也会增加需要信任、升级和审查的代码。

选择依赖时，不要背排行榜。先说明问题，再比较标准库和候选库的语义，检查维护、安全、平台与许可证，最后用自己的输入和失败场景验证。能清楚讲出“为什么需要、它怎样工作、边界在哪里”，比记住大量库名更重要。

## 思考题与面试题

1. package、crate 和 module 有什么区别？一个 package 为什么可能包含多个 crate？
2. `Cargo.toml` 与 `Cargo.lock` 分别表达什么？为什么只有版本范围还不足以完全记录一次构建使用的依赖？
3. 标准库已经有 TCP 和线程，项目仍可能为什么选择 Tokio？哪些项目反而不需要它？
4. 引入一个第三方队列前，需要确认哪些容量、阻塞和断开语义？
5. “这个解析库是零拷贝的”这句话缺少哪些上下文？
6. 为什么依赖最近没有提交，不能单独证明它已经无人维护？你还会检查什么证据？
7. 选择一个你熟悉的依赖，按“问题—标准库差距—语义—维护风险—验证方法”完整说明一次选择理由。
