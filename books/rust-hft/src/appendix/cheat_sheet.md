# Rust 低延迟开发速查表

这张表用于面试前复习和代码评审，不是第一次学习概念的教材，也不要求逐项背诵。看到陌生词时先回到对应章节：CPU/缓存见[程序执行总览](../foundations/computer_execution.md)，并发见[并发模型](../foundations/concurrency.md)，网络见[网络基础](../network/basics.md)，市场术语见[术语表](glossary.md)。看到“通常”“优先”时，要继续问：**在哪个硬件、什么负载、哪条关键路径、用什么证据？**

面试前优先复习正确性不变量、端到端延迟、分位数、内存分配、并发拓扑和失败恢复。RCU、SeqLock、Hazard Pointer、PGO 等专项名词只在简历项目或岗位说明涉及它们时复习；速查表中出现不等于通用必考。它们在下面出现时仍会给出一句定义，方便你判断是否需要继续读。

## 0. 优化顺序

```mermaid
flowchart LR
    A[定义正确性不变量] --> B[定义端到端指标]
    B --> C[建立可复现基线]
    C --> D[剖析定位瓶颈]
    D --> E[一次只改一个因素]
    E --> F[性能 + 语义回归]
    F -->|未达目标| D
    F -->|达标| G[记录条件并持续监控]
```

> **口诀**：先正确，后可测；先端到端，后局部；先证据，后技巧。

## 1. 指标速查

| 指标 | 回答什么问题 | 常见陷阱 |
|---|---|---|
| P50 | 平常一次有多快 | 看不见少量长暂停 |
| P99 / P99.9 | 尾部有多差 | 样本不足、负载不真实 |
| Max | 观测期最差一次 | 对样本时长和环境噪声敏感 |
| Throughput | 单位时间处理多少事件 | 排队可能让吞吐高、延迟差 |
| Queue depth | 下游是否跟不上 | 只看均值会漏掉瞬时堆积 |
| Drop / Gap | 是否丢弃或缺失数据 | “没报错”不等于没丢数据 |
| CPU / cycles | 计算资源消耗 | 100% CPU 对忙轮询可能是设计选择 |
| Cache/TLB miss | 访存是否拖慢执行 | 计数器含推测执行，需结合代码分析 |

`P50`、`P99` 分别是第 50、99 百分位：约 50% 或 99% 的样本不超过该值。`TLB`（Translation Lookaside Buffer，地址转换后备缓存）保存近期虚拟地址到物理地址的转换结果；TLB miss 表示还要走更慢的页表查询路径。

### 基准必须记录

```text
硬件：CPU/NUMA/内存/网卡
软件：OS/内核/rustc/LLVM/依赖版本
构建：release、target-cpu、LTO（链接时优化）、PGO、panic 策略
负载：数据来源、分布、峰值、预热、批大小、并发度
结果：P50/P99/P99.9/max、吞吐、错误、队列、CPU
验证：输出哈希/逐事件比对/回放不变量
```

## 2. CPU、缓存与内存

| 概念 | 准确理解 | 何时考虑 |
|---|---|---|
| Cache line | 缓存和一致性协议处理的数据块；很多 x86_64 系统是 64 B，但应确认目标硬件 | 热数据布局、跨核写共享状态 |
| False sharing | 多核写同一缓存行里的不同字段，导致缓存行反复转移 | `perf c2c`、基准或一致性事件显示问题时 |
| Padding / align | 隔开热点字段，但会增加对象大小与缓存占用 | 少量、高频、跨核写字段 |
| AoS（Array of Structures，结构体数组） | 一条记录的字段放一起 | 每次处理需要同一记录的大多数字段 |
| SoA（Structure of Arrays，数组结构） | 同类字段放在连续数组 | 批量只处理少数字段、希望向量化时 |
| Huge pages | 较大页面可减少 TLB 压力，但增加配置和内存碎片风险 | 大而稳定的工作集且 TLB miss 已成瓶颈 |
| Prefetch | 提前把将访问的数据拉近 CPU | 访问模式可预测、计算能覆盖取数延迟时 |
| Branch prediction | CPU 猜测控制流；稳定偏向分支通常容易预测 | 分支不可预测且确认为热点时再改写 |

### 布局保证

- 默认 `repr(Rust)` 不保证字段声明顺序或稳定 ABI（Application Binary Interface，二进制调用与布局约定）；可用 `size_of`、`align_of`、`offset_of` 检查当前构建，但不能把结果当跨版本协议。
- `#[repr(C)]` 固定 C 兼容布局规则，主要用于 FFI（Foreign Function Interface，跨语言调用边界）；它不会自动处理字节序、填充字节和协议版本。
- `#[repr(packed)]` 可能产生未对齐字段。创建对未对齐字段的引用会有安全问题，应使用按值复制或 `read_unaligned`/`write_unaligned` 并审查 `unsafe`。
- `#[repr(align(64))]` 保证起始对齐，不代表类型“只占一条缓存行”，也不保证适配所有硬件。

## 3. 分配、容器与所有权

| 类型/技术 | 主要成本 | 使用建议 |
|---|---|---|
| `Box<T>` | 一次堆分配、间接访问、释放 | 启动期和冷路径很常见；热路径是否可用取决于是否反复分配和访问模式 |
| `Vec<T>` | 容量增长时分配与复制 | 启动期 `with_capacity`，热路径复用并定义最大容量 |
| `String` | 与 `Vec<u8>` 类似，另有 UTF-8 语义 | 协议热路径常优先借用字节，边界处再转换 |
| `SmallVec` | 类型更大；超过内联容量仍会分配 | 小集合大小分布稳定时评估，别只看最好情况 |
| `Rc<T>` | 非原子引用计数 | 单线程共享；clone/drop 仍有计数和潜在释放 |
| `Arc<T>` | 原子引用计数、堆分配 | 跨线程所有权管理；避免在每条消息上无意义 clone/drop |
| `Cow<'a, T>` | 枚举分支；写入时可能克隆 | 大多数输入只读、少量需要规范化时适用 |
| Arena / Slab | 批量管理生命周期，可能保留内存 | 对象大小与生命周期可分组且上限清楚时 |
| 对象池 | 复用对象，但引入归还、清理和容量管理 | 分配确为瓶颈，且能处理耗尽/污染/跨线程问题时 |

### 热路径检查

```text
[ ] 是否发生容量增长？
[ ] 是否隐式格式化或构造错误字符串？
[ ] 是否频繁 clone/drop Arc？
[ ] 大对象 Drop 是否形成尾延迟？
[ ] 缓冲区复用前是否清理了业务状态？
[ ] 池耗尽时是阻塞、丢弃、降级还是扩容？
```

## 4. Rust 抽象成本

| 机制 | 常见实现成本 | 不能直接推出的结论 |
|---|---|---|
| 泛型 | 单态化、可内联，可能增加代码体积 | 不代表一定比 `dyn Trait` 快 |
| `dyn Trait` | 通常一次间接调用，可能阻碍内联 | 不代表在冷路径不可用 |
| 迭代器 | 常能优化为紧凑循环 | 不代表所有 adapter 链都零成本 |
| 闭包 | 捕获状态形成匿名结构体 | 不捕获闭包常可转函数指针，但需看用法 |
| `Result<T, E>` | 带判别的值类型，大小取决于布局优化 | 不存在异常展开成本，不代表错误路径免费 |
| `Option<T>` | 某些 `T` 可用 niche 优化 | 不是所有 `Option<T>` 都和 `T` 一样大 |
| `async fn` | 编译为保存跨 await 状态的状态机 | 不代表适合最严格的 thread-per-core 热循环 |
| 宏 | 编译期生成代码 | 不自动保证生成代码正确、紧凑或易调试 |

### 静态分发还是动态分发

```text
热路径、类型集合固定、需要内联
    → 优先评估泛型/枚举分发

插件边界、冷路径、减少代码膨胀、运行期替换
    → dyn Trait 可能更清晰

最终决定
    → 比较端到端延迟、I-Cache（指令缓存）/代码体积和维护成本
```

## 5. 并发模型决策表

| 场景 | 优先考虑 | 关键问题 |
|---|---|---|
| 单线程拥有状态 | 普通 `&mut T`、事件循环 | 单事件会不会阻塞整个分片？ |
| 单生产者单消费者 | 有界 SPSC（Single Producer, Single Consumer）环形缓冲区 | 满/空语义、背压、缓存行与内存顺序 |
| 多生产者单消费者 | MPSC（Multiple Producers, Single Consumer）或生产者分片 | 生产者是否争用同一入队位置？ |
| 低竞争共享配置 | `Arc` + 不可变快照/整体替换 | 更新是否原子、旧快照何时释放？ |
| 一般共享读写 | `Mutex` / `RwLock` | 临界区、竞争、优先级反转；持锁线程 panic 后如何处理可能已被破坏的状态 |
| 读多写少快照 | RCU（发布新副本后延迟回收旧副本）或 SeqLock（读者发现版本变化就重试） | 读取是否可安全重试？写者是否唯一？旧数据何时可回收？ |
| 无锁回收 | Epoch（等全部读者越过旧代际再回收）或 Hazard Pointer（读者公布正在使用的指针） | ABA（值曾改变又恢复，CAS 可能误以为没变）、生命周期、回收延迟、内存上界 |

### 进展保证

- **Blocking**：线程可能睡眠等待其他参与者。
- **Lock-free**：系统整体持续取得进展，不保证每个线程不饥饿。
- **Wait-free**：每个操作在有界步骤内完成；这是比 lock-free 更强的证明责任。

“用了原子”不等于 lock-free；“没有 Mutex”也不等于 wait-free。

## 6. 原子内存顺序

| Ordering | 直觉 | 常见用途 |
|---|---|---|
| `Relaxed` | 只要求该原子操作不可撕裂，不建立其他数据的跨线程先后关系 | 独立统计计数、已由其他同步保护的状态 |
| `Release` store | 发布它之前的写入 | 生产者发布“数据已就绪” |
| `Acquire` load | 看到发布后，也能看到发布前的写入 | 消费者读取“已就绪”后访问数据 |
| `AcqRel` | 对读部分 Acquire、写部分 Release | 读改写原子操作 |
| `SeqCst` | 额外提供单一全局顺序模型 | 正确性优先或确实需要全序时 |

典型发布关系：

```rust,ignore
// Producer（伪代码）：先写普通数据，再发布就绪标志
slot.write(message);
ready.store(true, Ordering::Release);

// Consumer：Acquire 观察到 true 后读取数据
if ready.load(Ordering::Acquire) {
    let message = slot.read();
}
```

这是发布关系的伪代码，故意省略了 `slot`、`message` 和队列类型，mdBook 不把它当成独立程序编译。实际无锁代码还涉及别名、初始化、回收和回绕；不能只复制两行 Ordering。优先使用成熟实现，并用 Loom/Miri/模型推理补充常规测试。

## 7. 网络与 I/O

| 选择 | 优势 | 代价/边界 |
|---|---|---|
| Blocking socket | 简单，易调试 | 每连接线程模型可能扩展差；唤醒有抖动 |
| epoll/kqueue | 大量连接、成熟 | 就绪通知、系统调用和事件循环管理 |
| `io_uring` | 可批量提交/完成，适合多类异步 I/O | 内核版本、操作语义和运维复杂度 |
| UDP multicast | 一份行情高效分发给多个订阅者 | 不可靠，必须处理缺口、重复、乱序和恢复 |
| TCP | 有序可靠字节流 | 队头阻塞；应用仍需会话序号和业务恢复 |
| Busy polling | 减少睡眠/唤醒延迟 | 独占 CPU、功耗、热量和公平性成本 |
| Kernel bypass | 更直接控制 RX/TX（接收/发送）、队列与轮询 | 驱动、NIC（网卡）、内存、监控、升级与故障处理更复杂 |

### 行情链路不变量

```text
[ ] 每个序号作用域都能识别 gap、duplicate、out-of-order
[ ] 快照与增量有明确对齐点
[ ] 恢复期间策略状态明确：停止、降级或切换冗余源
[ ] 解析器拒绝非法长度、类型和字段，不越界、不挂起
[ ] 本地订单簿可校验：非负数量、合法价格、序号连续
[ ] A/B 通道仲裁不会把同一事件应用两次
```

## 8. 编译与性能工具

| 目标 | 常用工具/方法 | 注意事项 |
|---|---|---|
| 微基准 | Criterion、`std::hint::black_box` | 防止常量折叠，确认输入分布和预热 |
| CPU 剖析 | `perf record/report`、火焰图 | 采样频率、符号和生产开销 |
| 硬件计数 | `perf stat` | 多路复用、推测执行和系统噪声 |
| 缓存争用 | `perf c2c` | 需要支持的内核/硬件，结合对象地址解释 |
| 汇编 | `cargo asm`、Compiler Explorer | 汇编短不等于端到端快 |
| 内存安全 | Miri、sanitizers | 覆盖有限，不能证明所有 `unsafe` 正确 |
| 并发模型 | Loom | 只探索抽象模型中的调度，需要缩小状态空间 |
| 模糊测试 | `cargo-fuzz` | 设计语料、字典和不变量，长期运行 |
| PGO（Profile-Guided Optimization，基于运行画像的优化） | 代表性负载采样后重新优化 | 负载偏差可能反优化，需与非 PGO 版本 A/B |

### Release profile 不是固定答案

```toml
[profile.release]
opt-level = 3
lto = "thin"       # 也可比较 fat/off
codegen-units = 1   # 可能改善优化，但增加构建时间
panic = "abort"    # 采用前先设计进程恢复与状态核对
```

`target-cpu=native` 适合在同一机器构建并运行的实验，不适合直接分发到未知 CPU。生产应明确最低指令集、构建主机与运行主机兼容策略。

## 9. 上线前清单

### 正确性

- [ ] 协议版本、字节序、价格精度和消息上限已固定。
- [ ] 订单状态机覆盖 Ack、Partial Fill、Fill、Cancel、Replace、Reject 与重复回报。
- [ ] 风控位于不可绕过的边界；失败默认拒绝还是降级已有明确策略。
- [ ] 回放、属性测试、fuzz 和故障注入覆盖关键不变量。

### 性能

- [ ] 用峰值和突发负载验证，不只用均匀流量。
- [ ] 同时报分位数、吞吐、队列、丢弃和 CPU。
- [ ] 绑核、NUMA、IRQ（硬件中断请求）、频率与大页配置可审计、可回滚。
- [ ] 新优化的收益超过噪声，并在多次独立运行中复现。

### 恢复与运维

- [ ] 断线、丢包、磁盘满、时钟异常、依赖超时都有演练。
- [ ] 重启后先核对会话、未决订单、成交与持仓，再恢复交易。
- [ ] Kill switch 有权限、审计、演练和解除流程。
- [ ] 监控和日志不会在热路径失控；观测系统失效时行为明确。

## 10. 面试一分钟答题模板

```text
1. 场景与假设：生产者/消费者数量、流量峰值、延迟目标、正确性要求
2. 我的选择：先给清晰结论
3. 原因：指出主成本或不变量
4. 权衡：至少一个失败模式和替代方案
5. 验证：基准、剖析、回放、测试、上线指标
```

例如，被问“要不要用无锁队列”时，先确认拓扑和背压，再回答；不要把“无锁”当作自动更快。能说清 **什么时候不该用**，通常比背出实现更能体现工程成熟度。
