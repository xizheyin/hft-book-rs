# 一次程序怎样在计算机里运行

刚接触计算机系统时，CPU、进程、内核、内存、网卡和磁盘很容易变成一串孤立名词。理解它们最好的办法，不是先背名词，而是跟着一项真实工作走完整条路：程序收到一条网络请求，读取内存中的数据，生成结果，再把日志写入文件。

## 1. 先认识整台计算机中的对象

一台常见服务器可以先分成五类对象：

| 对象 | 它是什么 | 为什么需要它 |
|---|---|---|
| CPU | 执行机器指令的处理器 | 完成计算、判断和数据搬运 |
| 内存 | CPU 可以直接读写的临时存储 | 保存正在运行的代码和数据 |
| 存储设备 | SSD、硬盘等长期保存数据的设备 | 断电后仍能保留程序和文件 |
| I/O 设备 | 网卡、存储控制器等与外界交换数据的设备 | 接收网络数据或读写持久存储 |
| 操作系统 | 管理硬件并为程序提供共同接口的软件 | 隔离程序、分配资源并控制设备 |

这里的 **I/O（Input/Output，输入输出）**，指程序与外部对象交换数据，例如接收网络包、读取文件或写入日志。CPU 主要负责执行指令；网卡和存储设备负责具体传输。操作系统把两者连接起来。

## 2. 源代码怎样变成进程

源代码是给人阅读的文本，CPU 不能直接执行它。以 Rust 程序为例，启动前后会经历下面几步：

1. **编译器**把 Rust 源代码翻译成目标 CPU 能执行的机器指令。
2. **链接器**把程序自身和所需的库组合成可执行文件。
3. 用户或服务管理器发出启动请求，操作系统创建一个**进程**。进程是一次程序运行所拥有的内存、文件和权限的资源边界。
4. **加载器**把可执行文件中的代码和数据放入进程的虚拟地址空间，并准备栈、动态库和程序入口。
5. 操作系统的**调度器**从进程中选择一个线程，把它安排到 CPU 上执行。线程是一条能够被调度的指令执行流。

“程序”和“进程”不是同一个概念：程序通常指磁盘上的可执行文件，进程指它的一次运行实例。同一个程序可以启动多次，形成多个相互隔离的进程。编译、链接和装载的具体分工见[指令系统、机器码与程序装载](isa_machine_code.md)，进程与线程的完整关系见[进程、线程与文件描述符](processes_fds.md)。

```mermaid
flowchart LR
    S["Rust 源代码"] --> C["编译和链接"]
    C --> E["磁盘上的可执行文件"]
    E --> L["操作系统加载"]
    L --> P["进程及其地址空间"]
    P --> T["可执行的线程"]
    T --> X["CPU 执行机器指令"]
```

## 3. CPU 为什么不能只靠自己工作

CPU 执行机器指令。指令可以进行算术运算、比较两个值、读取内存、写入内存，或决定下一条要执行的指令。指令怎样经过取指、译码和执行等硬件路径见 [CPU 数据通路](cpu_datapath.md)。

程序正在使用的代码和数据放在内存中。CPU 访问内存需要时间，因此处理器旁边还有 **Cache（高速缓存）**。Cache 保存近期使用过的一小部分代码或数据副本，让 CPU 不必每次都等待主内存。Cache 的映射、替换和一致性机制见[存储层次](memory_hierarchy.md)。

可以把三者的关系理解为：

```text
CPU 寄存器：容量最小，CPU 当前直接操作的数据
    ↕
CPU Cache：保存近期常用数据的副本
    ↕
主内存：保存当前运行程序的大部分代码和数据
    ↕
SSD / 硬盘：长期保存文件，CPU 不能像访问内存一样直接使用它
```

程序中的地址通常是**虚拟地址**。虚拟地址是进程看到的地址编号，不是内存芯片上的直接位置。CPU 的地址翻译硬件和操作系统维护的页表共同把它转换成物理内存位置，这一过程见[虚拟内存](virtual_memory.md)。

## 4. 为什么应用不能直接控制硬件

如果每个应用都能任意修改内存映射或设备状态，一个程序的错误就可能破坏其他程序甚至整台机器。为此，CPU 提供不同的执行权限：

- **用户态**是普通应用运行时使用的受限权限；
- **内核态**允许操作系统内核管理内存、调度和设备。

Linux 的核心部分叫**内核**。应用需要读取文件、发送网络数据或创建进程时，会发起**系统调用**。系统调用是应用请求内核服务的受控入口，例如 `read`、`write` 和 `send`。

一次系统调用大致经历：应用准备参数，CPU 切换到内核态，内核检查参数并完成工作，最后返回用户态。权限发生切换，不代表一定换了线程；只有当前线程需要等待或被调度器暂停时，CPU 才可能改为运行另一个线程。

## 5. 内核、驱动和设备怎样合作

内核不会亲自实现每一种网卡或 SSD 的硬件协议。它用通用接口表达需求，再由了解具体硬件控制方法的**驱动**准备请求。设备从队列取得请求，常用 **DMA（Direct Memory Access，直接内存访问）**在设备和内存之间传输批量数据，并以中断或轮询报告完成。DMA 不等于 CPU 退出 I/O：CPU 和内核仍要创建请求、检查权限、处理协议并接收结果。中断、DMA 与设备控制器由[计算机 I/O 硬件](io_hardware.md)主讲；操作系统如何缓冲、排队和唤醒线程见[I/O 管理](io_management.md)。

```mermaid
flowchart LR
    A["应用线程"] -->|"系统调用"| K["操作系统内核"]
    K --> S["文件系统或网络栈"]
    S --> D["设备驱动"]
    D --> Q["设备队列"]
    Q --> H["网卡或存储设备"]
    H -->|"中断或轮询得到完成结果"| D
    H <-->|"DMA 传输数据"| M["主内存"]
```

## 6. 一条网络请求的完整流程

现在把各层重新连起来。假设一个服务收到请求，查询内存状态，返回响应并记录日志：

1. 网卡接收到网络数据，并把数据传到内存。
2. 驱动和内核网络栈解析数据。网络栈是内核中处理 TCP、IP 等网络协议的部分，它会找到正在等待这条连接的进程。
3. 内核让相应线程变为可运行，调度器再把线程安排到 CPU。
4. CPU 执行程序指令，从 Cache 或内存中读取请求和业务数据。
5. 程序生成响应，通过系统调用让内核把数据交给网卡发送。
6. 程序调用 `write` 记录日志。内核通常先把日志复制到内存中的页缓存，稍后再交给存储设备。

这条流程中不存在一个“自动完成一切”的组件。CPU 负责执行，内存保存当前状态，内核提供抽象和隔离，驱动控制设备，设备负责实际收发和持久存储。

## 7. 常见误解

- **“源代码可以直接在 CPU 上运行。”** CPU 执行的是编译后或解释器生成的机器指令。
- **“程序启动就是把整个文件复制进内存。”** 操作系统会建立地址映射，许多页面在真正访问时才载入。
- **“进入内核就一定更换线程。”** 系统调用的权限切换和调度器更换线程是两件事。
- **“DMA 以后 CPU 就不用参与 I/O。”** DMA 负责数据传输，CPU 仍要准备请求和处理完成。
- **“`write` 返回说明数据已经进入 SSD。”** 普通文件写入往往先到页缓存，持久化是后续步骤。

## 8. 三类系统怎样使用这些基础

前面的机制对所有程序都成立，区别只在于各类系统更关心哪一段：

| 场景 | 常见关注点 | 对应基础 |
|---|---|---|
| 传统互联网服务 | 大量连接、数据库读写、故障恢复 | 线程调度、网络栈、文件系统和持久化 |
| AI Agent 平台 | 启动大量隔离任务、调用模型和工具、限制资源 | 进程隔离、虚拟内存、网络 I/O 和操作系统权限 |
| HFT 系统 | 在稳定负载下减少等待和波动 | Cache、调度、设备队列和完整测量 |

基础知识先帮助我们回答“系统怎样正确工作”。只有在具体场景明确之后，才讨论容量、吞吐或响应时间等工程目标。

## 做题方法

遇到“一个程序或一次请求经过哪些层”的题，可以按下面的顺序画因果链：

1. **先找起点和终点**：起点是源代码、可执行文件、系统调用还是设备事件；终点是进程创建、数据返回还是持久化完成。题目不同，链条不能套用同一个终点。
2. **给每一步标执行者**：用户程序、CPU、内核、驱动、设备控制器分别做什么。若一句话没有明确主语，就容易把“内核发起 I/O”误写成“CPU 亲自搬完所有数据”。
3. **圈出边界跨越**：编译/链接发生在运行前；系统调用跨越用户态与内核态；中断由设备事件触发。边界前后的上下文必须连得上。
4. **分别画控制流和数据流**：例如网卡 DMA 搬数据属于数据流，中断通知 CPU 属于控制流。二者可以相关，但不是同一件事。
5. **用反问验算**：若去掉内核，权限和资源隔离由谁保证？若去掉驱动，通用内核接口怎样变成设备命令？答不上来通常说明链条漏了一层。

常见陷阱是把“执行了系统调用”直接等同于“发生了进程切换”，或把“函数返回”直接等同于“外设工作全部完成”。是否切换、返回承诺到哪一步，都要由具体机制决定。

## 9. 章末思考题

1. 为什么可执行文件和进程不是同一个对象？
2. 为什么内存中的数据断电后通常会丢失，而 SSD 中的数据可以保留？
3. 系统调用为什么不一定伴随线程切换？
4. DMA 替 CPU 完成了什么，哪些工作仍要由 CPU 和内核完成？
5. 画出一次网络请求从网卡进入、经过应用，再由网卡发出的完整路径。
6. 如果 `write` 已经返回，为什么仍不能直接断定日志已经持久化？

一分钟复述：**程序被加载为进程，线程在 CPU 上执行；CPU 通过 Cache 和内存取得数据，应用通过系统调用请求内核，内核再经驱动和设备完成网络或存储 I/O。** 能按这个顺序复述，说明你已经建立了整机地图；它也可以作为面试回答的开头。

### 参考答案与解答

<details><summary>展开答案</summary>

1. 可执行文件是存储介质上的代码和静态数据；进程是装载后形成的运行实例，还包含独立地址空间、线程、fd 和内核状态。同一文件可同时产生多个互相隔离的进程。
2. DRAM 用需要持续供电和刷新的电荷状态保存 bit，断电后状态消失；SSD 用非易失存储单元保存电荷阈值，断电后仍能保持。这里说的是介质性质，不代表一次普通写已经到达 SSD 的非易失边界。
3. 系统调用只表示当前线程受控进入内核。如果请求能立即完成，内核可返回同一线程；只有阻塞、时间片耗尽或更高优先级任务等情况才需要调度并切换任务上下文。
4. DMA 控制器在设备与主存间成块搬数据，减少 CPU 逐字节复制。CPU/内核仍要分配缓冲区、编程描述符、维护权限与缓存一致性、处理完成事件和错误。
5. 入站路径是 `网卡接收 → DMA 到主存 → 中断/轮询 → 驱动 → 网络协议栈 → socket 缓冲 → 应用 read`；应用处理后，出站沿 `应用 write → socket/协议栈 → 驱动描述符 → 网卡 DMA 取数据 → 发出`。验算点是数据流与“通知 CPU”的控制流分开标注。
6. 缓冲 I/O 的 `write` 通常在数据进入页缓存后返回；脏页、文件元数据、设备缓存和目录项可能仍未持久化。应依据故障模型调用并检查 `fsync`，新文件/重命名还可能需要同步父目录。

</details>
