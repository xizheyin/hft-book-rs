# 吞吐量优化：批处理、流水线与背压

> **面试优先级：P0。** 必须会解释“到达率超过处理率为什么必然排队”、批处理为什么既省固定成本又增加等待，以及队列满时怎样背压。具体 batch size 只能测量，不能背答案。

在低延迟系统中，吞吐量（Throughput）常常被误解为“次要指标”。事实上，延迟与吞吐量并不是彼此独立的两个世界。只要系统进入持续负载状态，吞吐量不足就会立刻表现为排队长度增加、缓存失效增多和尾延迟恶化。换句话说，许多看似“延迟问题”的现象，本质上都来自吞吐能力与到达速率之间的不匹配。

为了建立分析框架，可以先从最基本的排队关系出发。`λ`（lambda）表示平均到达率，`μ`（mu）表示稳定服务率。在负载分布相对稳定、容量模型成立的前提下，`λ < μ` 是长期不无限积压的必要条件；实际系统还要为突发、服务时间波动和故障留余量。当 `λ` 接近 `μ` 时，短暂波动更难被消化，P99 和 P999 往往迅速拉长。工程上需要的不只是“单次处理更快”，而是“在高负载下维持有余量的服务能力”。

## 1. 用 Little 定律连接吞吐、等待和在途数量

仅知道“每秒处理多少条”还不足以解释延迟，因为正在排队和处理中的工作也占用内存与时间。对一个长期稳定、统计口径一致的系统，可以用 **Little 定律**建立第一层估算：

<div class="formula" role="math" aria-label="Little's Law">
L = λ × W
</div>

其中，`L` 是系统内平均有多少项工作，`λ` 是平均完成率，`W` 是一项工作从进入到离开的平均停留时间。三者必须统计同一边界和同一时间段。

例如，一个服务稳定完成 100,000 条消息每秒，每条消息平均在系统内停留 2 毫秒，则平均在途消息数约为：

```text
L = 100,000 条/秒 × 0.002 秒 = 200 条
```

如果吞吐仍是每秒 100,000 条，而平均停留时间升到 20 毫秒，平均在途数量就会升到约 2,000 条。这个结果提示我们检查排队和内存，而不是只看处理函数本身。

Little 定律是稳定状态下的平均关系，不直接预测 P99，也不能替代突发流量分析。面试使用它时先说清统计边界与单位，再用延迟分布和队列时间验证。

## 2. 吞吐量的代价模型

吞吐量并不直接等于每秒执行的函数次数，而是单位时间内系统能够完成的有效工作量。对于消息处理系统、订单流系统或网络网关，更有意义的指标通常是：

- 每秒处理消息数（messages/s）
- 每秒处理字节数（bytes/s）
- 每核吞吐量（throughput per core）
- 达到目标吞吐时的尾延迟

一个有用的近似模型是：

<div class="formula" role="math" aria-label="batch throughput approximation">
Throughput ≈ BatchSize / (FixedCost + VariableCost × BatchSize)
</div>

它说明了批处理的价值。若一次系统调用、一次原子同步或一次队列提交存在不可忽略的固定成本，那么把多个元素合并处理，往往比逐条处理更接近硬件上限。

公式中 `BatchSize` 是一批的元素数，`FixedCost` 是每批只支付一次的成本，`VariableCost` 是每个元素仍需支付的成本。这只是帮助推理的近似式，没有包含缓存失效、排队和下游拥塞。

## 3. 批处理：用摊还成本换取吞吐量

逐条处理消息的最大问题，不在于单条消息本身，而在于每条消息都要重复经历取队列指针、执行边界检查、更新原子变量和触发缓存一致性协议。批处理的作用，是把这些固定开销分摊到一组消息上。

```rust
pub fn consume_one_by_one<T: Copy, F: FnMut(T)>(
    buf: &[T],
    mut handler: F,
) {
    for item in buf {
        handler(*item);
    }
}

pub fn consume_in_batches<T: Copy, F: FnMut(&[T])>(
    buf: &[T],
    batch_size: usize,
    mut handler: F,
) {
    let mut start = 0;
    while start < buf.len() {
        let end = (start + batch_size).min(buf.len());
        handler(&buf[start..end]);
        start = end;
    }
}
```

这段代码并不复杂，但它对应着两种完全不同的成本结构。第一种写法把处理边界设定在“单条消息”上，第二种写法把处理边界设定在“批次”上。若 `handler` 内部需要提交网络发送、写入共享队列或更新可见性状态，批处理带来的收益会远高于示例代码本身所表现出来的差异。

不过批处理并不是越大越好。批次过大时，虽然平均吞吐量会上升，但首条消息在批次内部的等待时间也会增加，最终损害交互式场景中的响应时间。因此，工程上真正需要的是**受控批处理**：在吞吐量与延迟预算之间寻找一条稳定边界，而不是盲目扩大批次大小。

## 4. 流水线：把工作拆成可并行阶段

当单个处理步骤已经较难继续缩短时，另一种常见方法是把工作拆成多个阶段，通过流水线并行（Pipeline Parallelism）提升整体吞吐量。典型例子包括：

- 网络接收
- 协议解析
- 业务计算
- 编码与发送

```mermaid
flowchart LR
    A[接收 Receive] --> B[解析 Parse]
    B --> C[计算 Compute]
    C --> D[编码 Encode]
    D --> E[发送 Send]
```

流水线的核心收益不在于单个阶段更快，而在于多个阶段可以重叠执行。若每个阶段分别占用不同核心，并通过有界队列连接，那么系统的稳定吞吐量大致由最慢的阶段决定，而不是所有阶段耗时之和决定。

但流水线也引入新的问题。阶段之间一旦不平衡，较慢阶段之前的队列就会持续积压；而队列积压一旦出现，缓存局部性、预取效果和尾延迟都会同步恶化。因此，流水线设计不能只关注“并行度”，还必须关注“阶段平衡”。

## 5. 背压：防止吞吐量问题转化为失控排队

背压（Backpressure）是高吞吐系统中最容易被忽略、却最决定稳定性的一层机制。它回答的问题是：**当下游处理不过来时，上游应该如何减速或拒绝新工作。**

如果没有背压，系统通常只会做两件事：

- 把更多消息堆入队列
- 把更多对象推入堆分配器

这两件事看似“没有丢数据”，实际却会迅速把问题转化为：

- 队列长度不可控
- 内存占用上升
- 分配器、内存回收或操作系统 reclaim 压力增大
- P99/P999 延迟失真

一个最简单的背压机制是有界队列：

```rust
pub struct BoundedQueue<T> {
    buf: std::collections::VecDeque<T>,
    cap: usize,
}

impl<T> BoundedQueue<T> {
    pub fn push(&mut self, value: T) -> Result<(), T> {
        if self.buf.len() == self.cap {
            return Err(value);
        }
        self.buf.push_back(value);
        Ok(())
    }

    pub fn pop(&mut self) -> Option<T> {
        self.buf.pop_front()
    }
}
```

这种写法的意义并不在于它本身足够高性能，而在于它揭示了一个原则：队列容量不是“缓存空间”，而是“系统预算”。一旦容量达到上界，就必须显式地选择等待、丢弃、降级或重试，而不是让负载无上限地向下游传播。

## 6. 吞吐量与延迟的权衡

批处理、流水线和背压三者组合之后，系统往往会出现一个典型张力：

- 更大的批次有利于提升吞吐量
- 更深的流水线有利于提高并行度
- 更严格的背压有利于控制尾延迟

但同时：

- 更大的批次会增加单条消息等待时间
- 更深的流水线会增加阶段切换与排队成本
- 更严格的背压会降低短期峰值吞吐能力

因此，性能优化不应只比较“最快”实现，而应比较在目标负载下哪一种设计具有最好的稳定性。对于高性能系统，更有价值的衡量往往是：

- 在给定 P99 限制下的最大吞吐量
- 在给定 CPU 预算下的稳定处理速率
- 在突发流量下的退化方式是否可预测

## 7. 工程实践建议

第一，批处理应围绕固定成本设计，而不是围绕“整数倍更整齐”设计。只有当批次能够减少系统调用、同步开销或共享状态更新时，它才真正带来收益。

第二，流水线要围绕瓶颈阶段做容量规划，而不是平均分配工作。最慢的阶段决定了稳定吞吐能力，其前一阶段队列长度则决定了尾延迟恶化速度。

第三，背压机制必须是显式的。无论采用阻塞等待、丢弃策略还是优先级降级，关键都在于让系统在高负载下的行为可预测，而不是依赖隐式的内存扩张来“暂时掩盖问题”。

## 8. 小结

吞吐量优化不是“让循环更快”这么简单，而是通过批处理降低固定成本、通过流水线重叠执行阶段、通过背压限制负载传播，把系统从“单条消息视角”提升到“持续负载视角”。只有在这个层面上理解吞吐量，后续关于队列、网络 I/O 和可扩展性设计的讨论才有统一的分析基础。
